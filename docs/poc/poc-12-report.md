## 2. 做了什么

| 部分 | 内容 |
|---|---|
| `adapters/llm/` | `LlmAdvisor`（方案顾问的第三个实现）：把助手给的内容写成提示词 → 调用大模型 → 把回复解析成提议。两种协议：**Anthropic（Claude）** 和 **OpenAI 兼容**（DeepSeek、通义千问、智谱、Kimi 等）。`HttpClient` 端口和一个调用系统 `curl` 命令的实现 |
| BC-3 检测执行 | 调试运行时额外给出各节点输出的**统计信息**：图像的灰度分位数、区域选中的像素比例、连通域的面积列表。产线检测不计算（要把图像扫一遍） |
| 命令行 | `assist run <任务书> --llm <配置.json>`；`--no-statistics` 用于对比实验；和大模型的全部往来另存为 `<会话ID>.llm.json` |
| 示例 | `samples/assistant/llm.deepseek.json`、`llm.claude.json`；第二个场景 `golden sample --scenario glare` 和工作流 `bright-spot-glare`（三个可调项） |

助手的领域层和应用层**没有改动**。

### 怎么试

```bash
export VISION_LLM_API_KEY=你的密钥
```

```bash
vision-cli assist run ./golden-demo/brief.json --llm samples/assistant/llm.deepseek.json
```

换一家服务只需要改配置文件里的 `protocol`、`baseUrl`、`model`。

### 密钥怎么处理

- 只从环境变量读。配置文件里写了 `apiKey` 会被拒绝（配置文件会进代码仓库）
- `baseUrl` 必须是 https
- 密钥只出现在请求头里：不在命令行参数、日志、会话记录、往来记录里
- 交给 `curl` 的请求头写在一个只有当前用户能读的临时文件里，用完立即删除

## 3. 实测结果（DeepSeek）

### 3.1 和搜索顾问比

| 场景 | 可调项 | 搜索顾问 | 大模型顾问（有统计信息） |
|---|---|---|---|
| 亮斑（阈值、最小面积） | 2 | 10 轮 | **1、1、3、1、3 轮**（5 次，全部达标） |
| 亮斑 + 反光（再加最大面积） | 3 | 20 轮 | **1、1、1 轮**（3 次，全部达标） |

- 每次调用 2～3 秒；每轮输入约 4,600 个 token（16 个用例），输出约 200 个。一次会话的费用可以忽略
- 搜索顾问每轮只要 0.02 秒，所以按总时间算，这两个场景上搜索顾问反而更快（0.2～0.4 秒对 3～8 秒）。**大模型的优势是轮数不随可调项的个数增长**：用例多、单次检测慢、可调项多的时候才体现出来
- 大模型给的理由是能读懂的。一次真实的回复：

  > 误报全部来自 ok 用例里的小连通域：4 像素（灰尘）……真正的 NG 亮斑面积为 113 到 441 像素，亮度 p99.9 超过 232。……把阈值提高到约 180，使背景（最大约 162）不再被二值化……minArea 约 60，这样能保留最小的缺陷 113 像素，同时滤掉灰尘。

  它确实是从统计数字里“读”出了背景的亮度、灰尘和缺陷的面积，并且在两者之间选了值——这正是搜索顾问做不到的。

### 3.2 统计信息有多重要

同一个场景（亮斑，2 个可调项），只改“给不给统计信息”：

| | 轮数（4～5 次） | 达标 |
|---|---|---|
| 有统计信息（灰度分位数、连通域面积……） | 1、1、3、1、3 | 5 / 5 |
| 没有统计信息（只有“image 640x480”“blobs 3”和判定） | 15、6、7（放弃）、4 | 3 / 4 |

**结论：统计信息是大模型顾问的“眼睛”，默认必须给。** 没有它，大模型只能盲猜，比搜索顾问还差，而且有一次试了 7 轮之后自己放弃了。

这也回答了“不外发图像行不行”：**在这类任务上，不外发图像完全够用**。图像里对调参有用的信息，几个数字就概括了。外发图像是否还能带来额外的好处，要等有了能看图的模型再测。

### 3.3 发现的问题

1. **达标的参数不一定稳。**（已处理：增加了加固阶段，见 [hardening-report.md](hardening-report.md)。其中也更正了下面关于“阈值留在 100 很脆弱”的判断。） 反光场景里，大模型和搜索顾问都把阈值留在了初始的 100，改用“最大面积”把整块背景排除掉。调参集和盲测集都达标，但这个方案是靠背景恰好连成一大块才成立的，很脆弱。这和 POC-11 报告 §8 说的是同一个问题：**评估规则只数判错了几个，不奖励余量**。提示词里已经要求“不要贴着边界”，大模型在面积上照做了，在这一点上没有。
2. **每次的结果不一样。** 同样的输入，5 次得到 5 组不同的参数（阈值 160～200，最小面积 20～60）。都达标，但不可重现。好在会话记录和往来记录把每一次都完整记了下来，事后查得清。
3. **“出错”结束时，进行到一半的那一轮被计入“被拒绝”**，报告里的数字容易误解。（已修：现在记为“未完成”。）

## 4. 实现时做的决定（请确认）

| # | 决定 | 理由 |
|---|---|---|
| 1 | HTTP 请求通过系统自带的 **`curl` 命令**发出，不链接 HTTP 库 | POC 阶段不想多一个要在三个平台上编译的依赖（还要带上 TLS 库）。macOS、Linux、Windows 10 以上都自带 curl。**鸿蒙上没有**，所以这只是过渡：`HttpClient` 是端口，正式版换成 libcurl 或系统的网络接口 |
| 2 | 每一轮是**一次独立的请求**，不保留对话；需要的历史由助手每轮重新给 | 简单；状态只有一份（在会话聚合里）；任何一轮都可以单独重放 |
| 3 | 看不懂的回复变成**一份空的提议**，由助手拒绝并记录，消耗一轮预算 | 不在适配器里另写一套重试逻辑；大模型在下一轮能看到“上一轮被拒绝” |
| 4 | 大模型提出改结构之类的越界修改时，**如实转给助手的规则去拒绝**，不在适配器里悄悄丢掉 | 规则只在一个地方；记录里能看到大模型到底想干什么 |
| 5 | 限流、服务繁忙、超时：重试（默认 2 次）；密钥错误、请求不合法：不重试，直接失败 | 再试也没用的错误不该浪费时间 |
| 6 | 用例很多时不全发：判错的全部发，判对的每类最多 6 个 | 控制请求的长度和费用；判错的才是需要解决的 |
| 7 | 统计信息由**检测引擎**在调试运行时计算，不由助手或顾问计算 | 它是“节点输出的摘要”的一部分，以后界面上查看中间结果也用得上 |
| 8 | Claude 的默认模型写的是 `claude-opus-5-5`，请求里带了“被安全策略拒绝时由服务端换模型重试”的参数 | 按 Anthropic 当前的接口文档写的。**没有实测**（没有密钥） |

## 5. 没有做到的、已知的局限

1. **鸿蒙上没有验证**（A12 的后一半）。
2. **外发图像的两种策略没有实测。** 图像的读取、缩小、编码、附加到请求里都写了，也测了“策略不允许时不发、允许时只发调参集的、缩略图确实缩小了”，但没有一个真的能看图的模型看过它们。
3. **Anthropic（Claude）协议没有实测。** 只有请求格式和回复解析的单元测试。
4. **没有增加“带旋转定位或卡尺测量”的工作流**（后来补了卡尺算子和 `width-measure` 工作流：搜索顾问 6 轮、大模型 2 轮调到达标，稳健性 8 项全过。定位仍然没有，原因见 [../dev/operators.md](../dev/operators.md) §4。）——平台现在只有 5 个算子，没有这类算子。改用了同一条流水线上更难的一个场景（反光，3 个可调项）。它检验了“可调项变多”，没有检验“换一类任务”。
5. **只测了一种模型**（`deepseek-chat`），每种设置 3～5 次。次数少，上面的轮数只能看趋势。
6. **图像是合成的**，同 POC-11。
7. `curl` 客户端在 Windows、macOS 上没有真的发过请求（自动构建里只测了“连不上时返回失败”）。
8. 没有防**提示词注入**：任务书里的“目标”是用户写的文字，原样放进了提示词。现在大模型能做的只是提出调参提议，而提议要过规则检查，所以危害有限；但以后做“自由搭建”时必须重新考虑。

## 6. 对下一步的影响

- **“不外发图像，只给统计信息”作为默认策略成立。** D7-4 可以定下来：默认不外发，统计信息默认给。
- **搜索顾问应该留着**：它不联网、不花钱、可重现，适合作为没有大模型时的后备，也可以在大模型调到达标之后接着用它在达标范围里找中间值。
- 最值得接着解决的是 §3.3 第 1 条（余量）。一个直接的做法：把稳健性检查的结果也算进“哪个更好”，并且达标之后不立即结束，再用几轮扩大余量。这是助手领域层的改动，需要先定设计。
- 鸿蒙上的网络调用并入 POC-3b（ArkWeb 桥接）一起验证比较合适：到时候请求可以由界面那一侧发出。
