## 2. 性能（参考，Release 构建）

方案：输入 → 灰度 → 阈值 → Blob → 计数判定（5 个节点）。

| 图像 | 单张耗时 |
|---|---|
| 640×480（0.3MP） | 约 0.7 ms |
| 2592×1944（5MP） | 约 8 ms（第一张约 17 ms，含首次内存分配） |

NFR-03 要求 5MP、约 6 个节点的流程 < 100 ms：**满足**，余量很大。

**评价**：分层带来的额外代码主要是每个上下文的公开接口 `api.h` 和应用服务（三个上下文合计约 570 行），以及边界规则的 CMake 脚本（约 60 行）。换来的是：领域层可以不依赖任何技术独立测试；上下文边界由编译器保证。对于一个要长期维护、跨三个平台的项目，**这个代价可以接受**。

日常开发的感受：写一个新功能通常要动“领域对象 → 应用服务 → `api.h`”三处，比直接写多一步，但每一处都很薄，职责清楚。

## 4. 过程中发现的问题

| # | 问题 | 处理 |
|---|---|---|
| 1 | **算子注册的 bug**：用 ID 的引用作为 map 的键，但 ID 在之前已经随对象一起被 `std::move` 走了，导致所有算子都以空字符串为键，只剩第一个 | 已修复；新增回归测试 `catalog_tests` |
| 2 | 静态注册的算子如果打包进普通静态库，会被链接器丢弃 | 算子改用 CMake 的 OBJECT 库；已在 `operators/CMakeLists.txt` 中注明 |
| 3 | **ROI 使用像素坐标，因此方案和相机分辨率绑定**：同一个方案换到分辨率不同的相机上，ROI 会落到错误的位置 | 记为新的设计问题，建议在标定（BC-6）和相对 ROI 时一并考虑，见 §6 |
| 4 | 测试中给草稿加了未连线的节点后再发布，被发布规则 P1 正确拒绝 | 不是 bug，说明领域规则在起作用；测试已改为明确断言这个行为 |

## 5. 与设计文档的差异

| # | 差异 | 原因 | 是否需要改设计文档 |
|---|---|---|---|
| 1 | 共享内核除了视觉基础类型，还包含了**算子签名**（`OperatorSignature`、`PortDef`、`ParamDef`、`ParamValue`） | 算子目录、方案编排、检测执行三方都要用同一套方式描述“算子长什么样”，必须完全一致，符合共享内核的定义 | 是，更新 05 §1 |
| 2 | 图像入口算子叫 `vision.image_input`（POC 计划中写的是 `load_image`） | 图像由执行引擎送入，而不是算子自己读取文件，名字更准确 | 是，更新 04-poc-plan |
| 3 | 检测结果目前只有判定依据，还没有缺陷、测量值、位姿三类结果项（EXE-03） | POC-1 只验证架构 | 否，MVP 实现 |
| 4 | ROI 只支持矩形；相对 ROI、模型依赖、标定需求及对应的发布规则 P2～P4 未实现 | 依赖的概念（位姿、模型仓库、标定）还没有 | 否，按计划在 P1 实现 |
| 5 | 检测记录不保存（没有 `InspectionRepository`） | POC-1 不需要 | 否，MVP 实现（ADR-20 用 SQLite） |
| 6 | JSON 文件损坏时视为“不存在”，没有报告错误 | POC 简化 | 否，MVP 修正 |

## 6. 建议

1. **接受 A1 的结论**，以 POC-1 的代码结构作为正式开发的基础。
2. 新增设计问题：**ROI 与图像分辨率的关系**（§4 第 3 条）。可选方案：ROI 用归一化坐标；或在方案中声明期望的图像尺寸，部署时检查工位相机的分辨率。建议放到第 7 步场景走查的补充中讨论。
3. 更新设计文档中的两处差异（§5 第 1、2 条）。
4. 下一步：**POC-3a**（鸿蒙交叉编译与 NAPI）。POC-1 的核心代码没有平台相关的部分，可以直接拿去交叉编译。
