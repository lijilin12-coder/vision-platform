## 1. 要回答的问题

平台现在所有的能力都在命令行里。POC-2 不是“做一个好看的界面”，而是验证三件架构上还没碰过的事：

1. **核心能不能被一个长期运行的服务包起来。** 命令行是“启动、做一件事、退出”；服务要同时应付多个请求，一直开着。
2. **Web 界面能不能只通过一个接口（`PlatformClient`）使用核心。** 以后在鸿蒙上，同一套界面要换成通过 ArkWeb 的桥来调用；现在接口定得不好，那时就得重写界面。
3. **中间结果（图像）传到浏览器够不够快。** 调参数时改一下、看一眼，这个来回要在 300 毫秒以内才不难受。

计划里原来的通过标准只有一条，这里展开成可以逐条检查的（§7）。

## 2. 范围

**做：**

- `vision-runtime`：一个本地 HTTP 服务（第二个组装根），把已有的应用服务原样暴露出来
- 一个页面：算子面板、画布（节点和连线）、参数面板、图像预览
- 能做的事：新建或打开方案；拖入节点、连线、改参数；选一幅图像调试运行；点任何一个节点看它的输出（图像、区域、数字、判定依据）；发布方案

**不做（留给以后）：**

| 不做 | 原因 |
|---|---|
| 在图像上画 ROI、框模板 | 需要 Konva 画布交互，是单独的一块工作量。先用数字输入框 |
| 方案助手、训练、模型仓库、工位的界面 | 每一个都是一组页面。POC-2 只验证“这条路通不通” |
| 登录、多用户、同时编辑 | 服务只监听本机 |
| 撤销 / 重做、画布布局的保存 | 布局先由界面自动排，不存 |
| 鸿蒙上的 `BridgeClient` | 需要设备（POC-3b） |
| 界面美化、响应式布局、英文界面 | — |

## 3. 整体结构

```
浏览器（Vue 3 页面）
   │  只认识 PlatformClient 这个接口（TypeScript）
   ▼
HttpPlatformClient ───── HTTP（JSON；图像是 PNG）─────► vision-runtime（C++）
                                                          │  HTTP 接口层：只做“翻译”
                                                          ▼
                                                   应用服务（和命令行用的是同一批）
                                                   AuthoringService、ExecutionService、OperatorCatalog …
```

三条约束，写进代码结构里：

- **HTTP 接口层不含业务规则。** 它只把请求翻译成对应用服务的调用，把结果翻译成 JSON。规则（连线类型对不对、参数范围、能不能发布）仍然只在领域层。
  检验办法：界面上故意做一个不合规则的操作，看到的错误信息和命令行里的一字不差。
- **界面的组件不直接发 HTTP 请求。** 它们只调用 `PlatformClient`。检验办法：界面的单元测试用一个假的 `PlatformClient` 就能跑，不需要启动服务。
- **服务只监听 `127.0.0.1`。** 没有登录，所以不能暴露到网络上。

## 4. HTTP 接口

资源式的接口，JSON。每个接口对应一个已有的应用服务方法，没有新的业务能力。

| 请求 | 对应 | 说明 |
|---|---|---|
| `GET /api/operators` | 算子目录 | 每个算子的端口、参数定义（类型、默认值、范围、选项、说明） |
| `GET /api/recipes` | 列出方案 | |
| `POST /api/recipes` | 新建方案 | |
| `GET /api/recipes/{id}` | 取草稿 | 节点、连线、参数、模板 |
| `POST /api/recipes/{id}/nodes` | 加节点 | |
| `DELETE /api/recipes/{id}/nodes/{node}` | 删节点 | |
| `POST /api/recipes/{id}/edges`、`DELETE …` | 连线、删线 | |
| `PUT /api/recipes/{id}/nodes/{node}/params/{name}` | 改参数 | |
| `PUT /api/recipes/{id}/nodes/{node}/roi`、`DELETE …` | 设置、清除 ROI | |
| `POST /api/recipes/{id}/publish` | 发布 | |
| `POST /api/images` | 上传一幅图像 | 返回图像 ID（内容的哈希）。同一幅图像再传一次，ID 相同 |
| `POST /api/recipes/{id}/debug-runs` | 调试运行 | 请求体：图像 ID。返回：判定、每个节点的状态和耗时、每个输出的摘要和统计 |
| `GET /api/debug-runs/{run}/outputs/{node}/{port}` | 取一个输出的图像 | PNG。区域类型的输出画成黑白图 |
| `GET /api/health` | 服务是否活着、版本 | |

**出错的格式统一**：HTTP 状态码 + `{"code": "authoring.type_mismatch", "message": "…"}`。`code` 和 `message` 就是应用服务返回的那两个，不改写。
规则不允许 → 422；找不到 → 404；请求本身看不懂 → 400；服务内部出错 → 500。

**调试运行的结果怎么存**：放在服务的内存里，只留最近的几次（比如 8 次）。它们只是给界面看的临时东西，不是领域里的概念，不进仓储。

查过了：表里每一个操作，方案编排的应用服务都已经有对应的方法（包括删节点、删连线、清除 ROI），不需要补新的业务能力。

## 5. 界面

一个页面，四块：

```
┌──────────┬───────────────────────────────┬──────────────┐
│ 算子面板  │  画布（节点 + 连线）           │ 参数面板      │
│ 按分类列出 │                               │ 选中节点的参数 │
│ 拖到画布上 │                               │ 和 ROI        │
├──────────┴───────────────────────────────┤              │
│ 预览：选中节点的输出图像；判定、判定依据、耗时   │              │
└──────────────────────────────────────────┴──────────────┘
```

- 参数面板**按算子签名自动生成**：数字 → 数字输入框（带范围），选项 → 下拉框，布尔 → 开关，模板 / 模型 → 下拉框（列出方案里的模板 / 模型仓库里的模型）。
  新增一个算子，界面不用改一行——这一条要专门验证（§7）。
- 连线时，类型对不上的端口不能连（界面上先拦一道，为了体验）；**真正的检查仍然在服务端**，界面那一道只是提示。
- 改了参数之后自动重新运行（停止输入 200 毫秒后），预览跟着变。
- 画布的布局不保存：打开方案时按连线关系从左到右自动排。

技术选择沿用已经定的 ADR-07：Vue 3 + TypeScript + Vite，画布用 Vue Flow，控件用 Naive UI。Konva 这次用不到（不画 ROI）。

## 6. 推送：这次不引入 WebSocket（Q-06）

架构文档里写的是“HTTP + WS”，Q-06 问的是 WebSocket 库选哪个、或者改用 SSE。我的建议：

**POC-2 只用普通的 HTTP 请求，一个推送通道都不要。** 调试运行一次只有几毫秒到几十毫秒，请求发出去、结果直接回来，没有什么需要“推”的。

**以后需要推送时（工位的实时检测结果、训练进度），用 SSE，不用 WebSocket。** 原因：

| | SSE | WebSocket |
|---|---|---|
| 我们的需要 | 只有“服务 → 界面”一个方向，够用 | 双向，用不上 |
| 新的依赖 | 没有：就是一个不结束的 HTTP 响应，现在的 HTTP 库就能做 | 要再引入一个库，在 Windows、Linux 上各编译一遍 |
| 浏览器一侧 | 自带 `EventSource`，断了自动重连 | 重连要自己写 |
| 鸿蒙 | 那边走的是 ArkWeb 的桥，两种都用不上 | 同左 |

这等于修订 ADR-09（“HTTP + WS”→“HTTP，需要推送时用 SSE”）并关闭 Q-06。**需要你同意**（§9）。

## 7. 通过标准

| # | 标准 | 怎么验证 |
|---|---|---|
| 1 | 浏览器里从空白搭出“灰度 → 阈值 → Blob → 判定”，上传图像，运行，得到判定 | 自动的浏览器测试 |
| 2 | 点任意一个节点，能看到它输出的图像 / 区域 / 数字 | 同上 |
| 3 | 改一个参数，到预览更新完，**不超过 300 毫秒**（640×480 的图像，本机） | 浏览器测试里计时；另外报告 500 万像素图像的数字 |
| 4 | 不合规则的操作（类型不对的连线、超出范围的参数、缺判定就发布）被拒绝，界面显示的原因和命令行里的相同 | API 测试 + 浏览器测试 |
| 5 | 界面上搭的方案，命令行能打开、运行，结果相同；反过来也一样 | 测试里两边各做一次 |
| 6 | 界面的代码里，只有 `HttpPlatformClient` 一个文件发 HTTP 请求 | 一条自动检查（搜索 `fetch(`） |
| 7 | 新增一个算子（只加一个 `.cpp`），界面里出现它、能用，界面代码零改动 | 用测试里注册的一个临时算子 |
| 8 | 服务在同时收到多个请求时不出错 | 并发测试，在 ThreadSanitizer 下跑 |
| 9 | Windows 和 Linux 上都能编译、测试通过 | 自动构建 |

**训练出来的模型也能在界面里用**（`vision.anomaly_detect` 节点，看异常图）——这不是通过标准，但做完之后顺手验证一下，演示效果最好的就是这个。

## 8. 分几步、带来什么新东西

三步，每步一个 PR，CI 绿了我自己合并（按你之前说的），做到能演示时通知你：

| 步 | 内容 | 做完能看到什么 |
|---|---|---|
| ① | `vision-runtime` 和 HTTP 接口（纯 C++）。把组装根里共用的部分搬到 `apps/common/` | 用 curl 能完成整个流程；API 测试 |
| ② | 界面的骨架：`PlatformClient`、算子面板、打开已有方案并显示在画布上、调试运行并看中间结果 | 浏览器里打开命令行搭的方案，运行，看每一步的图像 |
| ③ | 编辑：拖节点、连线、改参数、发布；浏览器端到端测试；测量；结论报告 | 完整的通过标准 |

**新的依赖和工具**——这是这个 POC 最大的代价，先说清楚：

| 新东西 | 用途 | 代价 |
|---|---|---|
| **cpp-httplib**（C++，只有一个头文件） | HTTP 服务 | Linux 用 apt、Windows 用 vcpkg 安装，和现有依赖的装法一样 |
| **Node.js**（≥ 20）和 npm | 编译界面 | **开发机上要多装一样东西。** 只改 C++ 时不需要它：界面编译好的文件不进仓库，但服务没有界面也能启动（只是打开是空的） |
| Vue 3、Vue Flow、Naive UI、Vite、TypeScript | 界面 | npm 自动下载。国内下载慢的话换镜像源，文档里会写 |
| Playwright（浏览器自动化） | 端到端测试 | 自动构建里多几分钟。只在 Linux 上跑 |

**对妹妹的学习来说**：这一步会引入一门新语言（TypeScript）和一个前端框架（Vue）。她现在学的是 C++，这部分可以先不看，把界面当成一个“已经有的东西”来用；等想学前端时再回来读。第 ① 步是纯 C++，值得读——它是“同一批应用服务，换一种方式暴露出去”的一个很干净的例子。

## 10. 风险

| 风险 | 应对 |
|---|---|
| 图像编码成 PNG 太慢，500 万像素的图像超过 300 毫秒 | 先测。超了的话预览用缩小的图或 JPEG，原图另外按需取 |
| 界面一侧的工作量比估计的大（画布交互的细节很多） | 范围已经砍到最小；第 ② 步结束就有一个“只读但能运行”的版本可以演示 |
| HTTP 接口定下来之后，鸿蒙的桥做不到同样的事（比如传二进制图像） | `PlatformClient` 里取图像的方法返回的是“可以放进 `<img>` 的地址”，不是字节——桥做不了二进制时可以换成别的地址形式。真正的验证要等 POC-3b |
| 应用服务不是为“同时被多个请求调用”设计的 | 查过了：检测执行有锁；**方案编排的应用服务没有锁**（命令行一次只做一件事，不需要）。第 ① 步给它加上，并在 ThreadSanitizer 下测 |
