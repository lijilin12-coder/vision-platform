## 2. 做了什么

| 部分 | 位置 | 内容 |
|---|---|---|
| 服务 | `apps/runtime/` | `vision-runtime`：第二个驱动适配器。16 个接口：算子、方案的增删改、发布、上传图像、调试运行、取中间结果图 |
| 共用的组装 | `apps/common/platform.h` | 从命令行的代码里搬出来。两个程序用同一份 |
| 方案编排的应用服务 | 加了锁 | 原来没有：命令行一次只做一件事。服务要同时处理几个请求 |
| 图像 | `adapters/imaging` | 内存里的解码和 PNG 编码（图像不一定来自文件） |
| 依赖 | cpp-httplib | Linux 用 apt，Windows 用 vcpkg，和其他依赖的装法一样 |

**接口层里没有业务规则。** 它一共做三件事：把请求里的 JSON 取出来、调用一个应用服务的方法、把结果写成 JSON。
新增这 16 个接口，领域层没有改；应用层只改了一处（加锁）。

## 3. 实测数据

4 线程 CPU，发布版编译。一个来回 = 改一个参数 + 调试运行整个方案（5 个节点）+ 取回一幅区域图（PNG），都经过 HTTP：

| 图像 | 一个来回 | 其中调试运行本身 |
|---|---|---|
| 640×480 | 7.4 毫秒 | 约 5 毫秒 |
| 2592×1944（500 万像素） | 68.9 毫秒 | — |

（调试版编译：16 毫秒和 167 毫秒。）离 300 毫秒的要求很远，所以方案里准备的后手（预览用缩小的图、改用 JPEG）现在不需要。

PNG 编码用的是压缩级别 1：比默认的快，文件稍大。这是给界面预览的，快更要紧。

## 4. 过程中遇到的三件事

1. **算子目录在服务里是空的。** 算子靠全局对象的构造函数注册自己，放在一个 OBJECT 库里；这种库的目标文件只进入**直接**链接它的目标。
   服务多了一层静态库（接口层），算子就没被链接进最终的程序——编译、链接都不报错，只是运行时一个算子都没有。
   现在每个可执行程序都直接链接一次算子库，CMake 里写了说明。**这类问题只有真的跑起来才看得到**：是第一次 curl 就发现的。
2. **上传一幅很小的图像，得到“请求体太大”。** `curl --data-binary` 不写 `Content-Type` 时默认按表单发送，HTTP 库对表单另有一个 8 KB 的上限。
   出错信息里现在会提醒这一点，接口文档里也写了。
3. **ThreadSanitizer 的报告全在第三方库里**（OpenCV 内部用的线程库没有用 ThreadSanitizer 编译，它看不懂里面的同步）。
   这次把它们整理成了一个抑制文件 `tests/support/tsan.supp`，之后“我们的代码有没有问题”可以一眼看出来，不用再人工一条条分辨。

## 5. 实现时做的决定（请确认）

| 决定 | 原因 | 代价 |
|---|---|---|
| 改方案的操作成功后，回复改完之后的整个方案 | 界面不用再问一次；方案很小 | 方案有几百个节点时回复会大。到那时再改成只回复变化的部分 |
| “找不到”一律 404（按错误码里有没有 `not_found` 判断），其余的拒绝一律 422 | 简单、一致 | 加节点时算子 ID 不存在也是 404，严格说它不是“地址找不到”。靠错误码区分 |
| 调试运行的输出放在服务的内存里，只留最近 8 次 | 它们是给界面看的临时东西，不是领域里的概念 | 更早的中间结果图取不到了（会明确地回复“请重新运行”）。服务重启后也没有了 |
| 上传的图像存进内容仓库，用内容的哈希作 ID | 同一幅图像只存一份；和模板、样本、模型是同一套机制 | 上传过的图像不会自动清理 |
| 方案编排的应用服务整个加一把锁（可重入） | 最简单；编辑方案不是需要并行的事 | 两个人同时编辑两个不同的方案也要排队。现在没有这个场景 |
| 只监听本机，没有登录 | 用户与权限管理在范围外 | 不能直接给别的机器用 |

### 8.1 通过标准

方案 §7 的九条，现在全部有了结论。前五条由自动的浏览器测试检查（`web/e2e/editor.e2e.mjs`：真的浏览器 + 真的后端 + 中文数据目录）：

| # | 标准 | 结果 |

| 2 | 点任意一个节点，看到它输出的图像 | ✅ |
| 3 | 改一个参数到预览更新，不超过 300 毫秒 | ✅ **约 130 毫秒**（640×480）。这不包括界面故意等的 200 毫秒——等人停止输入再运行，免得每敲一个数字跑一次 |
| 4 | 不合规则的操作被拒绝，显示后端给的原因 | ✅ 超出范围的参数：红色提示里就是后端领域层的那句话 |

| 8 | 同时多个请求不出错 | ✅ 第 ① 步 |
| 9 | Windows 和 Linux | 后端 ✅；界面的编译和测试在 Linux 的自动构建里跑。**没有人在 Windows 的浏览器里亲手试过** |

### 8.2 做了什么

| 部分 | 位置 |
|---|---|
| 界面使用后端的唯一入口 | `web/src/platform/PlatformClient.ts`（接口）、`HttpPlatformClient.ts`（HTTP 实现） |
| 编辑器的状态和操作 | `web/src/editor.ts`：不依赖浏览器，对着假的后端有 11 个单元测试 |
| 看得见的部分 | `web/src/components/`：算子面板、画布（Vue Flow）、节点、参数面板、预览 |
| 后端新增 | 服务同时提供界面的文件；`GET /api/models`、`GET /api/images/{id}` |

界面一共做了这些事：新建和打开方案；点或者拖算子到画布上；拖线连接（类型对不上的放不下去）；双击连线删除；
按算子的定义自动生成参数输入框（数字、布尔、选项、模型、模板）；填数字设置 ROI；选图像后自动运行，改任何东西后自动重新运行；
点节点看它的输出图像；在图像上叠加缺陷的框和定位的十字；判定、判定依据、缺陷、测量值、位姿的列表；发布。

### 8.3 三条原则落到了哪里

1. **规则在后端。** 每个编辑操作都是“请后端改 → 用后端回复的最新方案替换本地的”。界面里没有“这条线能不能连”的判断——
   拖线时类型不对放不下去只是提示；真的发出去被拒绝时，本地的方案原封不动。
2. **界面不认识具体的算子。** 见上表第 7 条。
3. **界面不知道后端是通过 HTTP 访问的。** 组装只在 `main.ts` 里一行。单元测试用的就是另一个实现（假的后端）——这本身证明了换实现是可行的。

### 8.4 和原来计划的出入（请确认）

| 出入 | 原因 |
|---|---|
| **没有用 Naive UI**（ADR-07 里列了它） | 现在的控件只有按钮、输入框、下拉框，用浏览器自带的就够；少一个依赖，编译出来的文件 260 KB。页面多起来、需要表格和对话框时再引入 |
| **没有用 Konva**（ADR-07） | 它是用来在图像上画 ROI 的，这一步没有做。缺陷的框是用 SVG 叠在图像上的 |
| 节点在画布上的位置存在浏览器里，不属于方案 | 位置是“怎么看”，不是“方案是什么”；后端的方案里本来就没有画布布局。代价：换一台电脑打开会重新自动排 |
| 浏览器测试只在 Linux 的自动构建里跑 | Windows 的构建已经很慢了 |

### 8.5 没有做的

- 用鼠标画 ROI、框匹配模板；撤销；改名、删除方案
- 上线包、工位、训练、模型、方案助手的页面
- 推送（SSE）；多人同时编辑
- 鸿蒙上的 `BridgeClient`

## 9. 之后补上的：画 ROI 和工位页面（2026-11-24）

§8.5 里“没有做的”补了两样。演示步骤在 [dev/web-demo.md](../dev/web-demo.md) §5、§7。

| 补了什么 | 怎么做的 |
|---|---|
| **用鼠标画 ROI** | 预览图上叠着一层 SVG，它的坐标系就是图像的像素。拖出来的矩形直接是图像坐标，松开鼠标时交给后端（和填数字走的是同一个接口） |
| **工位页面** | 新建工位、绑定图像目录、部署和回滚、开始和停止；最近一帧图像（带缺陷框）、每次检测的记录、热切换发生在哪一次 |
| 发布之后**做成上线包** | 编辑页发布成功的提示上多一个按钮 |

后端为此加了上线包和工位的接口，以及一个部件 `StationRunner`（让工位持续运行：每个工位一个线程取图、检测）。
`vision-line serve` 原来自己有一份这样的循环，现在改成用同一个部件——命令行和界面背后是同一段代码。

界面知道工位有新的检测，靠的是**隔半秒问一次**（只取上次之后新出现的记录），不是后端推送。
方案里说过“需要推送时用 SSE”；现在半秒一次的询问足够，而且简单。工位很多、或者要更实时的时候再换。

浏览器测试相应加了两段：画一个只框住一个亮斑的 ROI（缺陷从 3 处变成 1 处）；
发布两个版本 → 各做成上线包 → 工位运行中从严格的换到宽松的（同一幅图像从 NG 变成 OK，记录里标出切换）→ 回滚。

**没有做的**：框匹配模板；检测记录的保存（服务只在内存里留最近 100 条）；工位的暂停 / 继续；图像目录的点选。
