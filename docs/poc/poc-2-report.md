## 2. 做了什么

| 部分 | 位置 | 内容 |
|---|---|---|
| 服务 | `apps/runtime/` | `vision-runtime`：第二个驱动适配器。16 个接口：算子、方案的增删改、发布、上传图像、调试运行、取中间结果图 |
| 共用的组装 | `apps/common/platform.h` | 从命令行的代码里搬出来。两个程序用同一份 |
| 方案编排的应用服务 | 加了锁 | 原来没有：命令行一次只做一件事。服务要同时处理几个请求 |
| 图像 | `adapters/imaging` | 内存里的解码和 PNG 编码（图像不一定来自文件） |
| 依赖 | cpp-httplib | Linux 用 apt，Windows 用 vcpkg，和其他依赖的装法一样 |

**接口层里没有业务规则。** 它一共做三件事：把请求里的 JSON 取出来、调用一个应用服务的方法、把结果写成 JSON。
新增这 16 个接口，领域层没有改；应用层只改了一处（加锁）。

## 3. 实测数据

4 线程 CPU，发布版编译。一个来回 = 改一个参数 + 调试运行整个方案（5 个节点）+ 取回一幅区域图（PNG），都经过 HTTP：

| 图像 | 一个来回 | 其中调试运行本身 |
|---|---|---|
| 640×480 | 7.4 毫秒 | 约 5 毫秒 |
| 2592×1944（500 万像素） | 68.9 毫秒 | — |

（调试版编译：16 毫秒和 167 毫秒。）离 300 毫秒的要求很远，所以方案里准备的后手（预览用缩小的图、改用 JPEG）现在不需要。

PNG 编码用的是压缩级别 1：比默认的快，文件稍大。这是给界面预览的，快更要紧。

## 4. 过程中遇到的三件事

1. **算子目录在服务里是空的。** 算子靠全局对象的构造函数注册自己，放在一个 OBJECT 库里；这种库的目标文件只进入**直接**链接它的目标。
   服务多了一层静态库（接口层），算子就没被链接进最终的程序——编译、链接都不报错，只是运行时一个算子都没有。
   现在每个可执行程序都直接链接一次算子库，CMake 里写了说明。**这类问题只有真的跑起来才看得到**：是第一次 curl 就发现的。
2. **上传一幅很小的图像，得到“请求体太大”。** `curl --data-binary` 不写 `Content-Type` 时默认按表单发送，HTTP 库对表单另有一个 8 KB 的上限。
   出错信息里现在会提醒这一点，接口文档里也写了。
3. **ThreadSanitizer 的报告全在第三方库里**（OpenCV 内部用的线程库没有用 ThreadSanitizer 编译，它看不懂里面的同步）。
   这次把它们整理成了一个抑制文件 `tests/support/tsan.supp`，之后“我们的代码有没有问题”可以一眼看出来，不用再人工一条条分辨。

## 5. 实现时做的决定（请确认）

| 决定 | 原因 | 代价 |
|---|---|---|
| 改方案的操作成功后，回复改完之后的整个方案 | 界面不用再问一次；方案很小 | 方案有几百个节点时回复会大。到那时再改成只回复变化的部分 |
| “找不到”一律 404（按错误码里有没有 `not_found` 判断），其余的拒绝一律 422 | 简单、一致 | 加节点时算子 ID 不存在也是 404，严格说它不是“地址找不到”。靠错误码区分 |
| 调试运行的输出放在服务的内存里，只留最近 8 次 | 它们是给界面看的临时东西，不是领域里的概念 | 更早的中间结果图取不到了（会明确地回复“请重新运行”）。服务重启后也没有了 |
| 上传的图像存进内容仓库，用内容的哈希作 ID | 同一幅图像只存一份；和模板、样本、模型是同一套机制 | 上传过的图像不会自动清理 |
| 方案编排的应用服务整个加一把锁（可重入） | 最简单；编辑方案不是需要并行的事 | 两个人同时编辑两个不同的方案也要排队。现在没有这个场景 |
| 只监听本机，没有登录 | 用户与权限管理在范围外 | 不能直接给别的机器用 |

## 6. 没有做的

- 界面（推迟）
- 上线包、工位、训练、模型、方案助手的接口——后面每做一件后端的事，顺手把它的接口加上
- 框模板的接口（需要“从某幅图像上框一块”的参数，等结果项和图像源定了一起做）
- 推送（SSE）：现在没有需要推的东西
- 服务作为系统服务安装、开机自启
