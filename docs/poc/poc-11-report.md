# POC-11 结论报告：方案助手的最小闭环（不用大模型）

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-20 |
| 验证平台 | Linux（Ubuntu 24.04，GCC 13.3，OpenCV 4.6）；Intel Xeon 2.3 GHz，4 核。Windows（MSVC）由自动构建验证。**macOS 上没有测过** |
| 验证的假设 | A11：“我们的循环驱动、顾问只提议”的方案助手走得通 |
| 结论 | **✅ 闭环和各项防护成立；“自动找到好参数”这一半还没有验证**（见 §5）|

## 1. 通过标准

| 标准（[04-poc-plan](../04-poc-plan.md) §4） | 结果 | 证据 |
|---|---|---|
| 领域层单元测试覆盖 A1～A10，且不链接 OpenCV、不访问网络 | ✅ | `assistant_domain_tests` 27 个测试，只链接 `assistant_domain`。A1 没有对应的测试，因为它不是靠检查保证的：聚合和端口里根本没有“发布”这个操作（集成测试另外核对了整个过程中没有出现“方案版本已发布”事件） |

测试汇总：全部 155 个测试通过（含教程示例）。本次新增 45 个：助手领域 27、基准图集和评估规则 6、助手集成 11、边界 1。新代码另外在 AddressSanitizer + UBSan 下跑了一遍，没有报告。

## 2. 做了什么

| 部分 | 内容 |
|---|---|
| BC-4 上线管理 | `GoldenSet` 聚合（冻结后不可改）、验收标准、**评估规则**（漏检、误报、出错的统计；是否达标；两次评估哪个更好）。这套规则只有这一份，以后验收检查和对比评估也用它 |
| BC-11 方案助手：领域层 | `Workflow`（节点、连线、可调项及范围、稳健性检查的设定）；`AssistSession` 聚合（A1～A10）；`RecipeAdvisor` 方案顾问接口；盲测集的分层抽取；助手报告的生成规则 |
| BC-11 方案助手：应用层 | `AssistService`：驱动“提议 → 检查 → 应用 → 试运行 → 评估 → 保留或回退”的循环，结束后做盲测、稳健性检查、出报告；采纳、放弃 |
| 适配器 | 按脚本出牌的顾问；把助手的端口接到方案编排、检测执行、上线管理上；工作流、会话、基准图集的 JSON 文件存储；图像扰动（亮度、噪声） |
| 命令行 | `workflow import/list`、`golden sample/list/show`、`assist run/show/list/adopt/abandon` |
| 示例 | `samples/workflows/bright-spot.json`、`samples/assistant/bright-spot.script.json` |

代码量：产品代码约 2,900 行，测试约 1,050 行。

### 结构

```
方案顾问（领域层的接口）          ← 脚本顾问（现在）、大模型顾问（POC-12）都只是它的实现
        ▲ 每轮问一次，只拿回一份提议（数据）
AssistService（循环在这里）──► AssistSession（规则在这里：A1～A10）
        │
        ├─ CandidateEditor ──► 方案编排的编辑命令（没有发布）
        ├─ TrialRunner     ──► 检测引擎（调试运行）
        └─ GoldenCases     ──► 上线管理（基准图集、评估规则）
```

助手的领域层和应用层**不依赖任何其他上下文**：三个端口由组装根接上。所以助手能做什么，看端口就知道——端口里没有发布，助手就发布不了。

## 3. 怎么试

```bash
vision-cli workflow import samples/workflows/bright-spot.json
```

```bash
vision-cli golden sample ./golden-demo
```

```bash
vision-cli assist run ./golden-demo/brief.json --script samples/assistant/bright-spot.script.json
```

`golden sample` 生成 24 张图（16 张调参用，8 张盲测用）和一份任务书。默认盲测集的光照更暗，报告会给出“不建议直接采纳”；加 `--blind-lighting same` 则两边光照一样，报告的结论是达标。

脚本里的 6 份提议和结果：

| 轮 | 提议 | 结果 |
|---|---|---|
| 1 | 阈值 = 140 | 没有改善（背景比 140 亮）→ **回退** |
| 2 | `judge.maxCount` = 5（故意越界） | **被拒绝**：不是可调项 |
| 3 | 阈值 = 300（故意越界） | **被拒绝**：超出范围 0～255 |
| 4 | 加一个节点（故意越界） | **被拒绝**：不能改变结构 |
| 5 | 阈值 = 195 | 误报 8 → 4，**保留** |
| 6 | 最小面积 = 30 | 误报 4 → 0，达标，会话结束 |

第 2 份提议值得注意：“允许最多 5 个亮斑”确实能让调参集上的误报消失，但它改的是判定标准本身。把判定用的参数排除在可调项之外，助手就不可能用“放宽标准”的办法达标。

## 4. 测量

24 个用例（640×480），16 个用于调参；6 轮，其中 3 轮有试运行。

| 项 | 调试版本 | 发布版本 |
|---|---|---|
| 一轮（应用 + 16 次试运行 + 评估 + 保存记录） | 22～25 ms | 8～12 ms |
| 被拒绝的一轮 | < 1 ms | < 1 ms |
| 整个会话（含初始评估、盲测、4 组稳健性检查、报告） | 1.05 s | 0.32 s |
| 单次试运行（平均） | 0.7～1.7 ms | 0.4～0.8 ms |
| 会话记录（一个 JSON 文件，6 轮） | 13.9 KB | 同左 |

结论：

- **循环本身的开销可以忽略**，时间几乎都花在试运行上，和“调参集的用例数 × 单次检测耗时”成正比。举例：如果单次检测要 10 ms、调参集有 200 个用例，一轮约 2 秒（这是推算，没有实测）。
- 接上大模型之后，一轮的时间会由大模型的响应时间（几秒到几十秒）决定，我们这部分不是瓶颈。
- 会话记录每轮约 1～2 KB（主要是每次评估覆盖的用例列表）。记录里只有数字和用例 ID，**没有图像**。

## 5. 没有验证的、已知的局限

1. **脚本顾问不会“找”参数。** 脚本是我看着图像的灰度值写出来的，它知道答案。所以这个 POC 证明的是：循环走得通、不合法的提议挡得住、变差了会回退、只适应调参集会被发现。它**没有**证明“自动调参能找到好参数”——这要等 POC-12（大模型顾问），或者先写一个不用大模型的搜索顾问（例如逐个可调项试几个取值）。
2. **图像是合成的。** 均匀的背景、规则的亮斑。真实图像上阈值类方案是否够用，是工作流设计的问题，这里没有回答。
3. **只有一个工作流、两个真正用到的可调项。** 可调项多了之后轮数会怎样增长，没有数据。
4. **工作流里没有 ROI。** 示例靠阈值把背景和亮斑分开；实际方案通常先限定零件区域。ROI 和图像分辨率的耦合（POC-1 报告 §6）仍然没有解决。
5. **会话中途程序退出不能续跑。** 每一轮结束都保存了记录，但没有实现“从记录恢复并继续”。
6. **数据外发策略只验证了“不外发图像”。** “缩略图”目前只是打了一个标记，真正生成缩略图要等有了会用图像的顾问。
7. macOS 上没有测过。

## 6. 实现时做的决定（请确认）

这些在设计文档里没有写明，实现时需要有一个确定的做法：

| # | 决定 | 理由 |
|---|---|---|
| 1 | 方案顾问的接口放在**领域层**；其余端口（编辑、试运行、基准图集）放在应用层 | “下一步怎么改”是领域里的一个角色，谁来担任是实现细节（按你之前说的“大模型属于领域层，具体实现可扩展”）。其余三个是和别的上下文打交道的技术接缝 |
| 2 | 被拒绝的提议**也消耗一轮预算** | 否则一个总是出错的顾问会让会话永远不结束 |
| 3 | “更好”的顺序：出错少 > 漏检少 > 误报少；**一样好不算更好**，回退 | 漏检的代价比误报大；一样好时保留原来的，避免参数无意义地漂移 |
| 4 | 稳健性检查在**调参集**上做 | 盲测集一次会话只能评估一次（A7），扰动之后再评估等于多看了几次 |
| 5 | “可能只适应了调参集”的判断：盲测集的漏检率、误报率或出错率比调参集高，**并且**盲测集没有达到验收标准 | 只是略差但仍然达标，不算问题 |
| 6 | 候选方案是一份**新的、独立的方案**；“采纳”只是把会话标记为已采纳，候选方案从此是用户的普通草稿，**发布仍然要用户自己做** | 助手从不碰用户已有的草稿，A1 最容易保证。以后做“改进我现有的方案”时再考虑合并回原草稿 |
| 7 | “放弃”之后候选方案**不删除** | 方案编排现在没有删除命令；留着也方便事后查看 |
| 8 | 时间预算只在**每一轮开始时**检查 | 不打断正在进行的试运行；所以实际用时可能超出预算至多一轮 |
| 9 | 顾问出错时会话以“出错”结束，仍然做盲测、出报告，交出当时最好的候选方案 | 已经花掉的轮次不应该白费 |
| 10 | 试运行出错（例如图像读不出来）计为这个用例 ERROR，不中止会话 | 跑不起来也是一种结果，如实计入评估 |
| 11 | 工作流里可调项的范围可以比算子允许的宽；超出算子范围时由方案编排拒绝，记为“被方案编排拒绝”并恢复原状 | 两道检查各管各的：助手管“工作流允许改什么”，方案编排管“这个值对算子合不合法” |

## 7. 对下一步的影响

- **POC-12（大模型顾问）可以开始。** 要做的只是 `RecipeAdvisor` 的一个新实现，其余代码不用改。交给顾问的内容（`AdvisorView`）已经定型：目标、工作流说明、可调项及当前值、历史（含被拒绝的原因）、每个调参用例的判定和各节点输出的文字摘要。
- 建议在 POC-12 之前或同时写一个**不用大模型的搜索顾问**（约 100 行）：一来补上 §5 第 1 条，二来给大模型顾问一个比较的基准——如果简单搜索就能达标，大模型的价值就要靠“轮数更少”或“能解释”来体现。
- 评估规则已经在 BC-4 里，验收检查（L2、L3）和对比评估可以直接用。
