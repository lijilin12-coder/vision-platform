### 1.3 规则 N1 是怎么保证的

```
样本用途：未分配 ──冻结基准图集──► 留作基准        （两种用途都不能再变）
              └──冻结数据集版本──► 用于训练
```

- 用途一旦定成一种，**不能改成另一种，也不能改回未分配**。因为冻结的基准图集和数据集版本本身不可修改，它们里面的样本用途也就永远成立
- **整体拒绝**：一批里有一个不行，整批都不改。被拒绝的基准图集不会保存；一起提交的其他图像的用途不受影响
- 用途确定之后**不能改标签**：冻结的图集和数据集版本记录的是冻结时的标签
- 提交训练任务时还会再检查一次（T-2，第 2 步）

### 1.4 实现时做的决定（请确认）

| # | 决定 | 理由 |
|---|---|---|
| 1 | 样本的 ID **就是**内容的 SHA-256，没有另外的编号 | “是不是同一个样本”变成比较 ID，不需要查表；同样内容的图像天然只有一个样本 |
| 2 | 哈希对**文件的字节**计算，不是对像素 | 简单、快。代价：同一幅画面另存成别的格式（PNG → BMP）会被当成两个样本，N1 拦不住。记入 Q-09（相似图像的隐性重叠），和“连拍的几张”是同一类问题 |
| 3 | 基准图集的每个用例在创建时**自动登记成样本**，标签取用例的真实判定 | 用户不用先导入样本再建图集；已有的命令和方案助手的示例都不用改 |
| 4 | 同一幅图像可以进**多个**基准图集，但不能在**一个**图集里出现两次 | 多个图集共用留作基准的图像是合理的；一个图集里重复只会让评估的数字失真 |
| 5 | 数据集冻结要求**每个样本都有标签** | 训练需要知道每一张是合格还是不合格 |
| 6 | 冻结数据集时先保存样本的用途，再保存版本 | 三种聚合分别保存，不是一个事务。万一中途失败，宁可样本被标成“用于训练”而没有对应的版本，也不要有一个版本里的样本还能被拿去做基准 |
| 7 | 没有接上数据上下文的程序里，基准图集和以前一样工作（不检查 N1） | 产线运行平台不需要数据上下文 |

### 1.5 没有做的

- 采集策略、短期图像缓存、从产线导入样本包（DAT-01、DAT-05）
- 检测框、分割掩码这类标注（DAT-03）；现在只有图像级的“合格 / 不合格”
- 样本和数据集的删除
- 按“零件编号 / 批次”整体划分用途（D8-10、Q-09）

全部 274 个测试通过。本步新增 16 个：数据领域层 8 个、集成 8 个（按内容识别、标签冲突、冻结、基准图集登记样本、N1 两个方向、重启之后仍然成立、没有接数据上下文时照常工作）。新代码在 AddressSanitizer + UBSan 下无报告。

### 2.3 五条不变量怎么落的

| 不变量 | 怎么保证 |
|---|---|
| T-1 只能用已冻结的数据集版本 | 提交时检查。数据上下文里“有版本号的就是冻结的”，没冻结的数据集取不到版本 |
| T-2 不能有留作基准的样本 | 提交时**再问一次**每个样本现在的用途。数据上下文的 N1 已经保证不会出现，这是第二道防线 |
| T-3 划分方式必须记录 | 比例和随机种子存在任务里；同样的样本和划分方式，在任何平台上结果相同（自己写的小伪随机数发生器，分层） |
| T-4 结束的任务不可修改 | 完成、失败、取消之后，任何命令都被拒绝；刷新时也不再去问训练后端。失败的任务不会“复活”，要重新提交 |
| T-5 模型版本必须记录来源 | 来源由任务给出；模型仓库拒绝来源不完整的“训练出来的”模型 |

### 2.4 出问题时的行为

| 情况 | 行为 |
|---|---|
| 提交不合规则（数据集没冻结、合格样本太少、划分不合法……） | **拒绝，不产生任务**，也不打扰训练后端 |
| 规则都通过，但训练后端连不上 | 任务**照样记录**，状态“已失败”，原因写明。它是一次合规的尝试，只是没能开始 |
| 查询进度时暂时连不上 | 任务状态**不变**（训练可能还在进行），下次再问 |
| 训练后端报告失败 | 任务“已失败”，带原因 |
| 训练后端报告完成但没有模型文件 | 任务“已失败”：不留下一个没有模型的“已完成” |
| 训练完成，但模型文件读不到 | 任务仍然“已完成”，没有模型版本，原因进日志 |
| 取消之后训练后端才报告完成 | 不接受，任务保持“已取消” |

### 2.5 实现时做的决定（请确认）

| # | 决定 | 理由 |
|---|---|---|
| 1 | “训练完成 → 导入模型仓库”由训练的应用服务**直接通过端口调用**，不是靠订阅领域事件 | 设计（08 §2.3）写的是领域事件触发。直接调用更简单，而且“导入失败了怎么办”好处理。事件照样发布，以后要改成订阅不难 |
| 2 | 划分由**我们的领域规则**做，训练后端拿到的是已经分好的样本 | 可重现（T-3）不依赖训练后端怎么实现 |
| 3 | 合格的样本至少 **8 个**才能提交 | 异常检测模型靠合格的样本学习“正常是什么样”。8 是个很低的门槛，只为了拦住明显的误操作 |
| 4 | 不合格的样本很少时，按比例四舍五入可能一个都分不到验证集、测试集 | 例如 4 个不合格样本、各 10%：全部进训练集。训练报告里的指标就没有意义。**这是个真实的问题**，第 3 步要处理（至少要在报告里说明） |
| 5 | 模型版本号由模型仓库自动递增（同一个模型名的下一个号） | 再训练一次就是下一个版本 |
| 6 | 训练进度只在内存里，不保存 | 它不是任务的一部分，只是最近一次查到的数字 |
| 7 | 没有配置训练服务的机器上，提交的任务以“已失败”记录 | 其余功能照常可用 |

## 3. 第 3 步：训练服务

到这一步，“数据 → 训练 → 模型进仓库”是真的了：一条命令提交，半分钟到几分钟后，模型仓库里多出一个带完整来源信息的模型版本。
模型还**不能**在检测引擎里运行——那是第 4 步。

### 3.1 通过标准

| 标准 | 结果 |
|---|---|
| 提交训练任务 → 完成 → 模型版本自动出现在模型仓库，来源信息完整 | ✅ 用合成图像；直接运行和 Docker 里运行都验证过 |
| 用 MVTec AD 的一个类别 | ⚠️ **没有验证**：这个环境下载不了数据集。提供了导入脚本 `tools/import_mvtec.py`，只在一个“目录结构和 MVTec 一样的假数据集”上跑过 |
| 训练服务不可用、训练失败时，任务状态正确，不影响其他功能 | ✅ 见 §3.4，五种情况都用真正的服务试过 |
| 记录训练耗时、镜像体积 | ✅ 见 §3.3。有无 GPU 的差别**没有测**：这个环境没有 GPU |

### 3.2 做了什么

| 部分 | 位置 | 内容 |
|---|---|---|
| 训练服务 | `services/training/`（Python + PyTorch） | `trainer.py` 训练小型卷积自编码器并导出 ONNX；`server.py` 用标准库的 `http.server` 包成 4 个接口；`Dockerfile` |
| 平台一侧的适配器 | `adapters/training_http/` | `HttpTrainingBackend`：`TrainingBackend` 端口的一个实现。领域层和应用层**一行没改** |
| HTTP 客户端 | `adapters/http/`（从大模型顾问那里搬出来） | 现在支持 GET、DELETE；发往本机的请求不走代理 |
| 命令行 | `apps/cli/` | `--training-url` / `VISION_TRAINING_URL`；`train submit ... --wait`、`train wait`；`sample generate` |
| MVTec AD 导入脚本 | `tools/import_mvtec.py` | 导入一个类别并冻结成数据集版本 |

**模型**：三层下采样、三层上采样的卷积自编码器，约 26 万字节。只用训练集里**合格的**图像训练。
导出的 ONNX 把“原图和还原图的差异”也算在里面：输入图像，直接输出异常得分和异常图。
这样第 4 步的推理算子不需要知道模型内部是什么，换一种异常检测方法也不用改算子。

**阈值**：训练服务给出一个建议值，写进训练报告和模型契约。只用训练集和验证集来定；测试集只用来最后报数。

### 3.3 实测数据

环境：4 个 CPU 线程，没有 GPU。数据：`sample generate` 生成的 640×480 合成图像——深色零件，表面有明暗渐变、随机的灰尘点、
±8% 的亮度浮动；不合格的有亮斑、深色划痕、污渍三种，各占三分之一。

| 项 | 数值 |
|---|---|
| 训练数据 | 60 幅合格 + 12 幅不合格；划分 0.8/0.1/0.1 → 训练集里合格的 48 幅 |
| 设置 | 120 轮（默认值），缩放到 256×256 |
| 训练耗时（从提交到模型进仓库） | **约 28 秒** |
| 测试集（7 幅：6 合格、1 不合格） | 全对，AUROC 1.0。**样本太少，这个数字说明不了什么** |
| 另外生成的 160 幅新图像（100 合格、60 不合格，换了随机种子） | **误报 0，漏检 0** |
| 得分的间隔 | 合格最高 0.065；划痕最低 0.094、污渍最低 0.105、亮斑最低 0.247；阈值 0.081 |
| 推理耗时（C++ ONNX Runtime，256×256，单线程，单幅） | 约 3.6 毫秒（第一幅约 8 毫秒） |

| Docker | 镜像能构建，容器里的训练服务跑通了完整流程（在换成 OpenCV 预处理之前验证的；之后只改了依赖里的一个包，**没有重新构建镜像**） |

#### 3.3.1 一个差点漏掉的问题：训练和推理的预处理不一致

为第 4 步做准备时，用 C++ 的 ONNX Runtime 跑了一下训练出的模型，发现**同一个模型、同一幅图像，得分和 Python 里不一样**：

| 图像 | Python（训练服务） | C++ | 阈值 |
|---|---|---|---|
| 一幅合格的 | 0.0054 | 0.0091 | 0.0083 |

合格的图像在 C++ 里超过了阈值——会被判成不合格。模型没有问题，问题在**送进模型之前的缩放**：
训练服务原来用 Pillow 缩小图像，它缩小时会先做平滑；C++ 里用 OpenCV 的双线性插值，不做平滑，图像上的噪声保留得多，模型还原不出来，得分就高。

这是机器学习项目里很常见的一类错误，而且**不会报错**，只是结果悄悄变差。改法：

- 训练服务改用 OpenCV 做预处理，和平台里的推理算子用**同一个库、同一种算法**（`cvtColor` → `resize(INTER_AREA)` → 除以 255）。改完之后两边的得分六位小数相同。
- 第 4 步要加一个自动的检查：训练服务报告的得分和推理算子算出的得分必须一致。

改对预处理之后，又暴露出模型打分方式的一个弱点：灰尘（合格）缩小后是一个很亮的像素，原来用“差异的平方”打分，把它放得很大，和污渍分不开了
（160 幅新图像里漏了 23 幅）。之前能分开，其实是 Pillow 的平滑顺手把灰尘抹掉了——**碰巧**。
现在打分改成“差异的绝对值在小范围里的平均”，看重成片的差异；默认的训练轮数从 40 提到 120。上表是改完之后的数字。

要老实说的几点：

1. **合成图像太简单**。缺陷和背景的差别很明显，零件位置固定。真实产品上（纹理、位置偏移、反光）效果会差很多，
   这个模型多半不够用。这一步验证的是闭环，不是算法。
2. **划痕的余量不大**（最低分只有阈值的 1.16 倍）。换一批更浅、更细的缺陷就可能漏。
3. 打分方式和训练轮数是**看着那 160 幅新图像的结果改的**，所以“误报 0、漏检 0”这个数字偏乐观：它不再是完全没见过的数据上的结果。
4. 模型把图像缩放到 256×256 再看：640 像素宽的图上，小于约 5 像素的缺陷缩小后不到 2 像素，基本看不见。
5. 合格图像的得分（0.065）主要来自零件的边缘：自编码器还原不出很锐利的边。训练轮数越多越好（300 轮时降到 0.048），但更慢。

### 3.4 出问题时的行为（都用真正的服务试过）

| 情况 | 结果 |
|---|---|
| 没有配置训练服务 | 任务记录为“已失败”，原因“这台机器没有配置训练服务”；命令退出码 1 |
| 配置了但服务没启动 | 任务记录为“已失败”，原因里有 curl 的出错信息 |
| 设置不对（例如 `imageSize` 不是 8 的倍数） | 训练服务报告失败，原因原样显示：“imageSize 必须是 8 的倍数，并且不小于 32” |
| 训练中取消 | 任务变成“已取消”；训练服务在下一轮开始前停下，服务本身继续可用 |
| 训练中训练服务被杀掉 | 查询时“连不上”——任务**保持“运行中”**（暂时查不到不等于失败）。服务重启后再查：它不认识这次训练了，任务变成“已失败”，原因“训练服务不认识这次训练（它可能重启过）” |

### 3.5 实现时做的决定（请确认）

| 决定 | 原因 | 代价 |
|---|---|---|
| 图像和模型以**文件路径**交接，不通过 HTTP 传内容 | 图像可能很多、很大 | 平台和训练服务必须看得到同一份文件。Docker 要把数据目录挂载到**相同的路径**；训练服务放到另一台机器上就不行了（那时要换成上传下载，只需要改适配器和服务） |
| 训练服务用标准库的 `http.server`，不用 Web 框架 | 内部服务，只有平台一个调用者，四个接口 | 没有登录、没有权限：默认只监听本机 |
| 任务状态只放在训练服务的内存里 | 简单 | 服务重启，正在跑的训练就丢了（平台能正确识别，见上表） |
| 划分在平台里做，训练服务只照着用 | 划分方式属于训练任务（T-3），要能重现 | — |
| **某一类样本很少时，测试集、验证集各至少留一个**（改了第 2 步的划分规则） | 原来按比例四舍五入，4 个不合格的样本 ×10% = 0，测试集里一个不合格的都没有，指标算不出来 | 很小的数据集上，实际比例会偏离设定的比例 |
| 训练服务用 OpenCV 做预处理（多一个 Python 依赖） | 必须和推理算子完全一致，见 §3.3.1 | 以后在鸿蒙上换推理引擎时，预处理仍然由我们自己的 C++ 代码做，不受影响 |
| 训练集里不合格的图像不参与训练，但用来帮忙定阈值 | 自编码器只学合格的；不合格的图像白放着可惜 | — |
| 等待训练完成是命令行每秒查询一次 | 没有做“训练完成时主动通知” | 界面做出来之后要换成事件 |

### 3.6 没有做的

- 模型在检测引擎里运行（第 4 步）
- 在真实数据（MVTec AD）上训练；GPU 上训练
- 更强的异常检测方法（需要预训练权重）
- 训练服务在另一台机器上；多个任务同时训练；训练过程的曲线和日志回传
- Windows 上运行训练服务（Python 代码没有平台相关的部分，但**没有试过**）

## 4. 第 4 步：模型在检测引擎里运行

闭环合上了：训练出来的模型，作为一个算子放进方案，随上线包部署到工位，在工位上判定合格与否。
一步一步的演示见 [dev/training-demo.md](../dev/training-demo.md)。

### 4.1 通过标准

| 标准 | 结果 |
|---|---|
| 训练出的模型能在检测引擎里作为算子运行 | ✅ `vision.anomaly_detect`；调试运行、正式检测、工位运行都验证过 |
| 推理的结果和训练服务一致 | ✅ 同一幅图像的得分六位小数相同；有一个自动的测试守着（§4.4） |
| 模型“经过转换” | ⚠️ **没有做**。Windows / Linux 上直接运行 ONNX，不需要转换；转换成 MindSpore Lite 是鸿蒙上的事（POC-10、POC-4） |
| 在产线运行平台上运行 | ⚠️ 现在两个平台还在同一个程序里。验证的是“经过上线包、在工位上运行”，不是“在另一台机器上运行” |

### 4.2 做了什么

| 部分 | 位置 | 内容 |
|---|---|---|
| 共享内核 | `core/kernel/include/vision/kernel/model.h` | `InferenceModel` 接口、`Tensor`、`ModelInfo`；参数类型 `Model` |
| 检测执行（BC-3） | `ModelSource` 端口 | 编译执行计划时按模型版本 ID 取出加载好的模型；之后每次检测直接运行 |
| 推理引擎 | `adapters/inference_onnx/` | `OnnxModelSource`：ONNX Runtime 只出现在这一个库里 |
| 算子 | `operators/src/anomaly_detect.cpp` | 预处理 → 模型 → 异常倍数、得分、异常图 |
| 方案编排（BC-2） | 规则 P3 | 需要模型的节点没有选模型，方案不能发布 |
| 上线管理（BC-4） | `LoadCheck` 端口 | 创建上线包前让检测引擎真的加载一次；加载不了（例如模型未发布）就拒绝 |
| 构建 | `cmake/OnnxRuntime.cmake` | 自动下载 ONNX Runtime 的预编译库；`-DVISION_WITH_ONNXRUNTIME=OFF` 可以关掉 |
| 命令行 | `model import` | 手工导入在别处训练好的模型 |

**依赖方向**是这一步最要紧的设计：

```
算子（anomaly_detect） ──► InferenceModel 接口（共享内核）◄── OnnxModelSource（适配器）──► ONNX Runtime
```

算子不知道推理引擎是谁，也不知道模型文件在哪里。到了鸿蒙上，只需要再写一个 `MindSporeModelSource`，算子和方案都不用动。

### 4.3 ONNX Runtime 是怎么引入的

这是平台第一个“不是从包管理器装”的依赖，开始之前担心的是：三个平台上各装各的、自动构建变慢。实际情况：

| 项 | 情况 |
|---|---|
| 来源 | 微软官方的预编译库，从 nuget.org 下载（Microsoft.ML.OnnxRuntime 1.22.0）。这个包是一个 zip，**同时含有头文件和 Windows、macOS、Linux 的库**，所以三个平台用同一个地址、同一个校验值（SHA-256 写在 CMake 脚本里） |
| 为什么不用 GitHub 上的发布包 | 当前环境下载不了；另外国内访问 GitHub 也常常很慢 |
| 为什么不用 vcpkg / Homebrew / apt | vcpkg 要从源码编译（一个多小时）；apt 里的版本很旧；三个平台三种装法 |
| 大小 | 下载约 120 MB（含所有平台）；Linux 上实际用到的库 21 MB |
| 配置耗时 | Linux 上第一次配置多 8 秒左右（下载 + 解压）；之后没有额外开销 |
| 运行时 | Linux、macOS：程序里记了库的位置（rpath），直接能运行。Windows：构建时把 `onnxruntime.dll` 复制到每个用到它的程序旁边 |
| **没有验证的** | ARM 的 Linux。Windows 已由自动构建验证（导入模型 → 检测 → 工位，中文数据目录）。macOS 的分支写了但没有试过——2026-11-24 起不再考虑 macOS |

### 4.4 训练和推理的一致性

第 3 步里发现过预处理不一致的问题（§3.3.1）。现在的保证有三层：

1. 两边用同一个库的同一种算法：`resize(INTER_AREA)`，然后除以 255。两处代码的注释互相指着对方。
2. 自动测试 `OnnxInference.ScoresMatchTheTrainingService`：仓库里放了一个训练出来的模型（`tests/data/surface-anomaly.onnx`，26 万字节）
   和两幅“画法固定”的图像在 Python 里算出的得分；C++ 一侧算出的必须相同（误差不超过 0.00002）。
   谁改了算子里的预处理，这个测试就会失败。
3. 算子的单元测试里有一条专门检查“缩小时是取平均”（棋盘格缩小一半必须得到 0.5）。

实测：演示流程里同一幅图像，训练服务报 0.058151，算子报 0.058151。

**还有一个没有堵上的口子**：彩色图像转灰度。训练服务读彩色图像时用 OpenCV 的 `cvtColor`，平台里是“灰度”算子，也是 `cvtColor`，
理论上一样；但如果有人在“灰度”和“异常检测”之间加了别的预处理（比如模糊），模型看到的就和训练时不一样了。
现在没有任何机制阻止这样做——只在文档里写了。合成图像本来就是灰度的，这条路**没有被测到**。

### 4.6 规则

| 规则 | 在哪里检查 | 测试 |
|---|---|---|

### 4.7 实现时做的决定（请确认）

| 决定 | 原因 | 代价 / 和设计的出入 |
|---|---|---|
| **方案直接写死模型版本**（`surface-anomaly@v1`） | 最简单；方案版本一冻结，用哪个模型也就定死了，可追溯 | ⚠️ **和 H-08 的决定不一样**。H-08 说的是“方案声明模型依赖（模型 + 兼容范围），上线包锁定具体版本”，这样换一个兼容的新模型不用改方案。现在换模型必须改方案、重新发布。要做成 H-08 那样，需要模型契约的主版本号、上线包里的锁定表——留到确实需要“只换模型”的时候再做 |
| 算子输出“异常倍数”（得分 ÷ 模型建议的阈值），判定写“不超过 1” | 重新训练后阈值会变；这样方案里不用抄一个会过期的数字 | 想比模型建议的更严或更松，改判定的最大值（例如 0.9） |
| 未发布的模型可以调试，不能正式使用 | 刚训练出来的模型要先试，才知道该不该发布 | “发布”现在只是一个人工确认的动作，没有自动的验证（那是 BC-8 模型工具链的事） |
| 算子不支持 ROI | 模型是用整幅图像训练的 | 想只看一部分，要用裁好的图像训练——现在没有这个流程 |
| ONNX Runtime 每次推理只用一个线程 | 线程由检测引擎安排；几条检测流程同时跑时，推理引擎各开一堆线程反而慢 | 只有一条流程时没有用上多核 |
| 模型从内存里的字节加载，不传文件路径 | Windows 上路径是宽字符，带中文容易出错；顺便核对哈希 | 模型文件要整个读进内存（现在 26 万字节，无所谓；几百兆的模型要再考虑） |
| 推理功能可以在编译时关掉 | 下载不了预编译库的机器上，其余功能照常可用 | 多一个编译选项要维护 |

### 4.8 没有做的

- 模型依赖的“声明 + 锁定”（H-08、L2）；模型契约的主版本号和兼容范围
- 量化、转换成 MindSpore Lite、不同推理引擎之间结果一致性的验证（BC-8，POC-10、POC-4）
- GPU / NPU 推理；批量推理
- 方案助手还不会用这个算子（工作流里没有“模型”这种槽位）
- 上线包不含模型文件本身：工位和模型仓库在同一个数据目录里才行。两个平台分开之后，上线包要把模型文件带上
- 在真实数据上的效果；Windows 上手工走一遍演示（含训练服务）

## 5. 总的结论

假设 A13（“从方案构建平台发起训练，训练出的模型能自动接回，并在产线运行平台上运行；规则 N1 能拦住基准和训练数据的重叠”）：**在合成数据上成立**。

- 架构上的收获：训练后端、推理引擎都是端口后面的适配器，领域层没有因为它们改过一行。第 3 步接上真的训练服务时，训练上下文的领域层和应用层没有动；
  第 4 步引入 ONNX Runtime，它只出现在一个适配器库里。
- 过程中最有价值的一个发现不是设计上的，而是 §3.3.1 那个预处理不一致的问题：它不报错，只让结果悄悄变差，是靠“在另一侧再算一遍”才发现的。
- 最大的未知仍然是**真实数据**。合成图像上的“全部判对”不能说明这个小模型在真实产品上够用；下一步最值得做的是找一批真实图像（MVTec AD 的一个类别，或者自己拍）走一遍。

## 6. 在真实数据上：MVTec AD（2026-11-24）

§5 说“最大的未知是真实数据”。数据集拿到之后跑了三个类别：瓶子（bottle，物体）、皮革（leather，纹理）、螺丝（screw，位置和角度不固定的小物体）。
图像是 900×900 或 1024×1024，bottle 和 leather 是彩色的。

### 6.1 流程

用 `tools/import_mvtec.py` 导入并冻结数据集，`train submit ... --image-size 256 --wait` 训练，都是默认设置（120 轮）。

- **导入脚本、训练、模型入库：都一次通过。** 这是导入脚本第一次在真数据上运行
- 每个类别训练约 2 分钟（4 线程 CPU，没有 GPU；训练集 180～290 幅）
- **彩色图像这条路是对的**：bottle 的三幅图像，C++ 算子和训练服务算出的得分六位小数相同（§4.4 里说这条路“没有被测到”，现在测到了）

### 6.2 效果

平台自己重新划分了数据（0.8 / 0.1 / 0.1），所以**下面的数字不能和论文里的直接比**——论文用的是数据集自带的划分，测试集大得多。

| 类别 | 测试集 | AUROC（验证 / 测试） | 按建议的阈值：测试集判错 | 定阈值时预计的漏检 / 误报 |
|---|---|---|---|---|
| leather | 37 幅 | 0.96 / 0.99 | 2 幅 | 6% / 4% |
| bottle | 29 幅 | 0.70 / 0.92 | 4 幅 | 56% / 4% |
| screw | 48 幅 | 0.43 / 0.45 | 30 幅 | 51% / 39% |

- **皮革**：可以用。纹理均匀，缺陷（划口、胶渍、颜色）和周围差别大
- **瓶子**：不行。漏掉一半以上。破口在瓶口边缘，而自编码器对边缘本来就还原不好（合格的图像在边缘上得分也高），缺陷被淹没了
- **螺丝**：完全不行，AUROC 低于 0.5，比瞎猜还差。螺丝每幅图的位置和角度都不一样，模型连“合格的螺丝长什么样”都没学会

作为参考（凭印象写的数量级，没有逐篇核对）：文献里卷积自编码器在 MVTec AD 上的平均 AUROC 在 0.7 上下，用预训练特征的方法（PatchCore 等）在 0.98 以上。我们的结果和前者是一个水平。
**这证实了开始时的判断：这个小模型只够验证闭环，不够用于真实产品。**

### 6.3 发现并修掉的问题：阈值定得太高，一个不合格的都检不出来

第一次跑出来，三个类别的“测试集判错的数量”正好都等于“测试集里不合格图像的数量”——按建议的阈值，**不合格的全部漏掉了**。

原因在定阈值的规则。合成图像上，合格和不合格的得分总能分开，阈值取中间就行。两类分不开的情况，原来的规则是“合格最高分的 1.5 倍”——
这在真实数据上远高于所有不合格图像的得分。合成数据上这条分支从来没有真的被走到过。

改成：分不开时，取“漏检率 + 误报率”最小的位置（按比例算，不按个数——否则“全部判合格”总是错得最少的）；
训练报告里给出这两个比率；加起来超过一半时，备注里直接写“不建议使用这个模型”。

| 类别 | 测试集判错：改之前 → 改之后 |
|---|---|
| leather | 4 → 2 |
| bottle | 6 → 4 |
| screw | 12 → 30（改之前是“全部判合格”，错的少只是因为不合格的少；改之后的数字才反映出这个模型没用） |

**这个问题只有真实数据才能暴露。** 合成图像上的 0 误报、0 漏检，没有测到这条分支。

### 6.4 结论和下一步

1. **闭环在真实数据上是通的**：导入、数据集版本、训练、模型仓库、推理算子、得分一致性，都不用改就能处理真实的彩色大图
2. **模型需要换**。要在 bottle、screw 这样的类别上可用，得用预训练特征的方法（PatchCore、PaDiM 一类）。这意味着：
   - 训练服务要能下载或自带预训练权重（几十到上百兆）
   - 模型契约要多一种（输出仍然可以是“得分 + 异常图”，推理算子不用改——这正是把“算差异”包在模型里的好处）
   - 没有 GPU 时，这类方法“训练”很快（只是提特征、建一个记忆库），推理比现在慢
3. 用的是平台自己的划分，测试集只有 30～50 幅。要得到可信的数字，需要支持“沿用数据集自带的划分”，或者用更多的图像

### 6.5 没有做的

- 另外 12 个类别
- 用 MVTec 的图像走完“方案 → 上线包 → 工位”（推理算子在这些图像上运行、得分一致已经验证过；后面的流程和图像内容无关）
- 逐种缺陷的检出率
- 像素级的评价（异常图和数据集给的缺陷位置对不对）
