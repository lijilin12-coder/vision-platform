POC-13 的内容多：数据、训练任务、模型仓库、训练服务、推理，平台里之前都没有。所以分四步，每步一个 PR：

| 步 | 内容 | 状态 |
|---|---|---|
| ① | 样本、数据集版本、规则 N1（BC-9 数据的最小部分） | ✅ 完成，见 §1 |
| ② | 训练任务聚合（T-1～T-5）、训练后端端口、模型仓库的最小部分、训练完成后自动导入 | ✅ 完成，见 §2 |
| ③ | 训练服务：一种异常检测模型，导出 ONNX | 待做 |
| ④ | 模型在检测引擎里作为算子运行 | 待做 |

2026-11-23 确认的三件事（D8-8 由此定为“做最小的自有训练服务”）：

| 问题 | 决定 | 原因 |
|---|---|---|
| 第一种模型 | **小型卷积自编码器** | 从零训练，不需要预训练权重，没有 GPU 也能在几分钟内训完。效果一般，但这个 POC 要验证的是闭环，不是算法 |
| 训练数据 | 这个环境里**先用合成图像**；同时提供脚本，下载了 MVTec AD 的机器上可以跑同样的流程 | 数据集的下载站在当前环境里被网络策略挡住；约 5 GB；许可是非商用 |
| ONNX Runtime | **第 ④ 步再引入** | 新的第三方依赖，要先确认三个平台上怎么装、自动构建要多久 |

所以计划里“用 MVTec AD 的一个类别”这条通过标准，在这个环境里**不会**被满足，只能做到“流程支持，脚本提供”。

## 1. 第 1 步：样本、数据集版本、规则 N1

### 1.1 通过标准

| 标准 | 结果 | 证据 |
|---|---|---|
| 同一张图像换文件名后再导入，仍然被识别为同一个样本 | ✅ | 样本的 ID 就是图像文件内容的 SHA-256。集成测试 `SameImageUnderAnotherNameIsTheSameSample`；命令行在中文文件名下验证 |
| 把它同时放进基准图集和数据集，冻结被拒绝 | ✅ | 两个方向都测了：`N1_TrainedImageCannotEnterAGoldenSet`、`N1_BenchmarkImageCannotEnterADatasetVersion`。换文件名也拦得住 |
| 领域层单元测试覆盖 N1 | ✅ | `data_domain_tests` 8 个，只链接领域库 |

### 1.2 做了什么

| 部分 | 内容 |
|---|---|
| BC-9 数据（新上下文 `core/contexts/data`） | `Sample` 聚合：按内容识别、图像级标签（合格 / 不合格）、样本用途（未分配 / 留作基准 / 用于训练）<br>`Dataset` 和冻结的 `DatasetVersion`<br>`DataService` |
| BC-4 上线管理 | 基准图集的用例**引用样本**（之前只引用图像路径）；新端口 `SampleRegistry`；冻结基准图集时把其中的样本定为“留作基准” |
| 适配器 | 样本、数据集的 JSON 存储；样本的图像内容进内容仓库（和匹配模板共用，ADR-20） |
| 命令行 | `sample import / list / label`、`dataset new / add / freeze / show` |

### 1.3 规则 N1 是怎么保证的

```
样本用途：未分配 ──冻结基准图集──► 留作基准        （两种用途都不能再变）
              └──冻结数据集版本──► 用于训练
```

- 用途一旦定成一种，**不能改成另一种，也不能改回未分配**。因为冻结的基准图集和数据集版本本身不可修改，它们里面的样本用途也就永远成立
- **整体拒绝**：一批里有一个不行，整批都不改。被拒绝的基准图集不会保存；一起提交的其他图像的用途不受影响
- 用途确定之后**不能改标签**：冻结的图集和数据集版本记录的是冻结时的标签
- 提交训练任务时还会再检查一次（T-2，第 2 步）

### 1.4 实现时做的决定（请确认）

| # | 决定 | 理由 |
|---|---|---|
| 1 | 样本的 ID **就是**内容的 SHA-256，没有另外的编号 | “是不是同一个样本”变成比较 ID，不需要查表；同样内容的图像天然只有一个样本 |
| 2 | 哈希对**文件的字节**计算，不是对像素 | 简单、快。代价：同一幅画面另存成别的格式（PNG → BMP）会被当成两个样本，N1 拦不住。记入 Q-09（相似图像的隐性重叠），和“连拍的几张”是同一类问题 |
| 3 | 基准图集的每个用例在创建时**自动登记成样本**，标签取用例的真实判定 | 用户不用先导入样本再建图集；已有的命令和方案助手的示例都不用改 |
| 4 | 同一幅图像可以进**多个**基准图集，但不能在**一个**图集里出现两次 | 多个图集共用留作基准的图像是合理的；一个图集里重复只会让评估的数字失真 |
| 5 | 数据集冻结要求**每个样本都有标签** | 训练需要知道每一张是合格还是不合格 |
| 6 | 冻结数据集时先保存样本的用途，再保存版本 | 三种聚合分别保存，不是一个事务。万一中途失败，宁可样本被标成“用于训练”而没有对应的版本，也不要有一个版本里的样本还能被拿去做基准 |
| 7 | 没有接上数据上下文的程序里，基准图集和以前一样工作（不检查 N1） | 产线运行平台不需要数据上下文 |

### 1.5 没有做的

- 采集策略、短期图像缓存、从产线导入样本包（DAT-01、DAT-05）
- 检测框、分割掩码这类标注（DAT-03）；现在只有图像级的“合格 / 不合格”
- 样本和数据集的删除
- 按“零件编号 / 批次”整体划分用途（D8-10、Q-09）

### 1.6 测试

全部 274 个测试通过。本步新增 16 个：数据领域层 8 个、集成 8 个（按内容识别、标签冲突、冻结、基准图集登记样本、N1 两个方向、重启之后仍然成立、没有接数据上下文时照常工作）。新代码在 AddressSanitizer + UBSan 下无报告。

## 2. 第 2 步：训练任务和模型仓库

这一步里**没有真正的训练**：训练后端是端口，测试用的是按脚本报告进度的假后端。真正的训练服务是第 3 步。这一步验证的是任务的生命周期、规则、失败时的行为，以及“训练完成 → 模型自动进模型仓库”这条线。

### 2.1 通过标准

| 标准 | 结果 | 证据 |
|---|---|---|
| 领域层单元测试覆盖 T-1～T-5 | ✅ | `training_domain_tests` 11 个，只链接领域库 |
| 提交训练任务 → 完成 → 模型版本自动出现在模型仓库，来源信息完整 | ✅（用假的训练后端） | `CompletedJobBecomesAnUnpublishedModelVersionWithFullProvenance`：模型版本未发布；文件进了内容仓库；来源里有训练任务、数据集版本、划分方式、训练后端 |
| 训练服务不可用、训练失败时，任务状态正确，不影响其他功能 | ✅（用假的训练后端） | `UnavailableBackendLeavesAFailedJobAndEverythingElseWorks`、`TrainingFailureIsRecordedWithItsReason`、`NoBackendConfigured` |

### 2.2 做了什么

| 部分 | 内容 |
|---|---|
| BC-12 模型训练（新上下文 `core/contexts/training`） | `TrainingJob` 聚合（T-1～T-5）；训练配置、划分方式、训练报告；可重现的分层划分 `assignSplits`；`TrainingBackend` 端口（在领域层，ADR-30）；`TrainingService` |
| BC-7 模型仓库（新上下文 `core/contexts/models`） | `ModelVersion` 聚合：模型契约、来源、未发布 / 已发布；`ModelService`：导入、发布、查询 |
| 适配器 | 训练任务、模型版本的 JSON 存储；模型文件进内容仓库；训练 ↔ 数据、训练 ↔ 模型仓库的两个接缝；“没有配置训练服务”的占位后端 |
| 命令行 | `train submit / status / list / cancel`、`model list / show / publish` |

训练上下文的应用层**不依赖**数据和模型仓库：两个端口（数据集从哪里来、模型交到哪里去）由组装根接上。

### 2.3 五条不变量怎么落的

| 不变量 | 怎么保证 |
|---|---|
| T-1 只能用已冻结的数据集版本 | 提交时检查。数据上下文里“有版本号的就是冻结的”，没冻结的数据集取不到版本 |
| T-2 不能有留作基准的样本 | 提交时**再问一次**每个样本现在的用途。数据上下文的 N1 已经保证不会出现，这是第二道防线 |
| T-3 划分方式必须记录 | 比例和随机种子存在任务里；同样的样本和划分方式，在任何平台上结果相同（自己写的小伪随机数发生器，分层） |
| T-4 结束的任务不可修改 | 完成、失败、取消之后，任何命令都被拒绝；刷新时也不再去问训练后端。失败的任务不会“复活”，要重新提交 |
| T-5 模型版本必须记录来源 | 来源由任务给出；模型仓库拒绝来源不完整的“训练出来的”模型 |

### 2.4 出问题时的行为

| 情况 | 行为 |
|---|---|
| 提交不合规则（数据集没冻结、合格样本太少、划分不合法……） | **拒绝，不产生任务**，也不打扰训练后端 |
| 规则都通过，但训练后端连不上 | 任务**照样记录**，状态“已失败”，原因写明。它是一次合规的尝试，只是没能开始 |
| 查询进度时暂时连不上 | 任务状态**不变**（训练可能还在进行），下次再问 |
| 训练后端报告失败 | 任务“已失败”，带原因 |
| 训练后端报告完成但没有模型文件 | 任务“已失败”：不留下一个没有模型的“已完成” |
| 训练完成，但模型文件读不到 | 任务仍然“已完成”，没有模型版本，原因进日志 |
| 取消之后训练后端才报告完成 | 不接受，任务保持“已取消” |

### 2.5 实现时做的决定（请确认）

| # | 决定 | 理由 |
|---|---|---|
| 1 | “训练完成 → 导入模型仓库”由训练的应用服务**直接通过端口调用**，不是靠订阅领域事件 | 设计（08 §2.3）写的是领域事件触发。直接调用更简单，而且“导入失败了怎么办”好处理。事件照样发布，以后要改成订阅不难 |
| 2 | 划分由**我们的领域规则**做，训练后端拿到的是已经分好的样本 | 可重现（T-3）不依赖训练后端怎么实现 |
| 3 | 合格的样本至少 **8 个**才能提交 | 异常检测模型靠合格的样本学习“正常是什么样”。8 是个很低的门槛，只为了拦住明显的误操作 |
| 4 | 不合格的样本很少时，按比例四舍五入可能一个都分不到验证集、测试集 | 例如 4 个不合格样本、各 10%：全部进训练集。训练报告里的指标就没有意义。**这是个真实的问题**，第 3 步要处理（至少要在报告里说明） |
| 5 | 模型版本号由模型仓库自动递增（同一个模型名的下一个号） | 再训练一次就是下一个版本 |
| 6 | 训练进度只在内存里，不保存 | 它不是任务的一部分，只是最近一次查到的数字 |
| 7 | 没有配置训练服务的机器上，提交的任务以“已失败”记录 | 其余功能照常可用 |

### 2.6 没有做的

- 真正的训练（第 3 步）
- 量化、转换、验证（BC-8 模型工具链，POC-10）；模型契约的主版本号和兼容范围
- 方案里声明模型依赖、上线包锁定模型版本（P3、L2、L3）
- 训练任务完成时主动通知（现在要自己查询）
