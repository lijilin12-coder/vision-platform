| 项 | 内容 |
|---|---|
| 日期 | 2026-11-24 |

这份清单是对着 P0 需求逐条核对代码得出的。POC 阶段做了不少 P1 的东西（方案助手、训练闭环、定位），反而有几条 P0 还空着。

## 1. P0 需求的现状

| 需求 | 内容 | 现状 |
|---|---|---|
| CAT-01、02 | 算子注册和元数据 | ✅ |
| AUT-01、02 | 编辑方案，随时保证不变量 | ✅ |
| AUT-03 | 自动生成参数面板 | 后端 ✅（算子签名里有全部信息）；面板本身是前端的事 |
| AUT-04 | 调试运行，查看中间结果 | 后端 ✅；现在只能从命令行看 |
| AUT-05、06 | 发布；绝对 ROI | ✅ |
| EXE-01、02、04 | 执行计划、检测、三种用途 | ✅ |
| **EXE-03** | 检测结果包含**缺陷、测量值、位姿**三类结果项 | ❌ 现在的检测结果只有判定、判定依据、每个节点的状态。缺陷在哪里、量出来多少，没有作为结果的一部分交出来 |
| REL-01 | 上线包锁定模型版本 | ⚠️ 简化了：方案里直接写死模型版本（2026-11-24 确认可以先这样） |
| **REL-02** | **方案包导出和导入（文件）** | ❌ 没有做。现在两个平台靠共用一个数据目录 |
| **STA-01** | 工位**绑定图像源** | ❌ 工位现在没有图像源的概念，图像是命令行一张张喂进去的 |
| STA-02、03、04 | 启动 / 暂停 / 停止、热切换、回滚 | ✅ |

另外，路线图 M2 要求的：

| 内容 | 现状 |
|---|---|
| **拆成两个程序**：方案构建平台、产线运行平台 | ❌ 现在是一个命令行程序，什么都能做 |
| 对外的服务接口（界面要用的） | ❌ 只有命令行 |

## 2. 要做的五件事，按顺序

| # | 做什么 | 补的是 | 为什么排在这里 |
|---|---|---|---|
| **A** | **`vision-runtime` 和 HTTP 接口**（POC-2 的第 ① 步，方案见 [poc/poc-2-plan.md](poc/poc-2-plan.md)） | 对外的服务接口 | 之后每一件事都可以通过它来用和测；将来的前端也靠它 |
| **B** | **结果项**：检测结果里带上缺陷（位置、大小）、测量值（名称、数值、单位）、位姿 | EXE-03 | 改的是检测结果的形状，越早定越好——接口、上线后的记录都依赖它 |
| **C** | **图像源**：定义端口；先做“一个目录里的图像”这一种；工位绑定图像源，自己取图、检测 | STA-01 | 有了它，工位才是“自己在跑”，而不是被人喂图 |
| **D** | **方案包**：把方案版本连同模板、模型文件打成一个文件，导出、导入，按 H-06 的规则检查 | REL-02 | 两个平台分开的前提：产线那边没有方案编排，只能靠导入 |
| **E** | **拆成两个程序**：方案构建平台（能编辑、训练、打包）和产线运行平台（只能导入、部署、运行） | M2 | 最后做：它需要 D（方案包）才有意义 |

每一件都按现在的做法来：需要设计的先写设计、领域层带不变量和测试、一个 PR、Windows 和 Linux 的自动构建通过后合并。

## 3. 不在后端 MVP 里的

- 前端（界面）。等上面五件做完再考虑
- 鸿蒙相关的一切（POC-3a、3b、4、6、7、8、10）
- 真正的相机。图像源先只有“目录里的图像”；相机属于范围外的“工业相机”和待做的 POC-7
- P1 里还没做的：对比评估、样本包、标注、复判
- 模型依赖的“声明 + 锁定”（H-08 的完整做法）

## 4. 做完之后是什么样

一台机器上的方案构建平台：搭方案（现在靠命令行或 HTTP 接口）、训练模型、调试、把方案版本和它用到的模板、模型打成一个方案包文件。
另一台机器上的产线运行平台：导入方案包，部署到工位；工位从一个目录里取图像，连续检测，每次的结果里有判定、缺陷的位置、测量值；可以热切换、回滚。
两边都通过 HTTP 接口操作，为前端准备好了。
