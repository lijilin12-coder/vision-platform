# 15 验收检查

> 状态：已实现（2026-11-25）。属于 **BC-4 上线管理**，对应需求 REL-05、规则 L4 的一半。
> 术语见[术语表](02-glossary.md)：验收检查、验收标准、基准图集、真实判定、上线包。

## 1. 要解决什么

在这之前，一个方案版本只要“能加载”就能做成上线包、部署到工位。没有任何一步回答过：**它判得对不对？**

验收检查就是这一步：把上线包在**基准图集**上跑一遍，和**人确认的真实判定**比，按**验收标准**得出通过 / 没通过，并把结果记在上线包上。

| 词 | 意思 |
|---|---|
| 基准图集 | 一组图像，每一幅都有人确认的真实判定（合格 / 不合格），加上验收标准。建好就冻结，不能改 |
| 验收标准 | 用户定的：最多漏检几张、误报率最多多少、最多出错几张。默认都是 0 |
| 漏检 | 真实不合格，却判成了合格 |
| 误报 | 真实合格，却判成了不合格。误报率 = 误报数 ÷ 真实合格的用例数 |
| 出错 | 检测没做下来（判定是 ERROR） |

## 2. 模型

验收记录 `AcceptanceRecord` 是上线包 `Release` 聚合里的一个实体（[05](05-tactical-design.md) §4.1）：

```
Release
  acceptance: AcceptanceRecord?
     goldenSetId、goldenSetName、checkedAtMs、passed
     当时的验收标准（抄一份）
     结果：用例数、漏检、误报、出错、耗时
     判错的用例：哪一个、真实判定是什么、判成了什么
```

标准和数字都抄在记录里：以后回头看这条记录，不用再去找当时的基准图集。

规则：

| 编号 | 内容 |
|---|---|
| L4（一部分） | 验收检查**没有通过**的上线包不能部署。还没做过验收检查的可以部署，见 §4 |
| A1 | 已撤回的上线包不再做验收检查 |
| A2 | 验收记录必须覆盖基准图集的**全部**用例。只跑了一部分的结果不能当验收结论 |
| A3 | 通过还是没通过，由验收标准**算出来**，不由调用的一方说了算 |
| A4 | 可以重新验收（例如换一个更全的基准图集）；以最近的一次为准 |

“对照真实判定算出漏检和误报”的规则（`evaluateCases`、`meets`）只有一份，方案助手的实验和验收检查用的是同一份（[08](08-platforms-and-training.md) §4）。

事件：`ReleaseAccepted`、`ReleaseAcceptanceFailed`。

## 3. 一次验收检查怎么走

```
ReleaseService::checkAcceptance(上线包, 基准图集)
  1. 取出上线包里的方案版本、基准图集
  2. 每个用例：CaseRunner（端口）读图像、用检测引擎检测一次（用途是“检查”）
  3. evaluateCases：对照真实判定 → 漏检、误报、出错
  4. Release::recordAcceptance：按验收标准得出通过 / 没通过，记下来（A1～A4）
  5. 保存，发布事件
```

- **没通过是一个正常的结果**，不是出错：检查做完了，结论是“不行”。接口返回成功、`passed` 为假；命令行的退出码是 2。
- **做不下去才是出错**：基准图集里的图像读不出来、方案加载不了。这时不留记录——半截的结果不能当结论（A2）。
- **检测本身出错**（某个算子失败）不算做不下去：这个用例记为“出错”，检查照常做完。
- 验收检查不经过工位，所以**不留检测记录**（[14](14-inspection-records.md)），也不影响工位的计数。
- 检测很慢，做的时候不拿着锁；记结果之前重新取一次上线包（这段时间里它可能被撤回了）。

## 4. 为什么“没验收的也能部署”

战术设计里的 L4 是“可部署，**当且仅当**验收检查通过”。现在只做了一半：没通过的不能部署；没验收的可以，界面和命令行上都标着“未验收”。

原因是产线运行平台：

- 基准图集在方案构建平台上。产线运行平台没有它，做不了验收检查
- 方案是靠**方案包**带到产线的，上线包是在产线那台机器上**重新创建**的——在方案构建平台上做的验收记录带不过去
- 所以如果严格执行 L4，产线上一个上线包都部署不了

要严格执行，需要先有**上线包文件**（`ReleaseBundle`，[05](05-tactical-design.md) §4.3：把上线包连同验收记录一起带到产线）。那是下一步的事。

## 5. 基准图集怎么来

以前只有 `golden sample`（给方案助手生成练习用的）。现在加了一种最直接的办法：**两个目录**。

```
golden create <名称> --ok <合格图像的目录> --ng <不合格图像的目录> [--max-misses N] [--max-false-alarm-rate R] [--max-errors N]
```

“这幅图像放在哪个目录里”就是人对它的确认。只看目录的第一层；用例的名字是 `ok/文件名`、`ng/文件名`。

和以前一样：同样内容的图像是同一个样本，不能在一个图集里出现两次；放进基准图集的图像不能再用于训练（规则 N1）。

## 6. 怎么用

| 方式 | |
|---|---|
| 命令行 | `golden create …`、`release accept <上线包ID> <基准图集ID>`、`release show`、`release list`（带验收状态） |
| HTTP | `GET/POST /api/golden-sets`、`POST /api/releases/{id}/acceptance`；`GET /api/releases` 里带验收状态和记录 |
| 界面 | “上线包”页面：左边是上线包和验收状态；右边建基准图集、点“验收”、看报告和判错的用例。工位页面的部署下拉框里标出没验收的、没通过的 |

## 7. 请确认的决定

1. **没验收的上线包可以部署**，只有没通过的不行（§4）。
2. **验收检查可以重做，以最近一次为准**（A4）。所以“标准定严了”时可以新建一个宽一些的基准图集重新验收——这是有意留的口子，但也意味着想绕过去的人绕得过去。记录里写着用的是哪个基准图集、当时的标准，事后查得到。
3. **已经在工位上运行的上线包，后来验收没通过，不会自动停下来**。规则只在部署那一刻检查。
4. **基准图集里只存图像的路径**，不复制图像。图像被删了、挪了，验收检查就做不下去（会说出是哪一个用例）。

## 8. 还没有的

- 上线包文件（把验收记录带到产线）→ 之后才能严格执行 L4
- 基准输出、跨平台一致性检查（L4 的另一半、L5）
- 验收检查在后台做、显示进度（现在一个请求做到底，用例多了要等）
- 对比评估：两个上线包在同一个基准图集上谁更好
- 验收记录的历史（现在只留最近一次）
- 测量值、缺陷位置对不对（现在只比“合格 / 不合格”）
