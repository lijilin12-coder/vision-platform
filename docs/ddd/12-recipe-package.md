## 1. 为什么需要

到这一步之前，“两台机器”只是一个说法：命令行的所有功能都在同一个数据目录上做。方案构建平台搭好的方案，产线上的电脑拿不到。

方案包就是那个可以拷走的东西：**一个文件**，里面有一个方案版本和它运行所需要的一切。

```bash
# 构建机
vision-cli package export <方案版本ID> 表面检测.vpkg

# 把文件拷到产线的电脑上（U 盘、网盘都行），然后在那里：
vision-cli package import 表面检测.vpkg
vision-cli release create <方案版本ID>
vision-cli station deploy <工位ID> <上线包ID>
```

## 2. 包里有什么

一个不压缩的 tar 文件（建议扩展名 `.vpkg`）：

| 文件 | 内容 |
|---|---|
| `manifest.json` | 清单：包 ID、方案版本的 ID 和内容哈希、用到的算子（ID 和主版本号）、每个模板和模型的哈希 |
| `recipe-version.json` | 方案版本文档（发布语言：节点、连线、参数、ROI、模板的引用） |
| `content/<sha256>` | 匹配模板的图像、模型文件。文件名就是内容的哈希 |

模型带着它的**契约**（种类、输入尺寸、阈值）和**来源**（哪次训练、哪个数据集版本）一起走：到了另一台机器上，仍然说得清这个模型是怎么来的。

**为什么是 tar**：格式简单到可以自己写一百行实现，不用为它引入一个压缩库；又是标准格式，`tar tf 某个包.vpkg` 就能看里面有什么。
不压缩，是因为里面主要是 PNG 和模型权重，本来就压不动。

同样的内容导出两次，除了包 ID 之外字节完全相同（文件里不写时间）。

## 3. 导入的规则

规则在上线管理的领域层（`planImport`），是纯粹的判断：输入“包里声称有什么”和“本机现在有什么”，输出“可以，要新增这些”或者“不行，因为……”。

| # | 规则 | 为什么 |
|---|---|---|
| K1 | 清单的格式版本必须是本平台认识的 | 来自更新的平台的包，宁可拒绝也不要猜 |
| K2 | 包里用到的每个算子，本机都必须有，主版本号相同。**缺一个就整个拒绝** | 缺算子的方案导进来也运行不了。出错信息把缺的全列出来，不是只报第一个 |
| K3 | **同 ID 不同内容是冲突，拒绝** | 方案版本、模型版本都是不可变的：同一个 ID 不可能指两样东西。出现了就说明哪里出了问题，不能悄悄覆盖 |
| K4 | **重复导入不出错**：本机已经有一模一样的，就什么都不做 | 导入可以放心地重试。上一次导入中途断了，再导入一次会把剩下的补齐 |

在这些规则之前，文件本身先要过关：每一份内容的哈希、方案文档的哈希，都必须和清单一致；包里不能有不认识的文件名。
文件被改了一个比特、被截断、根本不是方案包——全部拒绝，而且**什么都不留下**（测试里逐种检查过）。

导出也有一条规则：方案用到的模型必须已经**发布**。没发布的模型带过去也不能正式使用，不如在出门之前就拦住。

### 3.1 先检查完，再动手

导入分两步：

1. **只检查，不写**：文件的完整性 → 清单自洽 → K1～K4
2. **写**，顺序是“被引用的先写”：内容 → 模型 → 方案版本

第二步中途失败（磁盘满了、断电）的话，留下的只是一些还没人引用的内容和模型——它们本身是完整、正确的；再导入一次就能接着完成（K4）。
不会出现“方案版本已经在了，但它要的模板还没写进去”的状态。

## 4. 导入进来的方案版本放在哪里

**不进方案编排。** 方案编排里是可以编辑的方案；导入进来的是一份已经发布、不可变的方案版本文档，只给上线包和检测引擎用。
它放在上线管理自己的一个仓库里（`ImportedRecipes`）。

于是“按 ID 找方案版本”这个端口现在有两个来源：本机方案编排发布的、从方案包导入的。先找前者。

这一条是为下一步（拆成两个程序）准备的：**产线运行平台上没有方案编排**，它的方案版本全都来自导入。

## 5. 和原来的设计的出入（请确认）

[05-tactical-design.md](05-tactical-design.md) §4.3 里设计的是**两种**包：

| | 原设计 | 现在 |
|---|---|---|
| 方案包 `RecipePackage` | 带走方案**继续编辑** | ⚠️ 做了，但导入之后**不能继续编辑**，只能上线和运行 |
| 上线包文件 `ReleaseBundle` | 带到产线**部署**：含上线包、检查记录、指定平台的模型制品 | ✅ 2026-11-25 做了（[16](16-release-bundle.md)）：带上线包和验收记录；指定平台的模型制品还没有 |

也就是说，现在的方案包实际承担的是“带到产线部署”这个用途。原因：

- 后端 MVP 的目标是“产线那台机器能拿到方案并运行”，这是最短的路
- “继续编辑”需要把可编辑的方案（具名区域、画布布局、草稿）也带过去，而现在的发布语言里这些已经被展开、丢掉了
- 上线包文件要带的“检查记录”“指定平台的模型制品”，平台里现在都还没有

代价：产线上导入之后，要在产线机上再执行一次 `release create`。上线包不是在构建机上做好带过去的，所以“构建机上验收过的那个上线包”和“产线上运行的那个上线包”不是同一个对象（方案版本和模型是同一个）。
2026-11-25：验收检查和上线包文件都有了（[15](15-acceptance-check.md)、[16](16-release-bundle.md)）。从那时起，**只导入方案包、在产线上自己创建的上线包部署不了**（没有验收记录）；带到产线部署要用上线包文件。

其他决定：

| 决定 | 原因 | 代价 |
|---|---|---|
| 模型版本的 ID（`名称@v数字`）原样带过去 | 方案里写的就是这个 ID | H-06 说“ID 使用全局唯一 ID”，而这个 ID 不是：两台构建机各自训练出 `surface@v1`，内容不同，导到同一台机器上会被 K3 拒绝。结果是安全的（不会混），但要靠人改名。模型 ID 的问题留到做 H-08 的“声明 + 锁定”时一起解决 |
| 导入的模型直接是“已发布” | 它在导出的那一方已经发布过了（导出规则保证） | 产线机上没有再确认一次的环节 |
| 包里的内容整个读进内存 | 简单 | 几百兆的模型会占同样多的内存。现在的模型 26 万字节 |
| 不签名、不加密 | 范围外 | 校验和只防意外损坏，**不防有意篡改**：能改内容的人也能改清单里的哈希 |

## 6. 顺带修掉的一个缺陷

做这一步时撞出了一个早就潜伏着的问题：部署了一个用到模型的上线包之后**马上退出程序**，会崩溃（`pure virtual method called`）。

原因是销毁的顺序。C++ 里对象的成员按声明的反序销毁；在组装好的平台里，推理引擎声明在工位服务后面，所以先被销毁。
而工位的后台加载线程这时可能还在用它。

修法：平台开始销毁之前，先等工位的后台加载全部结束（`StationService::finishBackgroundWork()`）。
加了回归测试；去掉修复后它每次都崩溃，加上之后通过，在 AddressSanitizer 和 ThreadSanitizer 下干净。

- 一个包里放多个方案版本；批量导出
- “缺少对应格式的模型制品时可以导入但标记为不能上线”（H-06）：现在模型只有 ONNX 一种格式，没有“对应格式”的问题。到鸿蒙上用 MindSpore Lite 时再做
