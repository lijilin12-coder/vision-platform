## 1. 之前和现在

之前工位没有“图像从哪里来”的概念：`station run <工位> <图像...>` 是命令行把图像一张张喂给它。
这适合做实验，但不是工位在产线上的样子——产线上是工位**自己**从相机取图。

现在工位可以绑定一个图像源，自己取图、检测：

```bash
vision-cli station bind <工位ID> folder ./来料图像
vision-cli station run <工位ID>                # 取完为止
vision-cli station run <工位ID> --follow 30    # 暂时没有新图像时再等 30 秒：可以一边运行一边往目录里放图像
```

## 2. 设计

三样东西，各在各的层：

| 东西 | 在哪一层 | 是什么 |
|---|---|---|
| `ImageSourceBinding` | 工位的领域层 | 值对象：“哪一种、在哪里”（例如 `folder` + 一个目录）。工位只记这个，随工位一起保存 |
| `ImageSource`、`ImageSourceFactory` | 工位的应用层（端口） | “取下一帧”。工位这边只认识这个接口 |
| `FolderImageSource` | 适配器 `adapters/image_sources` | 一种实现：一个目录里的图像 |

以后接相机，是在适配器里再加一种实现、给它起一个种类的名字（比如 `usb`），工位的领域层和应用层不用改。

### 2.1 不变量

| # | 规则 |
|---|---|
| **S7** | 图像源只能在工位**停止**时绑定、更换、解除 |

运行中换图像源，等于检测对象在半路上变了：前一张是这条线的零件，后一张是那条线的。必须先停下来。

绑定时会先试着打开一次：目录不存在、种类不认识，**当场拒绝**，不会留下一个要等到启动之后才发现打不开的绑定。

### 2.2 “取下一帧”的三种回答

| 回答 | 含义 | 工位怎么办 |
|---|---|---|
| 一帧图像 | | 检测它 |
| 空 | 现在没有新的（目录里的都处理过了；相机还没拍下一张） | 不算出错，过一会儿再问 |
| 失败 | 这一帧坏了（文件损坏；相机出错） | 报告出去。**不算一次检测**，不占检测序号；再取会接着取后面的，不会卡在坏的那一帧上 |

### 2.3 目录图像源的行为

- 每次取图时重新看一遍目录，把还没处理过的图像按文件名顺序交出去，每个文件只交一次
- 所以运行过程中放进来的新图像会被接着处理——一个最简单的“假相机”
- “处理过哪些”只记在内存里。工位停止再启动，目录里的图像**从头再来一遍**
- 只认 `.png`、`.jpg`、`.jpeg`、`.bmp`（大小写都行）；别的文件和子目录不理会

## 3. 实现时做的决定（请确认）

| 决定 | 原因 | 代价 |
|---|---|---|
| **谁来循环**：工位服务只提供“取下一帧并检测”（`inspectNext`），循环由调用它的程序来转 | 最简单；什么时候取下一帧（触发）是另一个问题 | 2026-11-24 更新：`vision-line serve` 就是这个循环，工位由此可以持续运行（见 [13-two-programs.md](13-two-programs.md) §3）。“触发”（定时、外部信号）仍然没有 |
| 坏的一帧不算一次检测 | 它没有进入检测引擎，没有判定可言 | 产线上相机连续出坏帧时，现在不会触发自动回滚，也不会让工位进入故障状态。真接相机时要重新考虑：“取不到图”应该算工位的故障 |
| 停止再启动，目录从头再来 | 不用把“处理到哪里了”存下来 | 重启后会重复检测同一批图像。对“假相机”无所谓；真相机没有这个问题 |
| 图像源的位置是一段文字，由适配器自己解释 | 不同种类的图像源需要的信息不一样 | 写错了要到绑定时才知道（会被拒绝并说明原因） |

## 4. 没有做的

- 相机（USB、工业相机）：范围外的“工业相机”和待做的 POC-7
- 触发：定时取图、外部信号触发
- 工位在后台自己一直运行（见 §3 第一条）
- 多图像检测（多相机、多光源，H-11）
- 图像源的 HTTP 接口（工位的接口整体还没有加）
- 记录每次检测用的是哪一帧（2026-11-24 做了，见 [14](14-inspection-records.md)，属于 BC-10 质量分析）
