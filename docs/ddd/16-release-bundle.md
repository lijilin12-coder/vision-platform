# 16 上线包文件

> 状态：已实现（2026-11-25）。属于 **BC-4 上线管理**，对应需求 REL-03、走查发现 F-2；规则 L4 由此收紧。
> 术语见[术语表](02-glossary.md)：上线包、上线包文件、方案包、验收检查。

## 1. 要解决什么

[验收检查](15-acceptance-check.md)做完之后留下一个缺口：验收是在方案构建平台上做的（基准图集在那里），
而产线上的上线包是导入方案包之后**重新创建**的——验收记录带不过去。所以当时只能规定“没验收的也能部署”。

**上线包文件**把这个缺口补上：把上线包**连同它的验收记录**一起带到产线。于是规则可以收紧成设计里本来的样子：

> **L4：只有验收检查通过了的上线包才能部署。**

## 2. 两种文件

| | 方案包 `.vpkg` | 上线包文件 `.vrel` |
|---|---|---|
| 里面有什么 | 方案版本 + 它用到的模板、模型 | 方案包的全部 + **一个验收通过的上线包**（ID、验收记录） |
| 导入之后 | 有了方案版本。上线包要自己创建——没有验收记录，部署不了 | 有了方案版本，**也有了那个上线包**，ID 和验收记录不变，可以直接部署 |
| 命令 | `package export / import` | `release export / import` |

文件的格式是同一种（一个不压缩的 tar，[12](12-recipe-package.md) §3）；上线包文件只是清单 `manifest.json` 里多了 `release` 一项。
所以上线包文件也可以用 `package import` 导入——那样只拿到方案版本。

## 3. 规则

| 编号 | 内容 |
|---|---|
| L4 | 只有验收检查通过了的上线包才能部署。没验收的、没通过的、撤回了的都不行 |
| B1 | 只有“可以部署”的上线包（没撤回、验收通过）才能**导出**成上线包文件；也只有这样的才能从文件里**接收**进来 |
| B2 | 接收时本机已经有同一个 ID 的上线包：方案版本相同就什么都不做——已有的那个原样不动，**哪怕它后来在本机被撤回了**（再导入一次不能把它“复活”）；方案版本不同就是冲突，拒绝 |

方案版本和模型那一部分照旧按方案包的规则 K1～K4 导入。

**B1 接收时不只看“通过”这个标记。** 文件是可以手工改的：接收的一方按记录里的数字（漏检、误报、出错）和记录里的验收标准**重新算一遍**，对不上就拒绝。
这只防得住粗心和粗糙的改动，防不住有心的人把数字一起改掉——见 §6。

**上线包的 ID 不变。** 两台机器上说的是同一个上线包：产线上的检测记录里写的上线包 ID，拿回方案构建平台查得到。

## 4. 怎么走

```
方案构建平台                                        产线运行平台
release create <方案版本>
golden create … ; release accept <上线包> <基准图集>
release export <上线包> 亮斑.vrel   ──── 文件 ────→  release import 亮斑.vrel
                                                    station deploy <工位> <同一个上线包ID>
```

导出（`PackageService::exportRelease`）：向上线管理要这个上线包（B1）→ 和导出方案包一样收集方案版本、模板、模型 → 写文件。

导入（`PackageService::importRelease`）：
1. 读文件、核对校验和（适配器）
2. 文件里没有上线包、上线包和带的方案版本对不上、验收没通过 → 拒绝，**什么都不留下**
3. 按方案包的规则导入方案版本和模型
4. 上线管理接收上线包（`Release::adopt`，B1、B2），保存，发布 `ReleaseImported`

第 3 步之后第 4 步失败（磁盘满了）的话，留下的是一个完整、正确的方案版本，没有上线包；再导入一次就接着完成。

## 5. 调试用的口子：`--allow-unaccepted`

规则收紧之后，有些事做不了了：刚搭好方案想马上在工位上试一试、用压力测试量热切换的耗时——这些时候没有基准图集，也不关心判得对不对。

三个程序都有一个选项 `--allow-unaccepted`：允许部署**还没验收**的上线包。

- **验收没通过**的仍然不行。它放过的是“没人检查过”，不是“检查过、不行”
- 每次使用都在日志里记一条警告
- 默认关。它不是给正式生产用的

## 6. 定下来的决定（2026-11-25 确认）

1. 规则 L4 是严格的：没验收的上线包不能部署。“发布 → 做成上线包 → 部署”中间要多一步验收；产线上要用上线包文件，方案包只能带方案。
2. 留一个调试用的口子 `--allow-unaccepted`（§5）。
3. 上线包文件没有签名。接收时会重新核对验收记录的数字，但有心的人可以把数字一起改掉；要防这个需要签名和密钥管理，以后再做。
4. 产线上撤回了的上线包，重新导入不会复活（B2）。要重新用它，得在方案构建平台上做一个新的上线包。
5. 方案包保留，没有被上线包文件取代：它的用处是“只把方案带过去”。

## 7. 还没有的

- 签名（§6 第 3 条）
- 基准输出、跨平台一致性检查：现在上线包文件导入之后直接可以部署，没有“在本平台上再跑一遍，和基准平台的结果比”这一步（L4 的另一半、L5）
- 指定目标平台的模型制品：现在带的是同一个 ONNX 文件，各平台通用
- 界面上的导入（产线运行平台没有界面）
- 导入方案包之后继续编辑
