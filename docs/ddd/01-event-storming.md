## C. 方案发布、上线包与部署

> 依据 H-08 的决定：**方案声明模型依赖（模型 ID + 兼容范围），上线包锁定具体版本**。上线包是验证、热更新和回滚的最小单位。

| # | 🟧 事件 | 🟦 命令 | 🟨 执行者 | 备注 |
|---|---|---|---|---|
| C1 | 方案校验已通过 | 校验方案 | 方案开发者 / 系统 | 必填输入都已连接、引用都存在 |
| C2 | ❌ 方案校验未通过 | 校验方案 | 方案开发者 / 系统 | |
| C3 | 方案版本已发布 | 发布方案 | 方案开发者 | 发布后不可修改；包含模型依赖声明 |
| C4 | 上线包已创建 | 创建上线包 | 方案开发者 | 锁定：方案版本 + 每个模型依赖的具体版本 |
| C5 | ❌ 上线包创建被拒绝 | 创建上线包 | 方案开发者 | 选择的模型版本超出方案声明的兼容范围，或者模型还未发布 |
| C6 | 一致性验证已通过 | 运行一致性验证 | 系统 | 以上线包为单位，用基准图在目标平台上运行，结果与基准一致 |
| C7 | ❌ 一致性验证未通过 | 运行一致性验证 | 系统 | 🟥 见 H-03 |
| C8 | 上线包已部署到工位 | 部署上线包 | 方案开发者 | 进入工位的“待切换”状态，见 G 阶段 |

| C10 | 方案版本已停用 | 停用方案版本 | 方案开发者 | 已停用的版本不能再用于创建新的上线包 |

## 🟪 规则（每当……就……）

| # | 规则 |
|---|---|
| P1 | 每当**检测已完成**，就按**采集策略**决定是否保存图像（→ E2） |
| P2 | 每当**检测已完成**，如果属于某个批次，就更新批次统计 |
| P3 | 每当**复判发现误判**，就把图像加入“待标注”数据集（→ E4） |
| P4 | 每当**模型已导入**，就自动依次执行量化 → 转换 → 验证（F3 → F4 → F6） |
| P5 | 每当**上线包已创建**，就在目标平台上运行一致性验证（→ C6） |
| P6 | 每当**上线包已就绪**，就在下一次检测开始前切换（→ G4） |
| P7 | 每当**切换后连续 N 次检测出现 ERROR**，就自动回滚到上一个上线包（→ G6） |
| P8 | 每当**工位启动**，就加载上次生效的上线包并预热模型（→ G1、G2） |
| P9 | 每当**新的模型版本已发布**，且在某个方案声明的兼容范围内，就提示可以为该方案创建新的上线包 |

## 🟥 热点问题

### 待讨论

| # | 问题 |
|---|---|
| H-01 | 算子升级后（比如参数变了），已经发布的方案怎么办？算子需要版本号吗？方案要记录它用的算子版本吗？ |
| H-02 | 方案引用的模型，在目标平台上没有对应格式的文件时，是在部署时拒绝，还是在运行时报错？（初步：部署时拒绝，见 C9） |
| H-03 | “结果一致”怎么定义？传统算法在不同平台上也可能有微小的浮点误差，容差定多少？哪些输出要比较（判定、测量值、缺陷位置）？ |
| H-06 | 方案怎么从一个平台带到另一个平台？（建议：领域层定义“方案包”及导入规则，传输方式作为基础设施适配器，先只做文件导出导入。待确认） |
| H-07 | 平台内的标注工具做到什么程度？还是直接对接现成的开源标注工具？ |
| H-10 | 一台电脑上多个工位同时运行，会争用 CPU、GPU、NPU。需要工位优先级或资源分配吗？ |

### 已决定

| # | 问题 | 决定 | 日期 |
|---|---|---|---|
| H-04 | 热更新时，正在进行的检测用旧版本还是新版本？ | **以检测开始时工位生效的上线包为准** | 2026-11-12 |
| H-05 | 一台电脑可以同时运行多个工位吗？ | **可以**。工位是独立的运行单元，各自绑定图像源和生效的上线包 | 2026-11-12 |
| H-08 | 方案版本和模型版本的关系？ | **声明 + 锁定**：方案声明模型依赖（模型 ID + 兼容范围，主版本号相同即输入输出格式相同）；**上线包**锁定方案版本和具体模型版本，作为验证、热更新、回滚的单位。只换兼容的模型不需要改方案；超出兼容范围必须发布新的方案版本 | 2026-11-12 |
| H-09 | 回滚的单位？ | 由 H-08 推出：**回滚到上一个上线包**，方案和模型一起回到之前验证过的组合 | 2026-11-12 |
