## 1. 要解决的问题

缺陷检测和测量都默认“零件每次都在画面的同一个位置”。实际上零件会偏、会转。不先知道零件在哪里，ROI 就框不准，卡尺就量错地方。

**定位**就是回答“零件在画面的哪里、转了多少度”。最常用的办法是模板匹配：事先从一张样图上框出零件上有特征的一块（**匹配模板**），检测时在画面里找到和它最像的位置。

这带来三件平台现在没有的东西：

1. 方案要能带着一幅图像（模板）一起保存、发布、上线
2. 算子之间要能传递“位置和角度”（**位姿**）
3. 定位之后，后面的算子要能用上这个结果

## 2. 模板不是模型

模板和模型都是“方案运行时要用的二进制内容”，很容易想成一类东西、放进模型仓库统一管理。它们其实不一样：

| | 模型 | 匹配模板 |
|---|---|---|
| 从哪里来 | 训练出来的，训练和方案无关 | 从**这个产品**的一张样图上框出来的 |
| 属于谁 | 独立存在，多个方案可以共用 | 属于一个方案，离开这个方案没有意义 |
| 方案怎么引用 | 只声明“需要哪一类”（模型依赖 + 兼容范围） | 直接包含 |
| 什么时候定下来 | **组装上线包时**才锁定具体版本 | **发布方案时**就定了，和参数一样 |
| 能不能单独换 | 能。换模型不用重新发布方案 | 不能。换模板就是改方案，要重新发布 |

**结论：匹配模板是方案的一部分，随方案版本一起冻结。** 不进模型仓库，上线包里不单独锁定——上线包锁定了方案版本，模板自然跟着锁定了。

这样做的直接好处：一致性验证、热切换、回滚都不用改。它们本来就以“方案版本不可变”为前提。

## 3. 通用语言

| 术语 | 代码名 | 定义 | 状态 |
|---|---|---|---|
| 匹配模板 | `MatchTemplate` | 从样图上框选、用于定位的一小幅图像，连同它在样图上的位置。属于一个方案，有名字 | 已有，补充定义 |
| 基准位置 | `ReferencePose` | 模板在样图上的位置。“零件在标准位置”就是指模板出现在这里 | **新增** |
| 位姿 | `Pose` | 位置（x、y，像素）+ 旋转角度（度）。由定位算子输出 | 已有，明确内容 |
| 定位 | `Locating` | 在图像里找到匹配模板，得到位姿 | 已有（作为任务类型） |
| 对齐 | `Align` | 按位姿把图像平移、旋转，让零件回到基准位置 | **新增** |
| 相对 ROI | `RelativeRoi` | 相对于定位基准定义的 ROI，运行时按位姿换算 | 已有，**这次不做**（§7） |

几点说明：

- **不引入“方案资源”这个泛化的概念。** 现在只有匹配模板一种。以后如果要“和标准图像比较”，那是另一个有明确含义的领域概念（标准图像），到时候再加；它们在技术上会共用同一个内容仓库，但在通用语言里不叫同一个名字。
- **位姿里没有“匹配分数”。** 分数是“这次匹配有多可信”，不是位置的一部分。定位算子把位姿、分数、是否找到分成三个输出。
- **角度的方向**：**顺时针为正**（按屏幕上看到的方向），单位是度，范围 (-180, 180]。和教程大作业一致。（v1.0 这里写的是“逆时针为正，和 `getRotationMatrix2D` 以及教程大作业一致”，这句话自相矛盾：教程用的是顺时针。见 §15。）

## 4. 方案编排（BC-2）的变化

### 4.1 `Recipe` 聚合

```
Recipe（聚合根）
  …
  └─ MatchTemplate（实体）× N
       templateId, name            名字在方案内唯一
       content: ContentRef         图像内容的哈希 + 字节数（ADR-20 内容寻址）
       width, height               模板的尺寸
       reference: ReferencePose    模板左上角在样图上的位置
       sourceWidth, sourceHeight   样图的尺寸
```

聚合里只有**引用**（内容哈希），没有图像数据本身。图像数据在内容仓库里。所以领域层仍然不依赖 OpenCV，方案草稿的 JSON 文件也不会因为带了模板而变大。

原设计里的 `TemplateRef（值对象）` 升级为 `MatchTemplate（实体）`：它有自己的标识和名字，可以被改名、被多个节点引用。

### 4.2 节点怎么引用模板

新增一种参数类型：**模板参数**（`ParamType::Template`）。它的值是方案里某个匹配模板的 `templateId`。

为什么是参数而不是输入端口：端口上流动的是“这一次检测的数据”，每次检测都不一样；模板和阈值一样，是事先配好、每次都相同的东西。

### 4.3 新的规则

| # | 规则 | 何时检查 |
|---|---|---|
| **R7** | 模板参数的值必须是本方案里存在的匹配模板；仍被节点引用的匹配模板不能删除 | 随时 |
| **R8** | 匹配模板的名字在方案内唯一；尺寸至少 8×8，并且不超过样图 | 随时 |
| **P6** | 每个模板参数都已设置（不为空） | 发布时 |

R7 和已有的 R5（具名区域的引用）是同一种规则。

### 4.4 命令和事件

| 命令 | 说明 | 事件 |
|---|---|---|
| `createMatchTemplate(name, 样图, 框)` | 应用层把框里的图像裁出来、存进内容仓库，得到内容引用，再调用聚合 | B11 匹配模板已创建（和其他编辑命令一样，不对外发布） |
| `renameMatchTemplate` / `removeMatchTemplate` | 删除时检查 R7 | — |

**模板的内容不可修改。** 想换一幅图，就新建一个模板、把节点指向它、删掉旧的。内容寻址存储本来就是这个语义：内容变了，哈希就变了，就是另一个东西。

### 4.5 发布语言：方案版本文档

格式版本从 `0.1` 升到 `0.2`，新增一段：

```json
"templates": [
  { "id": "t1", "name": "定位孔",
    "sha256": "9f2c…", "bytes": 18234,
    "width": 96, "height": 96,
    "reference": { "x": 212, "y": 140 },
    "source": { "width": 640, "height": 480 } }
]
```

模板参数在节点的 `params` 里就是一个字符串（`"template": "t1"`）。

`0.1` 的文档（没有 `templates`）继续能读：没有这一段就是没有模板。

## 5. 位姿：共享内核的变化

```
Pose（值对象）
  x, y                      基准点现在的位置（像素）
  angle                     相对于基准位置转了多少度，顺时针为正
  referenceX, referenceY    基准点在样图上的位置（v1.1 新增，见 §15）
```

基准点是模板的中心。

- `PortType` 新增 `Pose`；`Value` 新增 `Pose`
- 类型兼容规则不变：位姿只能连到位姿
- 调试运行时的摘要：`pose (213.4, 141.2) 旋转 3.5°`

这是这次**唯一改动共享内核**的地方。影响面：端口类型的解析和显示、值的摘要、JSON 仓储里端口类型的名字。已有的算子和方案不受影响。

## 6. 定位算子

只需要两个新算子。“分数太低判不合格”不用新算子：把分数接到已有的**范围判定**上。

### 6.1 `vision.template_match` 模板匹配

| | |
|---|---|
| 输入 | `image`（灰度） |
| 输出 | `pose`（位姿）、`score`（数值，0～1）、`found`（布尔） |
| 参数 | `template`（模板参数）、`angleRange`（搜索的角度范围 ±度，0 表示不旋转）、`minScore`（低于它算没找到） |
| ROI | 设置了就只在 ROI 里找 |

做法沿用 [OpenCV 教程第 9 课大作业](../tutorial/opencv/09-capstone-rotated-matching.md)：图像金字塔从粗到细；粗的一层上按角度步长搜索，细的一层上只在上一层的结果附近搜索；最后对位置和角度做亚像素插值。

**没找到不算出错**：`found` 为 false，位姿取基准位置，`score` 是找到的最好的分数。由后面的范围判定去判不合格（和卡尺测宽“量不到”的处理一致）。

### 6.2 `vision.align_to_pose` 按位姿对齐

| | |
|---|---|
| 输入 | `image`、`pose` |
| 输出 | `image`（零件回到了基准位置的图像，尺寸不变） |
| 参数 | `fill`（转进画面的空白处填什么灰度） |

之后的算子、ROI、卡尺都在对齐之后的图像上工作，**一行都不用改**。

### 6.3 一个典型的方案

```
image_input → to_gray ─┬→ template_match ─(pose)──┐
                       │        └─(score)→ judge_range「定位」
                       └──────────────────────────→ align_to_pose → caliper_width → judge_range「宽度」
```

零件没放好（分数低）→ “定位”这一条判不合格，操作员看得到原因。

## 7. 为什么先做“对齐图像”，而不是相对 ROI

原设计（P2、术语表）走的是**相对 ROI**：图像不动，ROI 跟着位姿走。这次先做**对齐图像**：ROI 不动，图像转回去。

| | 对齐图像（这次做） | 相对 ROI（以后做） |
|---|---|---|
| 对已有算子的影响 | 无 | 每个支持 ROI 的算子都要能处理旋转的 ROI |
| 对 ROI 设计的影响 | 无 | ROI 要支持旋转矩形；编辑器要支持在基准图上画、运行时换算 |
| 运行时的代价 | 整幅图像重采样一次（5MP 约几毫秒，待实测） | 只换算几个坐标 |
| 精度 | 重采样会让边缘轻微变模糊，对亚像素测量有影响（待实测） | 不动原图，没有这个损失 |
| 调试 | 中间结果是“转正的图”，一眼看得懂 | 要在原图上叠加旋转的框 |

对齐图像简单、马上能用，并且**不堵死以后的路**：相对 ROI 需要的位姿、模板、定位算子，这次都做了。以后加相对 ROI 时，P2 按原设计实现，`align_to_pose` 继续保留给不在乎那点精度的方案用。

要记下来的风险：对齐对测量精度的影响没有数据。实现时要测（§10）。

### 方案助手和模板

工作流是“一类任务的通用骨架”，而模板是“这个产品的”。带定位的工作流要能用，任务书必须同时给出模板（或者给出“在哪张图上框哪一块”）。这需要改任务书和工作流的格式，**这次不做**；定位算子先只在手工搭的方案里用。记为待办。

## 9. 存储

沿用 ADR-20 的内容寻址存储：

```
<数据目录>/content/sha256/9f/2c…      文件名就是内容的哈希
```

- 模板保存为 PNG（无损）。哈希对 PNG 文件的字节计算
- 同一幅模板被多个方案版本引用时只存一份
- 写入是幂等的：内容相同，文件就相同
- 读出来之后**校验哈希**：文件被改过或者损坏，加载失败并报错，而不是悄悄用一幅错的模板
- **不做垃圾回收**：删除模板只删引用，不删文件。已发布的方案版本可能还在用它。清理没人引用的内容是以后的事

## 10. 和分辨率的关系

模板和 ROI 一样，是按像素定义的：在 640×480 的相机上框的模板，换到 1280×960 的相机上找不到东西。这是 POC-1 报告里记下的那个老问题（ROI 和分辨率绑定），这次**不解决，但要能发现**：

- 模板记录了样图的尺寸
- 模板匹配时，如果图像的尺寸和样图不一样，**直接报错**并说明原因，而不是给出一个很低的分数让人去猜

## 14. 实施记录：步骤 ②（模板机制）

**做了什么**

| 部分 | 内容 |
|---|---|
| 共享内核 | 参数类型新增“模板”；`MatchTemplateData`（算子拿到手的模板：图像 + 基准位置 + 样图尺寸） |

| 适配器 | `adapters/content`：内容寻址的文件仓库（SHA-256）、模板的 PNG 编码和解码 |
| 命令行 | `recipe template add / rename / remove`；`recipe show` 列出模板 |

BC-4 上线管理和 BC-5 工位运行**没有改一行代码**：带模板的方案组装成上线包、部署到工位、后台加载、加载失败不影响生产，都直接成立（有测试）。这验证了 §2 的判断——模板属于方案版本，所以以“方案版本不可变”为前提的东西都不用动。

**实现时做的决定**

| # | 决定 | 理由 |
|---|---|---|
| 1 | SHA-256 自己实现（约 60 行），不引入加密库 | 不想为了识别内容给三个平台多加一个依赖。只用于识别内容，不用于安全用途。用标准文档的测试向量核对过，包括补位边界上的几个长度 |
| 2 | 创建模板时**先让聚合检查、再保存图像内容** | 被拒绝的创建（重名、出界、太小）不在内容仓库里留下任何东西 |
| 3 | 模板的 ID 是 `t1`、`t2`……删除之后可能被重新使用 | 已发布的方案版本有自己的快照，不受影响。和具名区域的做法一致 |
| 4 | 发布时**没有被任何节点引用的模板也一起进了方案版本** | 简单；多出来的只是一条引用。要不要在发布时去掉，留到做方案包（H-06）时一起考虑 |
| 5 | 执行计划的运行器在**创建时**拿到模板，而不是每次运行时 | 模板和算子实例一样，是“这个节点固定不变的部分” |
| 6 | 加载时除了校验哈希，还核对解码出来的尺寸和方案里记录的一致 | 多一道检查，几乎没有成本 |

**没有做的**

- 上线包文件（`ReleaseBundle`）还不存在，所以“把模板一起打包带到没有网络的产线电脑”还没有做。现在两个平台在同一个程序、同一个数据目录里
- 内容仓库没有垃圾回收（设计如此，§9）
- 模板只能从命令行创建；从 JSON 草稿文件（`recipe build`）还不能带模板

**测试**：全部 240 个测试通过，新增 24 个：方案编排领域层 8 个（R7、R8、P6、冻结；不链接 OpenCV）、共享内核 1 个、端到端 15 个（SHA-256 的标准测试向量、内容仓库、模板传到算子、版本冻结、内容只存一份、被拒绝的创建不留痕迹、重启之后还在、内容损坏或丢失时在加载阶段报错、旧格式的文档、随上线包部署到工位）。新代码在 AddressSanitizer + UBSan 下无报告。

端到端测试里用的是一个只在测试里存在的算子（检查“输入图像在基准位置上的那一块是不是和模板一模一样”），平台本身还没有任何使用模板的算子。

## 15. 实施记录：步骤 ③（位姿和定位算子）

实测数据、出问题时的行为、局限，都在 [poc/locating-report.md](../poc/locating-report.md)。这里只记和 v1.0 设计不一样的地方。

| # | 设计（v1.0） | 实现 | 原因 |
|---|---|---|---|
| 1 | 角度逆时针为正 | **顺时针为正** | v1.0 说“和教程大作业一致”，而教程用的是顺时针；那句话自相矛盾，是我没有核对。选了和教程一致的方向 |
| 2 | 位姿只有 x、y、角度 | 多了 `referenceX`、`referenceY` | 位姿自己带着基准点原来的位置，对齐算子只需要一个位姿输入，不用再接一次模板参数 |
| 3 | 三个算子（匹配、位姿判定、对齐） | 两个（匹配、对齐） | “得分太低判不合格”直接用已有的范围判定。v1.0 的正文里已经是这样，只是我在对话里说过三个 |

**§7 留下的问题有了答案**：对齐之后再用卡尺测量，误差在 0.15 像素以内（平均 0.04）。相对 ROI 不急。

**新暴露的问题**：模板匹配慢（5MP 上用大模板要 0.7 秒），见实测报告 §4。
