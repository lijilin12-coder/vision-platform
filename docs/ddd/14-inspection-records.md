# 14 检测记录的保存和查询

> 状态：已实现（2026-11-24）。属于 **BC-10 质量分析**，这是这个上下文的第一块。
> 术语见[术语表](02-glossary.md)：检测记录、上线包、判定依据、结果项。

## 1. 要解决什么

在这之前，工位检测了什么只留在内存里（最近 100 条）和日志里：程序一关就没了。
产线上出了问题，要能回答三个问题（NFR-06 可追溯）：

| 问题 | 靠记录里的什么 |
|---|---|
| 什么时候、哪个工位、哪一幅图像 | 时间、工位、帧的名字、图像的内容哈希 |
| 当时是用什么检测的 | 上线包、方案版本——由方案版本可以追到每一个参数、用的哪个模型 |
| 结果是什么、为什么 | 判定、判定依据、结果项（缺陷、测量值、位姿） |

## 2. 模型

`InspectionRecord`（`core/contexts/quality/domain`）是一个**不可变的值**：写下之后不再改。

不变量：

| 编号 | 内容 |
|---|---|
| Q1 | 记录只追加，不修改、不删除。这个类没有任何修改自己的方法；仓储只有 `append` |
| Q2 | 必须说得清是谁、什么时候、用什么检测的：工位、时间、上线包、方案版本都不能为空 |
| Q3 | 判定只能是 OK / NG / ERROR；判 NG 的记录至少有一条不合格的判定依据（和检测执行的 I4 一致） |

**记录的编号**：13 位的毫秒时间 + 6 位序号，例如 `1795521600000-000042`。
按字符串比大小就是按时间先后，所以“翻页”只要说“比这个编号更早的”。
时钟往回走的时候（系统对时）沿用上一条的时间、序号加一，编号不会倒退。
工位自己的“第几次检测”不能当编号：工位重建之后会重新计数。

**汇总**（`Summary`）：总数、OK / NG / ERROR 各多少、每种缺陷出现了多少个、良率。
良率 = OK ÷ (OK + NG)。ERROR 不算进去：它说明的是系统出了问题，不是产品的好坏。一次都没有的时候良率是“没有”，不是 0% 也不是 100%。

## 3. 工位怎么把检测交给质量分析

```
工位运行（BC-5）                       质量分析（BC-10）
StationService::inspect
   └─ InspectionObserver（端口）──→ RecordInspections（apps/common）──→ QualityService::record
```

- 工位只知道“有人想听”（`station::InspectionObserver`），质量分析只知道“有一次检测要记”（`InspectionToRecord`）。两个上下文互不认识，翻译在组装根里做。
- 只有**产线检测**会被记下来。调试运行、试运行不经过工位，不留记录。
- 记录写不下来（磁盘满了）**不让检测失败**：产线照常跑，日志里留一条警告。图像存不下来同理：记录照样写，只是没有图像。

**为什么不用领域事件**（上下文映射图里写的是“BC-3 → BC-10：领域事件 `检测已完成`”）：
那个事件是检测执行发的，它不知道工位、上线包、第几次检测，也不带图像。
要记的这些东西只有工位在检测结束的那一刻全都有，所以由工位来交。04 文档已经照此改了（§7）。

## 4. 留不留图像

一条记录几百字节，一幅图像几百 KB，不能都永远留着。

最初的办法是只留不合格的和出错的，判 OK 的一幅都不留——于是漏检的那张图事后找不回来（场景走查里的 F-3）。
2026-11-25 改成了[短期图像缓存](18-image-cache.md)：不合格的、出错的长期保留；判 OK 的先留 72 小时，过期自动清掉；复判过的转成长期保留。

## 5. 存在哪里

```
<数据目录>/inspection-records/<工位 ID>/2026-11-24.jsonl     一行一条记录（JSON），只往后追加
```

- **为什么不是一条记录一个文件**：一个工位一天可能有几万次检测。
- **为什么不是数据库**：现在的查询只有“某个工位最近的若干条”“只看某种判定”，按天分文件足够；也不用为它多一个依赖。等要做跨工位、按批次、按缺陷种类的统计时再换，仓储接口（`InspectionRecordRepository`）不用变。
- **断电**：写到一半断电，最后一行是残缺的。读的时候跳过这一行，别的不受影响；下一次追加之前先补一个换行，不让新的一条接在半行后面。
- 日期按 UTC 分。界面上显示的时间也是 UTC（标明了）。
- 汇总：第一次问到时把这个工位的记录全部读一遍，之后每记一条就累加——界面会反复来问，不能每次都重读。

## 6. 怎么查

| 方式 | |
|---|---|
| HTTP | `GET /api/stations/{id}/records?verdict=NG&before=<编号>&limit=50`、`GET /api/stations/{id}/summary`；图像用已有的 `GET /api/images/{imageId}` |
| 命令行 | `station records <工位ID> [--ng] [--limit N]`、`station summary <工位ID>`（`vision-cli` 和 `vision-line` 都有；`vision-line serve` 运行着的时候也能直接用） |
| 界面 | 工位页面的“历史记录”：累计次数和良率、只看不合格、点一条看当时的图像和缺陷框、往前翻 |

## 7. 定下来的决定（2026-11-25 确认）

1. 工位通过端口把检测交给质量分析，不用领域事件（§3）。上下文映射图（04）已经照此改了。
2. ~~判 OK 的不留图像~~ 后来改成了短期图像缓存（§4）。
3. 记录永远不删。清理策略（留多少天）以后再做——一天 5 万次检测大约 25 MB 的记录，加上不合格的图像。
4. 时间一律 UTC。
