## 使用规则

1. **一个概念一个词，一个词一个概念。** 表中“不要说”一列列出了禁止使用的近义词。
2. **代码直接用“代码名”**：类名、函数名、变量名、JSON 字段都以此为准。
3. 发现新概念或歧义，**先改这张表，再改代码**。
4. 第 4 步划分限界上下文后，同一个词在不同上下文里的模型差异会在这里注明。

## 1. 角色

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 方案开发者 | `RecipeDesigner` | 搭建、调试、发布方案的人 | 工程师、配置人员 |
| 操作员 | `LineOperator` | 在产线上启动工位、查看结果、复判的人 | ⚠️ 代码中**不能**用 `Operator`（已被“算子”占用，见 §9 Q-1） |
| 算子开发者 | `OperatorDeveloper` | 编写新算子的人 | 算法工程师 |

## 2. 算子

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 算子 | `Operator` | 一种算法能力，有固定的输入输出端口和参数定义。算子库中每种算子只有一个 | 工具、模块、插件、函数 |
| 算子 ID | `OperatorId` | 算子的全局唯一标识，如 `vision.threshold` | |
| 算子元数据 | `OperatorMeta` | 算子的名称、分类、端口定义、参数定义 | |
| 端口 | `Port` | 算子的输入或输出接口，有确定的端口类型 | 引脚、插槽 |
| 端口类型 | `PortType` | 端口传递的数据类型：图像、区域、Blob 列表、位姿、测量值、数值、布尔…… | |
| 参数定义 | `ParamDef` | 一个参数的名称、类型、默认值、取值范围 | |
| 脚本算子 | `ScriptOperator` | 用脚本编写、不需要重新安装程序就能加入的算子 | 动态算子 |

## 3. 方案编排

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 方案 | `Recipe` | 一套完整的检测配置：节点、连线、参数、ROI、模型依赖等 | 流程、工程、作业、配方、项目；⚠️ 也不要说“工作流”（它专指方案助手里的可复用骨架，见 §10） |
| 方案草稿 | `RecipeDraft` | 正在编辑的方案，允许不完整 | |
| 方案版本 | `RecipeVersion` | 方案发布后形成的**不可修改**的快照 | |
| 节点 | `Node` | 方案中对某个算子的一次使用，有自己的参数 | 步骤、算子实例、工具块 |
| 连线 | `Edge` | 从一个节点的输出端口连到另一个节点的输入端口 | 连接、链接 |
| 参数值 | `ParamValue` | 某个节点上某个参数的取值 | |
| ROI | `Roi` | **人为指定**的检测范围（矩形、旋转矩形、圆），是输入 | 区域、框、检测区 |
| 相对 ROI | `RelativeRoi` | 相对于定位基准定义的 ROI，运行时根据位姿换算成实际位置 | 跟随框 |
| 具名区域 | `NamedRegion` | 有名字、可被多个节点按 ID 引用的 ROI 定义 | 公共区域、全局 ROI |
| 区域 | `Region` | **算法计算出**的像素集合，比如阈值分割的结果，是输出 | ⚠️ 不能用来指 ROI |
| 位姿 | `Pose` | 平移 + 旋转（+ 缩放），由定位算子输出，作为相对 ROI 的基准 | 坐标系、偏移 |
| 匹配模板 | `MatchTemplate` | 从样图上框选、用于定位的模板 | 模板图 |
| 模型依赖 | `ModelDependency` | 方案中某个节点声明需要的模型：模型 ID + 兼容范围 | 模型引用 |
| 兼容范围 | `CompatibleRange` | 可以被接受的模型版本范围；**主版本号相同**即模型契约相同，视为兼容 | |
| 调试运行 | `DebugRun` | 编辑时运行方案，缓存每个节点的中间结果，用于查看和调参 | 试运行、测试运行 |

## 4. 标定

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 标定 | `Calibration` | 建立像素与真实尺寸（毫米）之间换算关系的过程 | ⚠️ **不能**说“校准”（已被量化占用，见 §7） |
| 标定档案 | `CalibrationProfile` | 某个**工位相机**的标定结果：换算比例、畸变参数等。**属于工位，不属于方案**（D4-1）；有版本，检测时记录所用的标定档案；有**有效期**，过期视为无效（F-7） | 标定文件 |
| 标定需求 | `CalibrationRequirement` | 方案声明的“需要标定、单位为毫米”。部署时据此检查工位相机是否有有效标定 | |

## 5. 上线包与部署

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 上线包 | `Release` | 锁定了**方案版本 + 每个模型依赖的具体模型版本**的组合；是一致性验证、热更新、回滚的最小单位 | 发布包、部署包（见 §9 Q-2） |
| 已撤回 | `Withdrawn` | 上线包的状态：确认有问题、不允许再部署；不可撤销（F-5） | 作废、禁用 |
| 上线包文件 | `ReleaseBundle` | 上线包导出成的文件，包含上线包、方案版本、模型版本元数据和指定平台的模型制品，用于**带到产线部署**（F-2）。区别于方案包（用于带走继续编辑） | 部署包 |
| 验收检查 | `AcceptanceCheck` | 在基准平台上用基准图集运行上线包，和**人工确认的真实判定**比较，回答“判得对不对”；同时生成基准输出（F-1） | 回归测试 |
| 验收标准 | `AcceptanceCriteria` | 用户为基准图集设定的验收要求，如“漏检 0 张、误报率 ≤ 2%” | |
| 跨平台一致性检查 | `ConsistencyCheck` | 在目标平台上运行上线包，和**基准平台上同一个上线包的基准输出**比较，回答“各平台结果是否一致”（F-1） | 一致性验证、兼容性测试 |
| 基准平台 | `referencePlatform` | 上线包指定的、作为一致性比较基准的平台，通常是创建上线包的平台 | 参考平台 |
| 基准输出 | `ReferenceOutputs` | 上线包在基准平台上对基准图集的完整输出，由验收检查自动生成 | 期望结果 |
| 真实判定 | `groundTruth` | 基准图集中每个用例由人确认的正确判定（OK / NG，可选缺陷类别），长期有效，与上线包无关 | 标准答案、期望结果 |
| 基准图集 | `GoldenSet` | 带有**真实判定**的一组图像，以及验收标准和一致性标准；用于验收检查和跨平台一致性检查。**不保存期望输出** | 测试集（容易和数据集混淆） |
| 一致性标准 | `ConsistencyCriteria` | 方案开发者为基准图集设定的“多大差异算一致”的规则：判定、测量值、缺陷、位姿各自的容差。平台只提供默认值 | 容差配置、阈值 |
| 部署 | `Deploy` | 把上线包交给某个工位，进入“待切换”状态 | 下发、推送、安装 |
| 方案包 | `RecipePackage` | 可以在平台之间传递的自包含单元：方案版本 + 依赖声明 + 附带资源 + 清单 | 导出文件、方案文件 |
| 目标平台 | `TargetPlatform` | 鸿蒙电脑、Windows、Linux 之一 | 系统、环境 |

## 6. 产线运行

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 工位 | `Station` | 一个独立的检测运行单元，绑定一个图像源，有自己生效的上线包。一台电脑可以有多个工位 | 产线、通道、相机（见 §9 Q-3） |
| 生效上线包 | `activeRelease` | 工位当前用于新检测的上线包 | 当前版本 |
| 待切换上线包 | `pendingRelease` | 已部署、已加载、等待在下一次检测前切换的上线包 | |
| 图像源 | `ImageSource` | 工位获取图像的来源：相机、文件夹…… | 输入、采集卡 |
| 检测 | `Inspection` | 用工位生效的上线包，对**一次触发得到的图像**（一张或多张，见 H-11）执行一次完整的运行。**包括缺陷检测、尺寸测量、定位等所有任务类型**；单独说“检测”时只指这个概念 | 运行、任务、作业、执行 |
| 检测结果 | `InspectionResult` | 一次检测的全部产出：缺陷列表、测量值列表、位姿列表，以及判定和判定依据。**结果项按类型区分**（缺陷、测量值、位姿是不同的值对象），检测本身不按任务类型区分 | 输出、结果数据 |
| 缺陷检测 | — | 找缺陷这一**类算法或任务**的统称，由若干节点完成。⚠️ 不能简称“检测” | 检测（单独使用时） |
| 尺寸测量 | — | 测量尺寸这一**类算法或任务**的统称，由若干节点完成；测量值超出公差会导致判 NG | 测量检测 |
| 节点执行 | `NodeExecution` | 一次检测中某个节点的执行记录：状态、耗时、输出 | |
| 判定 | `Verdict` | 一次检测的最终结论：**OK / NG / ERROR**。NG 可能来自缺陷，也可能来自测量值超差 | 结果（太宽泛） |
| 判定依据 | `VerdictReason` | 单个结果项（缺陷、测量值、位姿……）对判定的贡献：合格或不合格，加上原因说明，如“孔径 A 超差 +0.03 mm”。判定由所有判定依据汇总而来 | 原因、错误信息 |
| 缺陷 | `Defect` | 检测中发现的一个具体问题：类别、位置、大小、置信度 | 瑕疵、不良 |
| 测量项 | `MeasurementItem` | 方案中定义的“要测什么”：名称（如“孔径 A”）、单位、标称值、公差。不同检测中的同一个测量项可以放在一起做趋势统计 | 测量点、尺寸项 |
| 测量值 | `Measurement` | 某次检测中某个测量项的实际测得值，带单位，能根据公差判断是否合格 | 尺寸、读数 |
| 公差 | `Tolerance` | 测量值的标称值和允许偏差 | |
| 节拍 | `CycleTime` | 工位允许一次检测花费的最长时间 | 周期 |
| 复判 | `Review` | 操作员人工确认系统的判定是否正确 | 复检、人工检 |
| 误报 | `FalseReject` | 系统判 NG，实际是良品 | 过杀、误杀 |
| 漏检 | `FalseAccept` | 系统判 OK，实际有缺陷 | 漏杀 |
| 批次 | `Batch` | 一组连续的检测，完成后生成统计报告 | 批量、一批 |

## 7. 数据与模型

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 采集策略 | `CapturePolicy` | 决定检测后哪些图像要保存的规则，例如 NG 全存、OK 抽样 5% | 存图规则 |
| 图像缓存 | `ImageCache` | 所有检测图像的短期保存区，保留期由用户设定（默认 72 小时），用于事后复判找回图像，尤其是漏检（F-3） | 临时目录 |
| 样本 | `Sample` | 保存下来、可加入数据集的一张图像及其来源信息（哪个工位、哪次检测、判定结果） | 图片（太宽泛） |
| 数据集 | `Dataset` | 用于训练或评估的样本集合，可以修改 | 图库 |
| 数据集版本 | `DatasetVersion` | 数据集冻结后的不可修改快照；可以追溯模型用了哪份数据 | |
| 标注 | `Annotation` | 样本上的人工标记：分类标签、检测框或分割掩码 | 标签（标签只是标注的一种） |
| 模型 | `Model` | 一个逻辑上的模型，如 `scratch-detector`，有多个版本 | 网络、权重 |
| 模型版本 | `ModelVersion` | 模型的一个具体版本，如 `v2.3`；发布后不可修改 | |
| 模型契约 | `ModelContract` | 模型的输入输出规格（形状、类型、预处理方式、输出含义）；**契约变化 = 主版本号变化** | 接口 |
| 模型制品 | `ModelArtifact` | 某个模型版本在某个平台格式下的具体文件（`.onnx`、`.ms`） | 模型文件 |
| 量化 | `Quantization` | 把模型从 FP32 转成 FP16 或 INT8，换取速度 | 压缩 |
| 量化校准集 | `QuantCalibrationSet` | INT8 量化时用来统计数值分布的一组样本 | ⚠️ 不能简称“校准”或“标定” |
| 转换 | `Conversion` | 把模型版本转换成某个目标平台格式的模型制品 | 编译、导出 |
| 模型验证 | `ModelValidation` | 检查模型制品的精度是否达标、各平台输出是否一致 | |

## 8. 热启动与热更新

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 热启动 | `WarmStart` | 工位启动时恢复上次生效的上线包，并预热模型，马上可以检测 | 自动恢复 |
| 预热 | `Warmup` | 启动后先空跑几次推理，避免第一次检测过慢 | |
| 热切换 | `HotSwap` | 在两次检测之间把待切换上线包变为生效上线包，不打断正在进行的检测 | 热更新（见下） |
| 热更新 | — | **用户视角的统称**：部署 + 热切换的整个过程。代码中不单独建模 | |

| 质量偏离告警 | `QualityDeviationAlert` | 热切换后的观察窗口内，NG 率相对切换前的偏离超过用户设定的阈值时发出的告警；**只告警，不自动回滚**（F-4） | 质量报警 |
| 影子运行 | `ShadowRun` | 新上线包在后台并行运行，但不影响判定，用于对比新旧版本 | 灰度、试运行 |

## 10. 方案助手

| 术语 | 代码名 | 定义 | 不要说 |
|---|---|---|---|
| 方案助手 | `RecipeAssistant` | 按工作流搭出方案，并自动调参、测试、迭代的功能 | AI、机器人 |
| 检测任务书 | `InspectionBrief` | 用户交给助手的输入：检测目标的文字描述、基准图集、留出集、验收标准、约束（节拍、允许的算子、工作方式、数据外发策略） | 需求、提示词 |
| 助手会话 | `AssistSession` | 助手针对一份任务书的一次完整工作过程，包含所有轮次的记录 | 对话、任务 |
| 方案顾问 | `RecipeAdvisor` | 回答“选哪个工作流”“下一步建议怎么改”的角色。大模型是它的一种实现 | 大模型、AI（在领域层里）；⚠️ 不叫“推理引擎”（“推理”专指模型推理） |
| 工作流 | `Workflow` | 针对**一类**检测任务的、可复用的方案骨架：固定的节点和连线，声明可调项及其范围、初始值、要做的稳健性检查。助手按工作流创建候选方案，再由顾问调参。**工作流不是方案**：方案是针对某一个具体产品配好参数、可以发布的检测配置 | 套路、模板（专指模板匹配里的模板图像）；不要用它指方案或助手的循环 |
| 可调项 | `Tunable` | 工作流里声明为可以由顾问修改的一个参数或 ROI，带取值范围 | |
| 工作流内调参 | `tuneWithinWorkflow` | 助手默认的工作方式：结构来自工作流，顾问只修改可调项 | |
| 自由搭建 | `freeform` | 顾问可以修改方案结构的工作方式（以后再做） | |
| 提议 | `Proposal` | 顾问给出的一组对候选方案的修改和理由 | 回答、输出 |
| 候选方案 | `CandidateDraft` | 会话期间助手正在修改的方案草稿副本；被采纳之前不影响用户的草稿 | |
| 实验 | `Experiment` | 把候选方案在调参集上实际运行一遍 | 测试、试跑 |
| 评估 | `Evaluation` | 一次实验的结果：误报数、漏检数、每张图的判定和判定依据、各节点耗时 | 分数 |
| 调参集 | `tuningCases` | 基准图集中顾问可以看到、用来迭代的用例 | 训练集 |
| 留出集 | `holdoutCases` | 基准图集中顾问**看不到**的用例，只在会话结束时评估一次 | 测试集 |
| 稳健性检查 | `RobustnessProbe` | 对图像做已知的扰动（亮度、噪声、小的平移和旋转）之后重新评估，看结果是否稳定 | 压力测试 |
| 助手报告 | `AssistReport` | 会话结束时的产出：调参集、留出集、稳健性检查上的表现，试过的做法，已知的局限 | |
| 采纳 | `adopt` | **人**决定用候选方案替换自己的方案草稿 | 发布（采纳不是发布） |
| 数据外发策略 | `DataSharingPolicy` | 任务书里规定可以交给顾问的内容：不外发图像（默认）、外发缩略图、外发原图 | |

|---|---|---|---|
| Q-7 | 方案助手里“固定结构的方案骨架”叫什么？ | **工作流**（`Workflow`）。初稿叫“套路”。取这个名字是因为它和业界的用法一致：工作流是预先定好的路径，由大模型在其中调参；与之相对的是由大模型自己决定结构的“自由搭建”。为避免混淆：方案不叫工作流，助手的“提议 → 实验 → 评估”过程叫“循环”，也不叫工作流 | 2026-11-13 |
| Q-4 | “过杀 / 漏杀”还是“误报 / 漏检”？ | **误报 / 漏检** | 2026-11-12 |
| Q-1 | “算子”和“操作员”英文都是 Operator | 算子 `Operator`，操作员 `LineOperator` | 2026-11-12 |
| Q-2 | “上线包”还是“发布包”？ | **上线包**。“发布”专用于方案版本和模型版本；把上线包交给工位叫“部署” | 2026-11-12 |
