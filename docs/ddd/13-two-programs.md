## 1. 之前和现在

之前只有一个命令行程序 `vision-cli`，什么都能做：搭方案、训练、部署、运行工位，全在一个数据目录上。
“两个平台”只是文档里的说法。

现在是三个程序，分属两个平台：

| 平台 | 程序 | 能做什么 |
|---|---|---|
| **方案构建平台** | `vision-cli`（命令行）、`vision-runtime`（HTTP 服务） | 全部：搭方案、调试、方案助手、数据集、训练、模型仓库、导出方案包；也能做产线那一侧的事（方便在一台机器上试） |
| **产线运行平台** | `vision-line` | 只有：导入方案包、上线包、工位、让工位持续运行 |

产线上的电脑只装 `vision-line`。它**没有**方案编排：在那台机器上改不了方案，也调试不了。方案和模型只有一个来路——方案包。

```bash
# 方案构建平台
vision-cli package export <方案版本ID> 表面检测.vpkg

# 产线运行平台
vision-line package import 表面检测.vpkg
vision-line release create <方案版本ID>
vision-line station create 一号工位
vision-line station deploy <工位ID> <上线包ID>
vision-line station bind <工位ID> folder ./来料图像
vision-line serve
```

## 2. 代码里是怎么分的

组装（把适配器和应用服务连起来的那段代码）分成两层：

```
apps/common/line_platform.h    LinePlatform：检测执行、上线管理、工位、模型仓库、方案包、图像源、推理引擎
apps/common/platform.h         Platform : LinePlatform   再加：方案编排、基准图集、方案助手、数据、训练
```

`vision-line` 只构造 `LinePlatform`；`vision-cli` 和 `vision-runtime` 构造 `Platform`。

**方案版本从哪里来**是两个平台唯一的行为差别，落在一个地方（`RecipeSources`）：
产线运行平台只有“从方案包导入的”；方案构建平台在它前面再接上“本机方案编排发布的”。

命令也分了：上线包、工位、方案包这几组命令搬到了 `apps/common/line_commands.cpp`，两个命令行程序共用同一份代码。

有一条编译期的检查（`tests/line_platform_test.cpp` 里的 `static_assert`）：`LinePlatform` 里不能有方案编排、训练、数据这些成员。谁加进去，编译不过。

## 3. 工位怎么“自己一直运行”

`vision-line serve` 让工位持续运行：每个工位一个线程，从自己的图像源取图、检测；图像源暂时没有新图像时歇 0.1 秒再问；按 Ctrl+C 停止。

**循环放在程序里，不放在工位服务里。** 工位服务（应用层）仍然只提供“取下一帧并检测”这一步。
什么时候取下一帧、几个工位怎么排线程，是“驱动”它的那个程序的事——现在是简单的循环，以后换成定时、外部触发信号，都不用动应用层。

每次检测输出一行；不合格时带上原因。停止时每个工位给一个合计。

## 4. 运行期间怎么部署：控制接口和转发

这里有一个容易想错的地方，我一开始也写错了：

> 服务在一个终端里运行着，另开一个终端执行 `vision-line station deploy`，热切换会发生吗？

**不会。** 另一个终端是另一个进程。工位的状态（生效的是哪个上线包、加载好了没有）在正在运行的那个进程的内存里；
新进程只能改磁盘上的文件，运行中的工位看不到。更糟的是两个进程会各写各的，把工位的文件写乱。

所以运行期间对工位的操作，必须交给正在运行的那个进程去做：

1. `serve` 启动时在本机的一个端口上开一个**控制接口**（HTTP，默认 8760，只接受本机的连接），并在数据目录里留一个记号文件，写着端口
2. 别的 `vision-line station ...` 命令开始前先看：记号文件在、而且那个端口上确实有服务在应答 → 服务正在运行
3. 正在运行时，`station list / show / deploy / rollback` **自动转发**给它；其他对工位的操作（创建、绑定图像源、`run`）被拒绝，提示先停服务

对使用的人来说，命令和平时一样：

```bash
vision-line package import 新版.vpkg        # 这两条不涉及工位的内存状态，照常在本进程里做
vision-line release create <方案版本ID>
vision-line station deploy <工位ID> <上线包ID>   # 自动交给正在运行的服务；下一次检测开始前热切换
vision-line station rollback <工位ID>           # 不行就回滚
```

程序崩溃留下的旧记号文件不算数：端口上没有服务应答，就当作没有在运行，并把旧文件清掉。

控制接口：

| 请求 | 作用 |
|---|---|
| `GET /api/health` | |
| `GET /api/stations`、`GET /api/stations/{id}` | 工位的当前状态 |
| `POST /api/stations/{id}/deploy` | `{"releaseId": "…"}` |
| `POST /api/stations/{id}/rollback` | `{"withdraw": false}` |

## 5. 实现时做的决定（请确认）

| 决定 | 原因 | 代价 |
|---|---|---|
| 方案构建平台的程序**也能**做产线那一侧的事（上线包、工位） | 一台机器上就能把整个流程试一遍；测试也方便 | 两个平台不是“互不重叠”的。产线上只装 `vision-line` 才有“这台机器改不了方案”的保证 |
| 产线运行平台**不能**导出方案包 | 方案包是在构建那一侧做的；产线机不应该成为方案的来源 | 想把产线机上的方案拷到另一台产线机，要回到构建机重新导出，或者直接拷原来的包文件 |
| 循环在程序里，不在工位服务里（§3） | 触发方式以后会变 | `vision-cli` 没有 `serve`；想持续运行必须用 `vision-line` |
| 运行期间只转发 list / show / deploy / rollback | 这四个是产线上运行时真正需要的 | 运行期间不能新建工位、换图像源：要先停服务。换图像源本来就要求工位停止（S7） |
| 控制接口没有登录，只监听本机 | 用户与权限管理在范围外 | 同一台机器上的任何程序都能让工位换上线包。产线电脑通常是专用的；接入网络之前必须加权限 |
| **“分开”只做到了组装这一层** | 最小的改动 | 适配器库还是共用的：`vision-line` 的可执行文件里仍然链接了一部分和训练、数据有关的适配器代码（没有被用到）。要彻底分开，得把 `adapters/content`、`adapters/persistence` 按平台拆开——留到真的需要给产线机做一个小的安装包时再做 |

- 相机
- 产线运行平台的完整 HTTP 接口（给界面用的）：现在只有控制工位的那几个

## 7. 测试

全部 351 个测试通过。本步新增 4 个（`tests/line_platform_test.cpp`）：

- 产线运行平台只认方案包带来的方案版本
- `serve`：取完现有图像、空闲后结束；坏的图像不算检测；没有可运行的工位时说明原因
- **运行期间通过控制接口热切换和回滚**：部署后不立即切换，下一幅图像到来、检测开始前才切换（S3）
- 转发：靠记号文件找到正在运行的服务；旧的记号文件被清掉；不能转发的操作返回“不支持”

在 ThreadSanitizer（三遍）和 AddressSanitizer 下干净。自动构建（Windows）里的端到端检查改成了真的用两个程序：`vision-cli` 导出，`vision-line` 导入、上线、`serve`。
