## 愿景

**为谁**：需要做外观检测和尺寸测量的团队：搭方案的工程师、现场操作员、扩展算法的算子开发者。

**解决什么问题**：每个检测场景都要单独写代码，开发慢、修改难，常常被绑定在某一个平台上；产线一停机就有损失，模型迭代又慢又麻烦。即使用上了拖拽式的工具，**搭出一个稳健的方案仍然需要很多视觉经验**：选什么方法、参数怎么调、怎样测试才算够。

**怎么解决**：
- **方案助手**：用户给出样本图像和验收标准，助手自动搭建方案、在图像上实际测试、根据结果迭代，交出一个人能看懂、能修改、能审核的方案和一份测试报告。助手是副驾驶：它不能发布，也不进入产线运行时。
- **可编排**：算法做成可以自由组合的算子，用拖拽的方式搭出检测方案。这是方案助手的基础：助手搭出来的就是普通的方案。
- **跨平台**：方案与平台无关，在任何支持的平台上（以鸿蒙电脑为主，其次是 Windows）都能编辑和运行，结果一致。
- **数据闭环**：从产线采图、整理数据集、标注，到导出给外部训练。
- **模型工具链**：导入训练好的模型，进行量化、转换、验证，然后发布。
- **不停机**：热启动；方案和模型热更新，可以随时回滚。

**范围外**：模型训练（由外部完成，平台只负责导出数据、导入模型）。

**靠什么赢**：① 方案助手：把视觉经验变成可以自动执行、自动验证的过程（建立在可编排之上）② 跨平台 ③ 数据到模型的闭环 ④ 不停机迭代。

> 2026-11-13 修订（草案）：原来的第 ① 条是“低门槛编排”。拖拽式编排同类软件都有，降低的是写代码的门槛，没有降低懂视觉的门槛，不足以构成差异。

## 平台定位

| 角色 | 平台 | 说明 |
|---|---|---|
| 主要部署平台 | **鸿蒙电脑** | 产品的目标平台，也是比赛的重点 |
| 第二部署平台 | Windows | 既是开发机也是工厂里最常见的工控机系统，开发时顺带保证可用 |
| 保持可编译 | Linux | 不单独投入，由自动构建保证；模型工具链本身运行在 Linux 上 |
| 开发机 | **macOS 和 Windows** | 两者地位相同，都必须能编译并通过全部测试。依赖 Linux 的工具（鸿蒙版 OpenCV 交叉编译、模型转换）在 Mac 上用 Docker，在 Windows 上用 WSL2 |
| 模型工具链 | 独立的 Linux 服务（Docker） | 可以部署在任何地方 |

> 2026-11-12 修订：开发机从“只有 Mac”改为“Mac 和 Windows”；部署以鸿蒙电脑为主。每次推送由 GitHub Actions 在 Windows 和 Linux 上自动编译和测试；Mac 上的构建由日常开发保证。

## 由愿景得出的设计约束

1. **方案中不能出现平台相关的信息**：模型用逻辑 ID 引用（如 `scratch-detector@v2`），由各平台在运行时找到对应格式的文件；不写绝对路径。
2. **“结果一致”是一条业务规则**，需要能定义、能验证（容差、验证方式在战术设计中确定）。
3. **热更新不能打断正在进行的检测**；任何更新都必须可以回滚。
4. **方案助手不能有特权**：它只能通过和人相同的命令编辑草稿、通过相同的检测引擎运行、用相同的标准评估；不能发布；产线运行时不依赖它，也不依赖大模型。
5. **大模型只是一种可替换的实现**：领域层只定义“方案顾问”这个抽象，具体用哪种大模型、部署在哪里，由适配器决定。
