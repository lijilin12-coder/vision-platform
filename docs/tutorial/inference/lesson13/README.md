先说明这一课的边界。FlashAttention 是一个为 GPU 设计的算子实现。它的**数学部分**（分块和在线 softmax）可以在 CPU 上原样实现并验证，这一课会完整地做。它的**性能部分**取决于 GPU 的存储层次，需要 NVIDIA 显卡才能实测，这一课只讲基本概念，并指给你继续学习的入口，不给出任何我们没有测过的性能数字。

## 1. 标准写法：三个矩阵运算

在 PyTorch 这类框架里，注意力最直接的写法是三步，每一步是一个对整个矩阵的运算：

```
S = Q · Kᵀ / √d          N × N    每个位置对每个位置的打分（再把掩码挡住的位置设成 -∞）
P = softmax(S)           N × N    每一行变成权重
O = P · V                N × d    按权重加权求和
```

[`attention.h`](attention.h) 里的 `attentionStandard` 照这三步写：先算出完整的 S，再整体做 softmax，再乘 V。

问题在中间那两个 N × N 的矩阵。Q、K、V 和最后的结果都是 N × d，d 是几十到一百多；而 N 是序列长度，可以是几千到几万。临时矩阵的大小是 N²：

| 序列长度 N | S 的大小（32 位浮点，一个头） |
|---|---|
| 1024 | 4 MB |
| 2048 | 16 MB |
| 32768 | 4096 MB |

（N × N × 4 字节。最后一行：32768² × 4 = 4 294 967 296 字节。）

这是**一个头、一层**的量，只是临时用一下，算完就扔。但它比真正的输入输出大得多，而且要被完整地写一遍、读两遍。

## 2. 在线 softmax

想不保存整张表，要解决的是 softmax。它看起来必须先拿到一整行的打分：既要知道最大值（为了数值稳定），又要知道总和（为了归一化）。

### 为什么要减最大值

softmax 的定义是 exp(s_j) 除以所有 exp(s_j) 的和。打分稍大一点，exp 就溢出：

```
打分是 100、99、98 时：不减最大值算出来不是一个数（NaN），减最大值算出来是 1.4248
```

32 位浮点数里 exp(100) 是无穷大，无穷大除以无穷大得到 NaN。标准的做法是先都减去最大值 m：exp(s_j − m) 最大是 1，不会溢出；分子分母同时除了 exp(m)，结果不变。

### 一块一块地看

我们最终要的不是权重本身，而是加权和 O = Σ p_j · v_j。把它展开：

```
       Σ exp(s_j − m) · v_j        o
O  =  ──────────────────────  =  ─────
         Σ exp(s_j − m)            l
```

分子记作 o，分母记作 l。两者都是“逐项累加”的形式，可以看一个加一个，唯一的麻烦是 m 要等看完全部打分才知道。

办法是：**先用“到目前为止的最大值”来算，最大值变大的时候再把已经累加的部分换算过去。** 假设已经看过一些打分，当时的最大值是 m旧，累加得到了 l旧 和 o旧。现在新来一块打分，其中有更大的，最大值变成 m新。旧的累加值里每一项都是 exp(s_j − m旧)，而现在需要的是 exp(s_j − m新)。两者的关系是：

```
exp(s_j − m新) = exp(s_j − m旧) · exp(m旧 − m新)
```

每一项都乘同一个系数 exp(m旧 − m新)，所以把 l旧 和 o旧 整体乘上这个系数就换算好了。然后把新的一块按 m新 累加进去。完整的更新规则：

```
m新 = max(m旧, 新来这一块里的最大打分)
l新 = l旧 · exp(m旧 − m新) + Σ(新来的) exp(s_j − m新)
o新 = o旧 · exp(m旧 − m新) + Σ(新来的) exp(s_j − m新) · v_j
```

全部看完之后，o / l 就是结果。**需要记住的只有 m、l、o 三个量，和已经看过多少个打分无关。**

这就是在线 softmax。[`online_softmax.cpp`](online_softmax.cpp) 里是它的实现：

```cpp
void addBlock(const float* scores, const float* values, int count) {
    float mNew = m;
    for (int j = 0; j < count; ++j) mNew = std::max(mNew, scores[j]);
    const float rescale = std::exp(m - mNew);   // 第一块时 m = -∞，rescale = 0，而 l、o 本来就是 0
    l *= rescale;
    o *= rescale;
    for (int j = 0; j < count; ++j) {
        const float w = std::exp(scores[j] - mNew);
        l += w;
        o += w * values[j];
    }
    m = mNew;
}
```

### 验证

推导出来的公式要用代码检查。1000 个随机打分，分成不同大小的块，和“拿到全部打分再算”的标准做法比较：

```
1000 个打分，标准做法的结果：0.043652

在线做法，每块的大小不同：
  每块    1 个：0.043652，和标准做法相差 3.35e-08
  每块    7 个：0.043652，和标准做法相差 5.22e-08
  每块   64 个：0.043652，和标准做法相差 4.84e-08
  每块 1000 个：0.043652，和标准做法相差 3.35e-08

最大的打分出现在最后一块（每块 2 个）：
  看完第 0 块：m =   2.0，l = 1.3679，o = 2.3679，当前结果 o/l = 1.7311
  看完第 1 块：m =   3.0，l = 1.5853，o = 5.1173，当前结果 o/l = 3.2280
  看完第 2 块：m =  50.0，l = 1.3679，o = 7.2073，当前结果 o/l = 5.2689
  标准做法：5.2689
```

- 不管块多大，结果都和标准做法一致，差别在 10⁻⁸ 的量级。这是浮点数加法顺序不同造成的舍入误差，不是算法的误差。**这一点和 KV Cache 不同**：那里是逐位相同，这里是“在浮点精度内相同”，所以检查时要给一个合理的容许范围。
- 第二个例子里，最大的打分 50 在最后才出现。看完第 2 块时，前两块累加的结果被乘上了 exp(3 − 50)，几乎变成 0，最终结果几乎完全由最后一块决定。这和标准做法得到的一样。

## 3. 分块计算注意力

有了在线 softmax，注意力就可以分块算。把 N 个查询（行）每 `blockQ` 个分成一组，N 个键（列）每 `blockK` 个分成一组。N × N 的打分表被切成很多小块，**一次只算一小块，用完就覆盖**：

```
               键（列），每块 blockK 个
             ┌────┬────┬────┬────┐
  查询       │ 1  │ ×  │ ×  │ ×  │   × ：整块都被因果掩码挡住，直接跳过
 （行）      ├────┼────┼────┼────┤
  每块       │ 2  │ 3  │ ×  │ ×  │   数字：计算的先后顺序
  blockQ 个  ├────┼────┼────┼────┤
             │ 4  │ 5  │ 6  │ ×  │   对角线上的块：块内部还有一半被挡住，逐个判断
             ├────┼────┼────┼────┤
             │ 7  │ 8  │ 9  │ 10 │
             └────┴────┴────┴────┘
```

对每一组查询：从左到右扫过各个键块；每个查询各自维护自己的 m 和 l；o 直接累加在输出的那一行上。扫完一行的所有块，输出除以 l 就是结果（[`attention.h`](attention.h) 的 `attentionTiled`）：

```cpp
for (int i0 = 0; i0 < n; i0 += blockQ) {                 // 一组查询
    std::fill(m.begin(), m.end(), -INFINITY);
    std::fill(l.begin(), l.end(), 0.0f);
    for (int j0 = 0; j0 < i0 + rows; j0 += blockK) {     // 一组键。更靠后的键块整块跳过
        // 1. 这一小块的打分：rows × cols，放在 s 里（上一块的内容被覆盖）
        // 2. 在线 softmax：每个查询更新自己的 m、l，把 exp(s − m) · v 累加到输出行上
    }
    // 3. 输出的这几行除以各自的 l
}
```

临时内存只有三个数组：一小块打分 `blockQ × blockK`，加上 `m` 和 `l` 各 `blockQ` 个数。**它的大小和 N 无关。**

[`tiled_test.cpp`](tiled_test.cpp) 用各种块大小验证结果（N = 100，故意不是块大小的整数倍）：

```
N = 100，d = 16。标准做法的临时内存：40000 字节（N × N × 4）

  查询块     键块  临时内存 字节       最大误差
       1        1             12       8.34e-07
       1      100            408       7.15e-07
       8        8            320       7.15e-07
      16       32           2176       7.15e-07
       7       13            420       7.15e-07
     100      100          40800       7.15e-07
     128      128          66560       7.15e-07
```

所有块大小的结果都和标准做法一致（误差在 10⁻⁶ 以下）。“临时内存”一列是按分配的数组大小算出来的，不包括输入和输出。

第 8 课的 `attendOne` 其实就是这张表里“查询块 1、键块 N”的那种情况：一次算一个查询的一整行打分。所以第 8 课的代码从来没有建过 N × N 的表。在 CPU 上逐行写循环时，这是很自然的写法；只有在“把运算写成对整个矩阵的操作”的框架里，才会不知不觉地建出这张表。

## 4. 测量

[`tiled_bench.cpp`](tiled_bench.cpp) 比较两种写法。数字来自一台 2.1 GHz 的机器，单线程，你的结果会不同，看比例：

```
单头注意力，d = 64，分块大小 64 × 64

       N |  标准 临时内存    耗时 ms |  分块 临时内存    耗时 ms |   最大误差
     256 |        0.25 MB        2.6 |        0.02 MB        2.6 |   4.77e-07
     512 |        1.00 MB        9.2 |        0.02 MB        8.1 |   4.77e-07
    1024 |        4.00 MB       33.3 |        0.02 MB       32.2 |   4.92e-07
    2048 |       16.00 MB      139.2 |        0.02 MB      153.0 |   6.11e-07

N = 1024，不同的分块大小：
          块    临时内存 字节    耗时 ms
    1 × 1                   12       42.3
    8 × 8                  320       26.0
   64 × 64               16896       25.2
 1024 × 1024           4202496       26.6
```

如实地读这张表：

- **临时内存**：标准做法随 N² 增长，N = 2048 时 16 MB；分块做法固定在 0.02 MB（16896 字节）。这是确定无疑的收益。
- **耗时：在这台机器的 CPU 上，两者没有明显差别。** 各行互有快慢，差距在测量的波动范围内。原因是：在我们这个单线程的实现里，时间几乎都花在点积和 exp 上，这部分两种写法的计算量完全相同；把 16 MB 的矩阵写进内存再读出来，相比之下只占很小一部分。
- **块太小反而慢**：1 × 1 时慢了六成，因为每算一个打分就要做一次“更新 m、换算 l 和 o”，这些额外的操作本来可以一整块只做一次。

所以这一课**在 CPU 上能验证的结论**是：分块 + 在线 softmax 给出相同的结果，临时内存从 N² 降到常数。**不能在这里验证的**是它在 GPU 上带来的速度提升。下一节解释为什么 GPU 上的情况不同。

## 5. GPU 上为什么这件事重要

这一节和下一节没有可运行的示例，只讲基础的、确定的内容。具体的数字（各级存储有多大、带宽是多少、能快多少）随显卡型号和模型而不同，请以论文和厂商文档为准。

### 存储的层次

C++ 教程第 14 课讲过 CPU 的缓存：访问内存比做运算慢得多，所以要让数据待在离处理器近的缓存里。[第 5 课](../lesson05/README.md) 的矩阵乘法分块就是为了这个。GPU 上有同样的层次：

| | 离计算单元近、小、快 | 离计算单元远、大、慢 |
|---|---|---|
| CPU | 各级缓存 | 内存 |
| GPU | 芯片上的存储（寄存器、共享内存、缓存） | 显存 |

GPU 的算力很强，很多算子的瓶颈不是“算不过来”，而是“数据从显存读进来、结果写回显存”的速度跟不上。这类算子叫**受内存带宽限制**的算子。

### 标准写法在 GPU 上的问题

三个矩阵运算在框架里是三个独立的算子，各自运行一遍：

```
算子一：读 Q、K            → 把 N × N 的 S 写进显存
算子二：从显存读 S         → 把 N × N 的 P 写进显存
算子三：从显存读 P、V      → 写 O
```

N × N 的中间结果在显存里被写两次、读两次。它们比输入输出大得多，所以大部分时间花在搬运这两个临时矩阵上，而不是花在计算上。另外，这两个矩阵本身要占显存，序列一长就放不下。

### FlashAttention 的做法

FlashAttention（Dao 等，2022）把三步合并成**一个**算子，在算子内部用的就是第 2、3 节的方法：把 Q、K、V 分成小块，一小块的打分算出来之后留在芯片上的存储里，立刻用在线 softmax 累加到输出上，然后丢弃。N × N 的矩阵从头到尾没有写进显存。计算量没有减少，减少的是对显存的读写。论文标题里的 “IO-Awareness”（考虑读写的开销）说的就是这个。它是**精确**的：结果和标准写法在浮点精度内相同，不是近似算法。

把它和前面的课联系起来看：

- 它是 [第 3 课](../lesson03/README.md) 的**算子融合**的一个例子：把相邻的几个算子合成一个，省掉中间结果。只是这里不能简单地把三步拼起来，中间隔着一个需要“看完整行”的 softmax，要先用在线 softmax 把它改写成能逐块累加的形式，才融合得了。
- 它是第 5 课的**分块**在另一种硬件上的应用：选块的大小，使一小块数据放得进离计算单元近的那一级存储。
- 这一课的 CPU 实现和 GPU 上的实现，数学上是同一个算法。差别在于 GPU 上块的大小要按芯片上存储的容量来选，并且很多块是并行计算的。

## 6. GPU 编程的基本概念

招聘要求里写着“熟悉 GPU 编程，至少掌握 CUDA、OpenCL……中的一种，并熟练使用 Nsight System/Compute 等性能分析工具”。**这部分需要一块 NVIDIA 显卡，本教程没有可运行的示例**，学完这套教程也不等于掌握了它。下面是开始自学之前需要知道的几个词。

| 概念 | 含义 |
|---|---|
| 主机与设备 | CPU 和内存这一侧叫主机（host），GPU 和显存那一侧叫设备（device）。数据要显式地在两边之间拷贝，拷贝本身有开销 |
| kernel | 在 GPU 上运行的一个函数。“写一个 GPU 算子”基本上就是写一个或几个 kernel。（注意和操作系统内核、卷积核是不同的意思。招聘要求里的“Kernel 级优化”指的是这个） |
| 线程、线程块、网格 | 启动一个 kernel 时，同一个函数由大量线程同时执行，每个线程根据自己的编号决定处理哪一部分数据。线程按“块”（block）组织，块再组成“网格”（grid） |
| 共享内存 | 同一个线程块里的线程可以共用的一小块芯片上的存储，比显存快得多、小得多。第 5 节说的“留在芯片上”主要就是放在这里和寄存器里 |
| 全局内存 | 就是显存。所有线程都能访问，容量大，访问慢 |

工具方面：

| 工具 | 作用 |
|---|---|
| Nsight Systems | 看整体的时间线：CPU 在做什么、GPU 在做什么、各个 kernel 什么时候运行、数据什么时候在主机和设备之间拷贝。用来回答“时间花在哪个阶段”，相当于 C++ 教程第 14 课的“粗粒度计时” |
| Nsight Compute | 分析单个 kernel：它受算力限制还是受内存带宽限制，各级存储的使用情况。用来回答“这个 kernel 为什么慢”，相当于 C++ 教程第 14 课的“性能分析器” |

招聘要求里还出现了两个名字，知道它们是什么即可：**CUTLASS** 是 NVIDIA 开源的一套 C++ 模板，用来在 CUDA 上实现高性能的矩阵乘法一类的运算；**Triton** 这个名字有两个不同的东西，一个是用 Python 写 GPU kernel 的语言，另一个是 NVIDIA 的推理服务器，和“GPU 编程”并列出现时一般指前者。

方法上，C++ 教程第 14 课的原则全部适用：先测量，再优化；先用 Nsight Systems 确定时间花在哪个阶段，再用 Nsight Compute 看具体的 kernel；优化之后验证结果没变（这一课 `tiled_test` 那样的检查）。

### 自学入口

1. **FlashAttention 的论文**：Dao 等，*FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness*（arXiv:2205.14135）。学完这一课，论文里的算法部分应该能直接读懂：它和第 3 节的 `attentionTiled` 是同一个思路，只是循环的组织方式和块大小的选法是按 GPU 来定的。性能数字以论文为准。
2. **NVIDIA 的 CUDA C++ Programming Guide**（官方文档）。先读编程模型那一章，对上表里的概念建立准确的理解。
3. **动手**：有显卡之后的第一个练习建议是把 [第 5 课](../lesson05/README.md) 的矩阵乘法写成一个 kernel，和 CPU 版本对比结果；第二个练习是把这一课的 `attentionTiled` 搬上去。没有 NVIDIA 显卡的话，OpenCL 可以在很多集成显卡上运行，概念是相通的。
4. **Nsight Systems 和 Nsight Compute 的官方文档**。等有了自己写的 kernel 再看，对着自己的程序学。

## 7. 和项目、岗位的关系

- **岗位**：三份招聘要求里，一份点名了 FlashAttention，一份要求“Kernel 级优化经验”，一份要求“自研 GPU 高性能算子的开发与性能分析”。面试时要能回答：标准写法的问题是什么（N × N 的中间结果，读写显存）；FlashAttention 怎么解决（分块、在线 softmax、融合成一个算子）；它是不是近似（不是）；它减少的是什么（对显存的读写，不是计算量）。在线 softmax 的更新公式最好能当场推出来，第 2 节就是推导过程。
- **项目**：路线图里计划把异常检测的骨干网络换成 ViT。高分辨率图像切成的块很多，N 很容易上千，注意力的 N × N 中间结果在端侧设备上就是内存问题。这一课的分块写法可以直接用在自己实现的算子里；用现成的推理后端时，要确认它对注意力有没有做类似的融合（[第 7 课](../lesson07/README.md)）。
- **PatchCore 的最近邻搜索**：“每个查询和记忆库里的所有特征算距离，取最小值”和注意力的形状一样：一个 N × M 的距离表，后面接一个“每行取最小”。按块计算、每行只保留当前的最小值，就不需要保存整张表。取最小值比 softmax 更简单，连换算都不需要。

## 9. 练习

1. **忘记换算**：把 `OnlineSoftmax::addBlock` 里的 `l *= rescale; o *= rescale;` 两行注释掉，运行 `online_softmax`。哪些情况的结果错了？“每块 1000 个”那一行为什么仍然正确？做完改回去。
2. **手算一遍**：打分是 1、3，对应的值是 10、20，每块 1 个。在纸上按第 2 节的更新规则算出每一步的 m、l、o，以及最后的 o / l。再用标准做法算一遍，对一下。
3. **峰值内存不靠算，靠测**：`scratchBytes` 是按数组大小算出来的。在 Linux 上用 `/usr/bin/time -v ./tiled_bench`（看 “Maximum resident set size”），或者在 macOS 上用 `/usr/bin/time -l`，分别只运行标准做法和只运行分块做法（改一下 `main`，N 取 4096），比较两次的峰值内存。差值和 N × N × 4 字节一致吗？
4. **多头**：`attentionTiled` 是单头的。参考第 8 课 `attendOne` 里对 `offset` 和 `headDim` 的处理，把它改成多头，并用第 8 课的 `selfAttention` 的结果来验证。
5. **每行取最小**（选做）：按第 7 节最后一条的思路，写一个函数：N 个查询向量、M 个记忆库向量，求每个查询到记忆库的最小距离，分块计算，不保存 N × M 的距离表。用“先算出整张表再取最小”的写法验证结果。这就是 PatchCore 打分的核心。
