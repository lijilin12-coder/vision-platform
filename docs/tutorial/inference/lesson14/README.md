# 第 14 课：读源码与大作业

> 预计用时：读完正文 1.5 小时；读源码和大作业以周计
> 示例代码：这一课没有新的示例。要读的是真实框架的源码，要写的是大作业

## 这一课要回答的问题

前面十三课，每一项技术都自己写了一个最小的版本。岗位要求里写的却是“熟悉至少一种主流推理框架源码”“负责推理引擎的二次开发”“为开源项目贡献过代码”。

1. 一个几十万行的推理框架，从哪里开始读？
2. 前面各课的概念，在 llama.cpp、vLLM、SGLang、ONNX Runtime 里分别在什么位置？
3. 怎么提出第一个能被合并的 PR？
4. 用什么项目证明自己真的会？

> **关于这一课里的文件路径**：这些仓库变化很快，文件经常被拆分、改名、移动。下面列出的目录和文件名，是 **2026 年 11 月**查看各仓库主分支时核对过的；函数名也是当时在文件里搜索到的。**你读到的版本很可能已经不同。** 路径对不上时，不要找这一课的错，直接在仓库里搜索表格里给出的关键词。会搜索比记住路径有用。

## 1. 怎么读一个推理框架的源码

第一次打开这类仓库的人，常见的做法是从目录的第一个文件开始往下读，读两天之后放弃。原因是没有问题可问，看到的每一行都同样重要，也就同样记不住。

下面的顺序更有效。

### 第一步：先跑通，测几个数

读之前先当用户。按仓库的说明编译、下载一个最小的模型、跑起来，然后**测出前面几课定义过的指标**：首字延时、每秒 token 数、内存占用。之后读代码时，你就知道自己在找“这个数字是哪段代码决定的”。

连编译都没跑通就开始读，后面每一步都会更难：没法加日志，没法打断点，没法验证自己的理解。

### 第二步：沿着一条请求的路径读

不要按目录读，按**一个请求从进来到出去经过的路径**读：

```
收到提示词 → 切成 token → 排队 → 组批 → 前向计算 → 采样 → token 变回文字 → 返回
```

用调试器是最省力的办法（C++ 教程第 12 课）：在最里层的计算函数上打一个断点，看调用栈。调用栈就是这条路径，一次就把“谁调用谁”全部给你。Python 写的框架同样可以：在模型的前向函数里加一行 `import traceback; traceback.print_stack()`。

第一遍只求走通，每一站只弄清“输入是什么、输出是什么、交给谁”，不看细节。

### 第三步：带着一个具体的问题深入

走通之后，每次只带一个问题回去读一个地方。好的问题都来自前面各课：

- “它的 KV Cache 存在什么数据结构里？一条序列结束时怎么释放？”
- “它什么时候决定让一个新请求进批？依据是什么？”
- “它怎么知道两个请求的前缀相同？”

读完之后做一次验证：**改一个参数或者加一行日志，预测结果，再运行。** 预测对了，才算读懂了。

### 第四步：把读到的写下来

写一页笔记：一张“请求路径”的图，加上每个概念对应的文件和函数。面试时被问到“你读过某某的源码吗”，能当场画出这张图，比说“读过”有说服力得多。

## 2. llama.cpp：从这里开始

llama.cpp 是 C/C++ 写的，可以只用 CPU 运行，依赖很少，和前面各课的示例最接近。**建议第一个读它。** 它分两层：下层 `ggml/` 是一个张量库（相当于第 1～6 课的内容），上层 `src/` 是大模型的推理逻辑（相当于第 8～10 课），`tools/server/` 是服务（相当于第 11 课）。

### 先跑通

按仓库 `docs/build.md` 编译，从它的 README 里找一个最小的 GGUF 模型下载运行，再用 `tools/llama-bench/` 测 Prefill 和解码各自的速度。然后读 `examples/simple/simple.cpp`：它只有两百来行，完整地做了“切 token → `llama_decode` → 采样 → 循环”，是整个仓库最好的入口。

### 阅读路线

| 本教程 | 在 llama.cpp 里 | 搜索关键词 |
|---|---|---|
| 第 1 课 张量与算子 | `ggml/include/ggml.h`（张量的定义和全部算子的声明）；CPU 上的实现在 `ggml/src/ggml-cpu/` | `struct ggml_tensor` |
| 第 2 课 计算图 | `ggml/src/ggml.c` 负责建图；`ggml/src/ggml-cpu/ggml-cpu.c` 负责执行 | `ggml_build_forward_expand`、`ggml_graph_compute` |
| 第 4 课 内存规划 | `ggml/src/ggml-alloc.c` | `ggml_gallocr` |
| 第 5 课 高性能算子 | `ggml/src/ggml-cpu/` 下的矩阵乘法和按指令集区分的实现 | `ggml_compute_forward_mul_mat`、`simd` |
| 第 6 课 量化 | `ggml/src/ggml-cpu/quants.c`（各种量化格式的编码和点积）；`tools/quantize/`（命令行工具）；`src/llama-quant.cpp` | `quantize_row_q4_0` |
| 第 7 课 推理后端 | `ggml/src/ggml-backend.cpp`，以及 `ggml/src/` 下每个硬件一个目录（`ggml-cuda`、`ggml-cann` 等） | `ggml_backend` |
| 第 8 课 Transformer 前向 | `src/llama-graph.cpp`（各种模型共用的建图部件，包括注意力）；`src/models/` 下每种模型结构一个文件 | `build_attn`、`build_graph` |
| 第 9 课 KV Cache | `src/llama-kv-cache.h` 和 `.cpp`；一次解码的总流程在 `src/llama-context.cpp` | `llama_kv_cache`、`find_slot`、`llama_context::decode` |
| 第 10 课 采样 | `src/llama-sampler.cpp` | `llama_sampler_init_top_k`、`llama_sampler_init_top_p` |
| 第 10 课 投机解码 | `common/speculative.cpp`；最小的例子在 `examples/speculative-simple/` | `common_speculative` |
| 第 11 课 连续攒批 | `tools/server/`。先读 `tools/server/README-dev.md` 的 Batching 一节，再读 `server-context.cpp` | `update_slots`、`server_slot` |
| 第 13 课 FlashAttention | `ggml/src/ggml-cpu/ops.cpp` 里有一个 CPU 上的实现 | `flash_attn_ext` |
| 模型文件怎么加载（大作业 B 要用） | `src/llama-model-loader.cpp`；文件格式的读写在 `ggml/src/gguf.cpp` | `gguf_init_from_file` |

三点说明：

- **它的服务端用的是“槽位”**（slot）：启动时定好最多同时处理几条序列，每条占一个槽位。`update_slots` 每调用一次就是第 11 课的“一步”：遍历所有槽位，把每个槽位的下一个 token（或者还没处理完的提示词）放进同一批，调用一次 `llama_decode`。对照第 11 课的 `runContinuous` 读。
- **它的 KV Cache 不是第 12 课的分页方式**。读的时候带着这个问题：它是怎么给一条序列找存放位置的，和分页相比各有什么取舍。
- `docs/development/HOWTO-add-model.md` 讲怎么添加一种新的模型结构，读完能明白“模型文件、结构定义、建图”三者的关系。

## 3. vLLM

vLLM 是 Python 写的服务端框架，计算交给 PyTorch 和各种 GPU 算子。它需要 GPU 才能发挥作用；没有 GPU 也可以**只读调度和内存管理的部分**，这部分是纯 Python，逻辑和第 11、12 课一一对应。

### 先读文档

`docs/design/` 下有设计文档，先读这几篇再看代码：

- `arch_overview.md`：进程结构、调度器、模型运行器各在哪里，并且给出了对应的文件路径。**以它为准**，它比这一课更新得快。
- `prefix_caching.md`：前缀缓存怎么用哈希实现（第 12 课第 5 节）。
- `paged_attention.md`：注意它开头的说明——这是一篇历史文档，描述的是最初论文里的实现，不是现在的代码。读它是为了理解原理。

### 阅读路线

| 本教程 | 在 vLLM 里 | 搜索关键词 |
|---|---|---|
| 请求入口 | `vllm/entrypoints/`（HTTP 服务和离线接口） | `api_server` |
| “一步”的主循环 | `vllm/v1/engine/core.py`：调度 → 执行 → 用结果更新调度器 | `EngineCore`、`def step` |
| 第 11 课 连续攒批 | `vllm/v1/core/sched/scheduler.py`。`schedule` 决定这一步谁在批里、每条序列处理多少个 token；`update_from_output` 在一步结束后移出完成的请求 | `def schedule`、`self.running`、`self.waiting`、`token_budget` |
| 第 11 课第 6 节 抢占、分块 Prefill | 同一个文件 | `preempt`、`prefill` |
| 第 12 课 块管理 | `vllm/v1/core/block_pool.py`（空闲块、引用计数）；`vllm/v1/core/kv_cache_utils.py`（块的定义）；`vllm/v1/core/kv_cache_manager.py`（给请求分配和释放块） | `ref_cnt`、`get_new_blocks`、`free_blocks`、`allocate_slots` |

建议的读法：把第 11 课的 `runContinuous` 和第 12 课的 `BlockManager` 打印出来放在旁边，读 `scheduler.py` 的 `schedule` 和 `block_pool.py`，逐项对照，列出**它比你的版本多考虑了什么**。多出来的每一项（token 预算、抢占、多种缓存类型、前缀缓存的淘汰）背后都是一个真实遇到过的问题，这张清单就是你对“工程版本”的理解。

## 4. SGLang 和 ONNX Runtime

### SGLang

SGLang 和 vLLM 定位相同，结构也相似，读懂一个再看另一个会很快。值得对比的是两者做法不同的地方：

| 本教程 | 在 SGLang 里（都在 `python/sglang/srt/` 下） | 搜索关键词 |
|---|---|---|
| 第 11 课 调度 | `managers/scheduler.py`；批的数据结构在 `managers/schedule_batch.py`；调度顺序在 `managers/schedule_policy.py` | `get_next_batch_to_run`、`get_new_batch_prefill`、`update_running_batch` |
| 第 12 课 缓存管理与前缀共享 | `mem_cache/`。先读这个目录里的 `README.md`。前缀共享用基数树：`radix_cache.py` | `RadixCache`、`memory_pool` |
| 第 13 课 注意力算子 | `layers/attention/`：每种后端一个文件 | `backend` |

带着一个问题读：vLLM 用“每块一个哈希值”找相同的前缀，SGLang 用基数树。两种做法在“前缀只有一部分相同”“缓存满了要淘汰谁”这两件事上各有什么不同？

### ONNX Runtime

ONNX Runtime 对应的是本教程的**第一部分**，也是本项目开发机上要用的推理后端（大作业 A）。它是 C++ 写的，规模很大，但结构清楚：

| 本教程 | 在 ONNX Runtime 里 | 搜索关键词 |
|---|---|---|
| 怎么调用（大作业 A 要用） | `include/onnxruntime/core/session/onnxruntime_cxx_api.h` | `Ort::Session`、`Run` |
| 一个模型从加载到能运行 | `onnxruntime/core/session/inference_session.cc`：加载 → 图优化 → 划分给各个后端 → 准备执行 | `InferenceSession::Initialize`、`TransformGraph` |
| 第 2 课 计算图 | `onnxruntime/core/graph/graph.cc` | `class Graph` |
| 第 3 课 图优化 | `onnxruntime/core/optimizer/`：每个优化遍一个文件，例如 `constant_folding.cc`、`conv_bn_fusion.cc`、`conv_activation_fusion.cc`；哪些遍在哪个优化级别启用，在 `graph_transformer_utils.cc` | `GenerateTransformers` |
| 第 4 课 内存规划 | `onnxruntime/core/framework/allocation_planner.cc` | `PlannerImpl`、`SequentialExecutionPlan` |
| 第 2 课 执行 | `onnxruntime/core/framework/sequential_executor.cc` | `SequentialExecutor` |
| 第 5 课 高性能算子 | `onnxruntime/core/mlas/lib/`：矩阵乘法等，按指令集分文件 | `sgemm`、`qgemm` |
| 第 6 课 量化 | `onnxruntime/python/tools/quantization/`（大作业 A 的 INT8 量化用它） | `quantize_static`、`calibrate` |
| 第 7 课 后端与子图划分 | `onnxruntime/core/framework/graph_partitioner.cc`；每个后端在 `onnxruntime/core/providers/` 下一个目录 | `GetCapability`、`Partition` |

第 3 课自己写过卷积和批归一化的融合。打开 `conv_bn_fusion.cc`，它做的是同一个推导，多出来的是各种边界条件的检查：这个节点的输出有没有被别人用、权重是不是常量、属性是否符合条件。读它是了解“一个优化遍在真实框架里要多小心”的最短路径。

## 5. 提出第一个 PR

第二份岗位描述的加分项里有一条：“为 vLLM、SGLang、llama.cpp 等开源项目贡献过代码”。它的意思不是要你提交一个大功能，而是证明你能在一个陌生的大型代码库里**找到问题、按别人的规矩改好、通过评审**。这正是入职第一个月要做的事。

### 先读规矩

每个仓库都有贡献指南，动手之前完整地读一遍：

| 仓库 | 贡献指南在哪里 |
|---|---|
| llama.cpp | 根目录的 `CONTRIBUTING.md` |
| vLLM | `docs/contributing/README.md` |
| SGLang | `docs/` 下开发者指南里的 contribution guide |
| ONNX Runtime | 根目录的 `CONTRIBUTING.md`，以及 `docs/PR_Guidelines.md` |

特别留意三类要求，不满足的 PR 通常直接被关闭：

- **关于使用 AI 工具的规定。** llama.cpp 和 vLLM 的贡献指南里都有专门的一节。提交之前读清楚它允许什么、要求你声明什么。无论规定怎么写，底线是一样的：**你提交的每一行，自己都要能解释。**
- **提交信息的格式和签名。** 例如 vLLM 要求提交带 `Signed-off-by`（指南里的 DCO 一节）。
- **代码风格和测试。** 指南里会写怎么在本地运行格式检查和测试。在本地跑通再提交。

### 从哪里找第一个 PR

按从易到难排列。前三种不需要 GPU：

1. **文档和注释里的错误。** 你在第 2～4 节按路线读代码时，一定会遇到文档里的路径已经失效、命令已经改名、注释和代码不一致的地方。这是最容易被合并的 PR，而且你已经在读了。
2. **补一个测试。** 读到一个函数的某种边界情况没有测试覆盖，给它写一个。评审者很欢迎这类 PR。
3. **你自己撞到的小 bug。** 跑通的过程中遇到的报错、在你的平台上编译失败、某个参数组合崩溃。先搜一下有没有人已经报告过。
4. **带着标签的入门问题。** 仓库的问题列表里通常有标着 good first issue 一类标签的条目。动手之前先在下面留言说明你要做，避免和别人重复。
5. **性能改进。** 必须附上改动前后的测量数据和测量方法。这是前面各课一直在练的事。

### 让 PR 容易被合并

- **小。** 一个 PR 只做一件事。五十行的改动几天内会有人看，五百行的可能一个月没人看。
- **说明白。** 写清楚：问题是什么，怎么复现，你怎么改的，怎么验证的。
- **先问再做。** 改动稍大时，先开一个问题描述你的想法，得到维护者认可再动手。
- **评审意见逐条回应。** 改了就说改了，不同意就说理由。被要求修改是正常的，不是否定。

## 6. 大作业

两个任选其一。A 把第一部分落到本项目里；B 把第二部分组装成一个完整的系统。时间有限时，按你想去的岗位选：偏芯片和端侧选 A，偏大模型服务选 B。

两个大作业共同的要求：

- 每个阶段结束时，程序是能运行、有测试的。
- **每一项优化都要有改动前后的测量数据**，并且验证结果没有变（C++ 教程第 14 课第 5 节）。
- 最后写一份报告，格式参考本项目的 [POC-1 报告](../../../poc/poc-1-report.md)。

### 大作业 A：给本项目加上推理后端和图优化

完成项目计划里的 [POC-4 和 POC-10](../../../04-poc-plan.md)，再给执行引擎加一个优化遍。

**阶段 1：`InferBackend` 端口和 ONNX Runtime 适配器。**（第 7 课）

- 在检测执行上下文的领域层定义 `InferBackend` 接口（设计见 [战术设计](../../../ddd/05-tactical-design.md) 第 3 节的端口列表）：加载模型、查询输入输出的形状、推理一批。接口里不出现任何 ONNX Runtime 的类型。
- 在 `adapters/` 下新建一个适配器，用 ONNX Runtime 的 C++ 接口实现它。按 `cmake/VisionBoundaries.cmake` 的规则，领域层不能依赖适配器。
- 用 Python 导出一个 ResNet18 的 ONNX 文件（模型文件不提交到仓库，`.gitignore` 里已经排除）。
- 验收：一个单元测试加载模型、推理一张固定的图，输出和 Python 里 ONNX Runtime 的输出最大误差小于 1e-5；模型文件不存在、输入形状不对时返回 `Result` 的错误，不崩溃。

**阶段 2：做成算子，接入方案。**

- 按 [如何新增一个算子](../../../dev/how-to-add-operator.md) 写一个分类算子：输入图像，输出类别和分数。预处理（缩放、归一化）放在算子里。
- 推理放在独立的推理线程里按批进行（C++ 教程第 16 课的结构），多个工位共用一个模型。
- 验收：`vision-cli inspect` 能跑通一个含这个算子的方案；第一次检测之前模型已经预热。

**阶段 3：测量与一致性。**（POC-4 的验收项）

- 记录 CPU 推理耗时：中位数和最坏情况，批大小 1、4、8 各一组。
- 打开 ONNX Runtime 的性能分析，得到逐层耗时；把优化后的图保存下来，对照第 3 课列出它融合了哪些算子。
- 有鸿蒙设备或模拟器时：用 MindSpore Lite 实现第二个适配器，验证“同一张图两端输出的最大误差小于 1e-3”。没有设备时，这一项写进报告的“未完成”里。

**阶段 4：INT8 量化。**（POC-10 的验收项，第 6 课）

- 用 ONNX Runtime 的量化工具，以 100 张图做校准，得到 INT8 模型。
- 验收：报告里有一张表——FP32 和 INT8 的模型大小、推理耗时、在一组测试图上的精度；并且解释精度变化主要来自哪几层（提示：逐层比较量化前后的输出）。

**阶段 5：给执行引擎加一个融合遍。**（第 3 课）

- 在编译执行计划的地方（`core/contexts/execution/domain/src/plan.cpp`）加一个优化遍：发现 `to_gray` 的输出**只**被一个 `threshold` 使用时，把两个节点合并成一个一次遍历完成的融合算子。
- 要处理的情况：`to_gray` 的输出还被别的节点使用时不能融合；融合后调试输出里仍然要能看到原来两个节点的信息；可以用一个开关关闭这个遍。
- 验收：融合前后所有示例图的检测结果完全相同；5MP 图像上这两个节点的总耗时有测量数据；`to_gray` 输出被两个节点使用的方案有测试，证明它没有被错误地融合。

**优秀线**：再做一项——按第 4 课的方法分析执行计划里每个中间图像的生命周期，让生命周期不重叠的图像复用同一块缓冲区，并测量一次检测申请内存的次数和峰值内存的变化。

### 大作业 B：一个最小的大模型推理服务

把第 8～12 课的部件组装起来，并且换上真实的模型权重。

**阶段 1：加载真实的权重。**（第 8 课）

- 选一个参数量在 5 亿左右或更小的开源模型，用 Python 把它的权重和词表导出成你自己定义的简单二进制格式（一个文件头加若干个带名字的数组就够）。想直接读 GGUF 文件的话，参考第 2 节表格最后一行。
- 把第 8 课的前向改成这个模型的真实结构。和第 8 课的示例相比，通常要补上：它用的那种归一化层、位置编码方式、分组查询注意力。这些在模型的配置文件和 llama.cpp 对应的模型文件里都能查到。
- 验收：同一段提示词，你的程序算出的下一个 token 的 logits，和 Python 里用 PyTorch 算出的最大误差小于 1e-3；贪心解码 50 个 token，输出的 token 序列完全相同。**这一步通过之前不要做任何优化。**

**阶段 2：KV Cache 和采样。**（第 9、10 课）

- 加上 KV Cache；加上温度、top-k、top-p 采样；流式输出。
- 验收：有缓存和没有缓存的 logits 逐步一致；报告首字延时和每秒 token 数。

**阶段 3：批量前向和连续攒批。**（第 11 课）

- 让前向支持一批里的序列长度不同，每条序列有自己的 KV Cache。
- 实现第 11 课的调度循环：一个推理线程，每一步接纳新请求、移出完成的请求。请求从别的线程提交，用 C++ 教程第 16 课的 `promise` / `future` 或者回调返回 token。
- 验收：同一个请求单独运行和与别的请求同批运行，贪心解码的输出相同；用一个压测程序按第 11 课的负载发请求，报告逐条处理和连续攒批两种方式的吞吐、首字延时的 P50 和 P99。**这一次是真实的测量，和第 11 课模拟的结论对照，一致和不一致的地方都要解释。**

**阶段 4：分页的 KV Cache。**（第 12 课）

- 把每条序列的 KV Cache 从“连续数组”换成第 12 课的块管理器，注意力计算按块表取数。
- 接纳新请求由空闲块数量决定；块用完时暂停一条序列。
- 验收：换成分页前后输出相同；报告在固定的缓存总量下，两种方式能同时容纳的序列数；测量按块表取数让注意力慢了多少。

**阶段 5（任选一项）：**

- 前缀共享：按第 12 课练习 5 的方式，让带相同系统提示词的请求共享块，测量首字延时的变化。
- 量化：把权重按第 6 课的方法量化成 8 位，测量速度、内存和输出质量的变化。
- 投机解码：用一个更小的模型做草稿模型（第 10 课），测量接受率和加速比。
- 一个 HTTP 接口：让现成的客户端能连上来。

**优秀线**：用性能分析器找出你的服务里最耗时的三处，各做一次有数据支撑的优化；然后在同一台机器、同一个模型上和 llama.cpp 的服务对比吞吐，并解释差距来自哪里。差距会很大，能把原因讲清楚就是这个大作业的价值。

## 7. 这套教程没有覆盖什么

第 0 课说过这套教程给不了什么。学完之后，按你要去的岗位补下面这些：

| 没有覆盖的内容 | 岗位描述里的说法 | 自学入口 |
|---|---|---|
| **GPU 编程实战** | “熟悉 GPU 编程，至少掌握 CUDA、OpenCL……中的一种，并熟练使用 Nsight 等性能分析工具” | 需要一块 NVIDIA 显卡（租用云主机也可以）。从 NVIDIA 官方的 CUDA 编程指南开始；第一个练习是把第 5 课的矩阵乘法写成 CUDA 版本，第二个是把第 13 课的注意力写成 CUDA 版本，并用 Nsight 看时间花在哪里。之后读 vLLM `csrc/` 下的算子 |

| **AI 编译器** | “熟悉 AI 编译器技术栈（MLIR、TVM、XLA、Glow），有编译器前端开发经验” | 第 2～4 课是它的入门：图、遍、内存规划。下一步做 MLIR 官方的 Toy 教程，它带你从头做一个小语言的前端并逐级变换到机器码；再看 TVM 的入门教程 |

最后一条建议。岗位描述列了十几项技术，没有人在入职前全部做过。面试官想确认的是三件事：**基础是不是扎实**（C++、体系结构、能不能把一个性能问题测清楚）、**核心概念是不是真懂**（能不能不看资料讲清楚 KV Cache 为什么有效、连续攒批改善了什么）、**有没有独立做完一件事**。这三件事分别对应 C++ 教程、这套教程的前十三课、和这一课的大作业。

## 8. 练习

1. **跑通并测量**：编译 llama.cpp，运行一个最小的模型，用它自带的测速工具得到 Prefill 和解码的速度。把线程数分别设成 1、2、4，速度怎么变？和第 5 课、第 9 课的结论对得上吗？
2. **画出请求路径**：用调试器在 llama.cpp 的矩阵乘法函数上打断点，运行 `examples/simple`，记下调用栈。根据它画一张图：从 `main` 到矩阵乘法经过了哪些层，每一层对应本教程的哪一课。
3. **对照阅读**：读 vLLM 的 `scheduler.py` 里的 `schedule` 函数（不需要 GPU，只读代码）。列出它在决定“这一步谁进批”时考虑了、而第 11 课的 `runContinuous` 没有考虑的至少五件事。
4. **找一个可以提 PR 的地方**：在完成练习 1～3 的过程中，记下每一处“文档和实际不一致”或者“报错信息让人看不懂”的地方。挑一处，按第 5 节的要求写出 PR 的说明（先不提交）：问题是什么，怎么复现，怎么改，怎么验证。
5. **选定大作业**：选 A 或 B，写一页计划：每个阶段预计用几天，验收时要展示的数字是哪些，最可能卡住的地方是哪里。
