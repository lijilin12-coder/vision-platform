# 第 6 课：量化——从 FP32 到 INT8

> 预计用时：2.5 小时
> 示例代码：就在这个文件夹里，和这份正文放在一起

## 这一课要回答的问题

[上一课](../lesson05/README.md)是让同样的计算跑得更快。这一课换一个方向：**把计算本身变便宜**。模型里的权重和中间结果原本都是 32 位浮点数（FP32），量化把它们换成 8 位整数（INT8）。

1. 把浮点数换成 8 位整数，模型为什么还能算对？
2. 量化的参数怎么选？选得不好会损失多少？
3. INT8 到底小多少、快多少、精度掉多少？
4. 大模型常说的“4 bit 量化”，和这里讲的是一回事吗？

## 1. 为什么要量化

| 好处 | 原因 |
|---|---|
| 模型小 | 一个权重从 4 个字节变成 1 个字节 |
| 读内存快 | 数据量是 1/4。上一课看到，矩阵大了以后瓶颈在“送数据”上 |
| 算得快 | 同样宽的 SIMD 寄存器能装下 4 倍的数；不少 CPU 有专门的 8 位乘加指令 |
| 硬件要求 | 很多 NPU 对 8 位整数的支持最好，有的型号只有量化后的模型才能跑在 NPU 上 |

代价是精度会掉一点。量化这门技术的全部内容，就是**怎样让精度少掉一点**。

项目的 POC-10 里有一条：“INT8 量化（用 100 张图作为量化校准集），记录精度变化”（[POC 计划](../../../04-poc-plan.md)）。学完这一课，你应该清楚这句话里的每个词在说什么，以及工具背后做了哪些事。

## 2. 基本公式：scale 和 zeroPoint

量化就是用一个整数 q 近似表示实数 r：

```
r ≈ scale × (q − zeroPoint)
```

- `scale`：相邻两个整数代表的实数间隔。
- `zeroPoint`：实数 0 对应的那个整数。

把区间 [−1.0, 3.0] 量化成 `uint8`（0～255）。间隔是 4.0 / 255 ≈ 0.0157，实数 0 落在第 64 格（[`quant_basics.cpp`](quant_basics.cpp) 的第 1 段输出）：

```
1. 把 [-1.0, 3.0] 量化成 uint8：
   scale = 0.015686，zeroPoint = 64
   -1.0000 →   0 → -1.0039   误差 -0.0039
    0.0000 →  64 →  0.0000   误差 +0.0000
    0.5000 →  96 →  0.5020   误差 +0.0020
    1.2345 → 143 →  1.2392   误差 +0.0047
    3.0000 → 255 →  2.9961   误差 -0.0039
    5.0000 → 255 →  2.9961   误差 -2.0039   ← 超出范围，被截断
```

从这几行能看出量化误差的两个来源：

- **舍入误差**：范围以内的数，误差最多半个 scale。范围越窄，scale 越小，这种误差越小。
- **截断误差**：范围以外的数被压到边界上，误差可以很大。范围越宽，被截断的数越少。

两者是矛盾的。**选范围，就是在这两种误差之间找平衡**，这一课后面的内容都围绕它。

另外注意第二行：实数 0 被**精确**地表示了。这是必须保证的，因为卷积补边补的是 0，ReLU 的输出里有大量的 0，它们不能带着误差。

代码在 [`quant.h`](quant.h) 里，量化和反量化各一行：

```cpp
std::uint8_t quantizeU8(float r, QParams p) {
    const long q = std::lround(r / p.scale) + p.zeroPoint;
    return static_cast<std::uint8_t>(std::clamp<long>(q, 0, 255));   // 超出范围的被截断
}
float dequantize(int q, QParams p) { return p.scale * static_cast<float>(q - p.zeroPoint); }
```

## 3. 对称还是非对称

- **非对称量化**：就是上面的做法，区间 [lo, hi] 可以不关于 0 对称，zeroPoint 是算出来的。
- **对称量化**：区间取 [−m, m]，zeroPoint 固定为 0，整数用有符号的 −127～127。公式简化成 `r ≈ scale × q`。

ReLU 之后的值没有负数。用对称量化，负的那一半整数永远用不到：

```
2. ReLU 之后的激活值（范围 [0.00, 7.34]，没有负数）：
   对称量化（int8，-127～127）：  scale = 0.05779，SQNR = 41.7 dB   ← 负的那一半整数全浪费了
   非对称量化（uint8，0～255）：  scale = 0.02878，SQNR = 47.7 dB
```

**SQNR** 是“信号与量化噪声之比”，单位分贝，越大越好。每多用 1 位，间隔减半，SQNR 大约高 6 分贝。这里正好差 6 分贝：对称量化相当于白白少了 1 位。

那为什么还要有对称量化？因为它算起来简单。下面第 6 节会看到，整数推理要算 `Σ qw × (qx − zeroPoint)`；权重的 zeroPoint 是 0 时，公式里少一项。权重的分布通常本来就大致关于 0 对称，损失很小。所以常见的搭配是：

| | 用哪种 | 原因 |
|---|---|---|
| 权重 | 对称，`int8` | 分布大致对称；计算简单 |
| 激活值（层与层之间的中间结果） | 非对称，`uint8` | ReLU 之后没有负数，不能浪费一半 |

## 4. 校准：范围从哪里来

权重是固定的，它的范围直接看最大绝对值就行。**激活值的范围要跑了数据才知道**。所以要准备一小批有代表性的输入，让 FP32 模型把它们跑一遍，记下每一层输出的取值，这个过程叫**校准**，这批数据叫**校准集**。校准集不需要标签，一般几十到几百个样本就够。

记下取值之后怎么定范围，有几种方法。最简单的是**最大最小值法**：见过的最小值和最大值就是范围。它的问题是怕离群值：

```
3. 带离群值的数据（20000 个数，千分之一被放大 40 倍）：
   最大最小值法：范围 [ -29.22,  31.89]，scale = 0.2397，普通值的 SQNR = 23.2 dB
   99.9 百分位： 范围 [  -3.12,   3.15]，scale = 0.0246，普通值的 SQNR = 42.9 dB
```

99.9% 的数都在 ±3 以内，但范围被极少数离群值撑到了 ±30。256 个格子里只有二十几个落在 ±3 以内，绝大多数数据只能用这二十几个格子来区分。

**百分位法**丢掉两头各 0.1% 的数据再取范围。被丢掉的数会被截断，误差很大，但它们太少了，对结果影响小；而剩下 99.8% 的数，精度高了将近 20 分贝（3 位多）。这就是第 2 节说的平衡：**宁可让极少数值错得多，也要让大多数值更准**。

真实的量化工具还提供别的方法（比如比较量化前后分布差异的“熵”方法），思路都是自动找这个平衡点。

## 5. 逐通道量化

到目前为止，一个张量只用一组量化参数。对权重来说这经常不够。把 BatchNorm 合并进卷积之后（[第 3 课](../lesson03/README.md)），每个输出通道的权重都乘上了各自的系数，通道之间的大小可能差几十上百倍：

```
4. 各行大小相差很多的权重矩阵（8 行 × 64 列）：
   行   最大绝对值   整个矩阵一个 scale          每行一个 scale
   0       0.053       5.6 dB（38 个变成 0）       45.6 dB
   1       0.092       9.9 dB（20 个变成 0）       45.7 dB
   2       0.265      17.7 dB（16 个变成 0）       42.3 dB
   3       0.358      24.0 dB（ 6 个变成 0）       46.0 dB
   4       1.001      30.4 dB（ 2 个变成 0）       44.1 dB
   5       1.764      36.2 dB（ 3 个变成 0）       46.2 dB
   6       2.811      40.2 dB（ 2 个变成 0）       45.0 dB
   7       5.053      46.4 dB（ 2 个变成 0）       46.4 dB
```

整个矩阵共用一个 scale 时，scale 由最大的第 7 行决定。第 0 行的 64 个权重里有 38 个直接变成了 0：这个通道基本上被抹掉了。

**逐通道量化**（per-channel）：每个输出通道（矩阵的每一行）用自己的 scale。每一行都得到 45 分贝左右。

为什么可以按**输出**通道分，却不能按输入通道分？因为每个输出通道是单独累加的，它的 scale 可以最后再乘上去；而不同输入通道的乘积要加在一起，加之前必须是同一个 scale。下一节的公式会看得更清楚。

## 6. 整数推理：全连接层怎么只用整数来算

真实的计算是 `y = Σ w·x + b`。把量化公式代进去：

```
w ≈ sw · qw                 （权重：对称，scale 是 sw）
x ≈ sx · (qx − zx)          （输入：非对称，scale 是 sx，zeroPoint 是 zx）
b ≈ sw · sx · qb            （偏置：特意用 sw·sx 做 scale，存成 32 位整数）

y ≈ sw · sx · [ Σ qw · (qx − zx) + qb ]
```

方括号里**全是整数**。这就是 [`quant_mlp.cpp`](quant_mlp.cpp) 里的 `accumulate`：

```cpp
std::int32_t sum = 0;
for (int i = 0; i < in; ++i)
    sum += static_cast<std::int32_t>(row[i]) * (static_cast<std::int32_t>(qx[i]) - input.zeroPoint);
acc[o] = sum + bias[o];
```

几个细节：

- **累加器是 32 位的。** 两个 8 位数相乘是 16 位，成百上千个加起来需要更宽的整数。
- **偏置为什么用 `sw·sx` 做 scale**：这样它可以直接加到累加器上，不需要任何换算。
- **逐通道**：每一行有自己的 `sw`，只影响最后乘的那个系数，不影响整数累加。

算完之后，累加器代表的实数是 `sw·sx·acc`。下一层要的是 `uint8`，所以还要按下一层输入的 scale 重新量化一次，叫 **requantize**：

```cpp
qh[o] = quantizeU8(fc1.realValue(acc1[o], o), fc2.input);   // 实数值 → 下一层的 uint8
```

**ReLU 消失了。** 下一层输入的范围从 0 开始，小于 0 的值在截断到 [0, 255] 时自然变成 0，不需要单独的 ReLU 步骤。

示例里 requantize 这一步用了浮点数（乘以 `sw·sx`、再除以下一层的 scale），这是为了好懂。真正只用整数的引擎会事先把这个比值换算成“乘一个整数、再右移若干位”，这样没有浮点运算单元的硬件也能跑。

## 7. 实测：精度和大小

`quant_mlp` 先用最普通的梯度下降训练一个小模型（64 维输入 → 128 → 10 类；训练部分不是本课重点，代码里可以跳过），然后量化、用整数推理、在 4000 个测试样本上比较：

```
测试集 4000 个样本，校准集 100 个样本

                                     精度      参数大小
  FP32                               97.55%    38440 字节
  INT8，最大最小值校准               95.03%    10592 字节
  INT8，99.9 百分位校准              97.42%    10592 字节（FP32 的 28%）

权重的位数越少，精度掉得越多（激活值仍然是 8 位，99.9 百分位校准）：
  权重位数   整个矩阵一个 scale   每行一个 scale
  8          97.42%               97.42%
  6          97.62%               97.47%
  4          96.65%               96.92%
  3          94.95%               95.92%
  2          47.20%               79.17%
```

（这些数字在不同的系统上可能有零点几个百分点的出入：训练里用到的 `exp` 在各个标准库里的实现略有不同。）

怎么读这张表：

- **INT8 可以几乎不掉精度**：97.55% → 97.42%，差 0.13 个百分点，4000 个样本里差 5 个。
- **校准方法很重要**：示例故意在 100 个校准样本里放了一个坏样本（有三个大得离谱的值，模拟坏点或过曝）。最大最小值法被它带偏，精度掉了 2.5 个百分点；百分位法不受影响。**真实的校准集里一定会有这样的样本。**
- **大小是 28%，不是 25%**：偏置还是 32 位的，另外每行存了一个 scale。
- **位数越少掉得越多，而且不是均匀地掉**：8 位到 4 位只掉了不到 1 个百分点，到 2 位就垮了。位数少的时候，逐通道量化的帮助很明显（2 位时 47% 对 79%）。
- **6 位比 8 位还高 0.2 个百分点？** 这是噪声：0.2% 只是 8 个样本。**这么小的差别不能说明任何问题**，报告精度变化时要有这个意识。

## 8. 实测：速度

[`quant_speed.cpp`](quant_speed.cpp) 测“矩阵 × 向量”，也就是全连接层的核心。四种写法：FP32 和 INT8，各有一个普通循环和一个手写 SIMD 的版本。

用 `-march=native` 编译（这台机器支持 AVX2 和 AVX-512；你的结果会不同，看比例）：

```
512 × 512 的矩阵乘以向量（FP32 权重 1.0 MB，INT8 权重 0.2 MB），取 51 次的中位数：
  FP32，普通循环      0.130 ms
  INT8，普通循环      0.005 ms   是 FP32 普通循环的 25.3 倍快
  FP32，SIMD          0.016 ms
  INT8，SIMD          0.010 ms   是 FP32 SIMD 的 1.7 倍快

4096 × 4096 的矩阵乘以向量（FP32 权重 64.0 MB，INT8 权重 16.0 MB），取 11 次的中位数：
  FP32，普通循环     24.857 ms
  INT8，普通循环      1.010 ms   是 FP32 普通循环的 24.6 倍快
  FP32，SIMD          3.608 ms
  INT8，SIMD          1.221 ms   是 FP32 SIMD 的 3.0 倍快
```

这组数字里有三件值得弄明白的事。

**一、“普通循环”为什么差 25 倍？** 因为编译器把整数的循环自动改成了 SIMD，浮点的没有改。原因是上一课提到的：浮点加法不满足结合律，把“一个一个加”改成“8 个一组加”会改变结果，编译器不敢擅自这样做（除非用 `-ffast-math` 之类的选项明确允许）；整数加法怎么换顺序结果都一样，编译器可以放心改。所以这 25 倍主要是“SIMD 对标量”，不是“整数对浮点”。

**二、公平的比较是两个 SIMD 版本**：矩阵放得进缓存时 INT8 快 1.7 倍；放不进时快 3 倍左右（几次运行在 3～6 倍之间）。后者主要来自数据量只有 1/4。

**三、INT8 的普通循环比手写的 SIMD 还快。** 看汇编可以发现，GCC 在这台机器上用了一条叫 `vpdpbusd` 的指令：它一步完成“8 位无符号数 × 8 位有符号数，相邻 4 个乘积相加，累加到 32 位”。这是 x86 专门为量化推理加的指令（VNNI）；ARM 上也有同类的指令。手写的版本只用了 AVX2，要先把 8 位扩展成 16 位再乘，步骤更多。

不带 `-march=native` 时（只能用所有 x86 都有的 SSE2），同样的程序：INT8 的普通循环比 FP32 快 4.8 倍（小矩阵）和 6.8 倍（大矩阵）。

结论：

- **INT8 快多少，取决于硬件有没有合适的指令，以及推理引擎有没有用上它们。** 不能想当然地认为“快 4 倍”。
- 量化后的模型**一定要在目标设备上实测**。在开发机上快，不代表在鸿蒙电脑的 CPU 或 NPU 上快；反过来也一样。

## 9. 训练后量化与量化感知训练

这一课做的叫**训练后量化**（PTQ，post-training quantization）：模型已经训练好，只用一小批校准数据就完成量化。不需要训练环境，几分钟做完，是首选。

精度掉得太多时，才考虑**量化感知训练**（QAT，quantization-aware training）：训练时就在前向计算里模拟量化的舍入和截断，让模型自己学会适应。它需要完整的训练流程和数据，成本高得多。

实际工作的顺序：先做 PTQ → 精度不够就换校准方法、打开逐通道量化、把最敏感的几层留成 FP32 不量化 → 还不够，再考虑 QAT。

### 用 ONNX Runtime 做 PTQ

POC-10 要用的就是它。下面的片段**不在自动构建里**，需要自己安装（`pip install onnx onnxruntime`）；写这份教程时在 onnxruntime 1.29 上运行过，参数以[官方文档](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)为准。

```python
from onnxruntime.quantization import (CalibrationDataReader, CalibrationMethod,
                                      QuantFormat, QuantType, quantize_static)

class Reader(CalibrationDataReader):          # 校准集：每次返回一个 {输入名: 数组}，没有了就返回 None
    def __init__(self, samples): self.it = iter(samples)
    def get_next(self): return next(self.it, None)

quantize_static("model.onnx", "model.int8.onnx", Reader(calibration_samples),
                quant_format=QuantFormat.QDQ,
                per_channel=True,                              # 第 5 节
                activation_type=QuantType.QUInt8,              # 第 3 节：激活值非对称
                weight_type=QuantType.QInt8,                   # 权重对称
                calibrate_method=CalibrationMethod.Percentile) # 第 4 节；还有 MinMax、Entropy 等
```

这一课的每个概念在参数里都能找到。量化后的模型里，每个算子前后多出了 `QuantizeLinear` 和 `DequantizeLinear` 节点（这种表示方式叫 QDQ），它们记录的就是 scale 和 zeroPoint。推理引擎加载时再把“反量化 → 算子 → 量化”合并成整数实现的算子，这又是一次[第 3 课](../lesson03/README.md)讲的算子融合。

## 10. 大模型的权重量化

大模型常见的“4 bit 量化”“Q4”，原理和这一课相同，侧重点不同。**下面只讲思路，具体格式的分组大小、位数、命名，以 llama.cpp 等项目的文档为准。**

**为什么大模型更需要量化。** 一个 70 亿参数的模型，用 16 位浮点存要 14 GB，4 位上下的量化之后是 4 GB 左右，才放得进普通电脑的内存或一块消费级显卡的显存。而且大模型逐个 token 生成时，每生成一个 token 就要把全部权重读一遍（第 9 课），速度基本由“每秒能读多少字节的权重”决定。权重小一半，差不多就快一倍。

**通常只量化权重。** 激活值仍然用浮点计算，权重在使用时再还原。这样不需要校准集，量化只是对权重文件做一次转换。

**分组量化。** 位数降到 4 位时，一个矩阵甚至一行共用一个 scale 已经太粗了（第 7 节的表：4 位时已经开始掉精度）。做法是把权重**每几十个分成一组**，每组存自己的 scale（有的格式还存一个偏移量）。这就是逐通道量化的思路推到更细的粒度。代价是每组要多存一点参数，所以实际平均下来每个权重占的位数比名义上的 4 位略多。llama.cpp 的 GGUF 文件里 `Q4_0`、`Q4_K_M`、`Q8_0` 这类名字，表示的就是位数和分组方式的不同组合。

**不同的层用不同的位数。** 对精度影响大的部分多给几位，其余少给几位，这和上一节“把敏感的层留成 FP32”是同一个思路。

还有一类方法在量化时用少量数据来调整舍入的方向，以弥补低位数带来的损失（GPTQ、AWQ 等），属于更精细的 PTQ。

| 量化对后续步骤的影响 | 异常检测的打分依赖特征之间的距离，骨干网络量化后特征会有偏移，要单独验证检出效果，不能只看分类精度 |

## 13. 练习

1. **换一个百分位**：把 `quant_mlp.cpp` 里的 `99.9` 改成 `99`、`99.99`、`100`，各运行一次。精度怎么变？`100` 相当于哪种方法？为什么 `99` 反而可能更差？
2. **激活值也降位数**：现在只有权重的位数可以调。给 `chooseAffine` 和 `quantizeU8` 加一个位数参数（比如 4 位就是 0～15），让隐藏层的激活值也用更少的位数，测一测精度。权重 4 位和激活值 4 位，哪个影响更大？
3. **干净的校准集**：把 `main` 里给 `calibrationSet[17]` 赋值的三行删掉。最大最小值法和百分位法的精度还差多少？这说明了什么？
4. **只用整数做 requantize**：`fc1.realValue(...)` 再 `quantizeU8(...)` 的过程用了浮点。把比值 `sw·sx / 下一层的 scale` 事先换算成“乘以一个 32 位整数、再右移 n 位”，用纯整数实现这一步，确认精度不变。
5. **看一看 `-ffast-math`**：给 `quant_speed.cpp` 加上 `-ffast-math` 重新编译（GCC 或 Clang）。“FP32，普通循环”变成了多少？结果和原来逐位相同吗？为什么推理引擎一般不敢对整个程序打开这个选项？
