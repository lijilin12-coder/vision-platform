# 第 11 课：Continuous Batching——推理服务的调度

> 预计用时：2 小时
> 示例代码：就在这个文件夹里，和这份正文放在一起

## 这一课要回答的问题

前面几课里，模型一次只服务一个请求。真实的推理服务同时面对几十上百个用户，一块 GPU 又很贵。

1. 为什么要把多个请求“攒成一批”一起算？
2. 视觉模型的攒批方法（C++ 教程第 16 课），直接搬到大模型上会出什么问题？
3. 连续攒批（continuous batching）是怎么做的？它改善了什么，没有改善什么？
4. 推理服务的好坏用哪几个数字衡量？

这一课**不做真正的推理**。我们写一个模拟器：按一个假设的成本模型推进时间，比较不同的调度方式。调度问题只关心“每一步花多长时间、谁在批里”，不关心算出来的数是什么，所以用模拟就能讲清楚。

## 1. 为什么要攒批

GPU 做一次前向计算，有一部分开销和“同时算几条序列”几乎无关：读一遍模型的全部权重、启动每一层的计算、框架本身的调度。模型的权重有几个 GB 到几十 GB，解码一步时每条序列只有一个新 token，所以时间主要花在“把权重过一遍”上。再多带几条序列，权重还是只过一遍，时间只增加一点。

这一课用下面的成本模型（**这是假设，不是测量**；真实数字取决于模型和硬件）：

```cpp
struct CostModel {
    Us stepFixedUs = 20000;      // 每一步的固定开销：20 ms
    Us stepPerSeqUs = 500;       // 每条正在解码的序列：0.5 ms
    Us prefillPerTokenUs = 20;   // Prefill 里每个提示词 token：0.02 ms
};
```

“一步”指一次前向计算。按这个模型算一算：

| 批大小 | 一步的耗时 | 每秒生成的 token 数 |
|---|---|---|
| 1 | 20.5 ms | 49 |
| 4 | 22 ms | 182 |
| 16 | 28 ms | 571 |
| 64 | 52 ms | 1231 |

批大小从 1 到 16，每一步只慢了三分之一，产出却多了十几倍。这就是攒批的全部理由：**固定开销被更多的序列分摊了**。

代价也在表里：批越大，每一步越慢，每条序列拿到下一个 token 要等的时间越长。批大小 64 时，每个用户看到的出字速度只有批大小 1 时的四成。吞吐和单个用户的体验是一对要权衡的量。

## 2. 衡量推理服务的四个数字

| 指标 | 含义 | 谁关心 |
|---|---|---|
| **吞吐**（token/s） | 整个服务每秒一共生成多少个 token | 付钱买 GPU 的人 |
| **TTFT**（首字延时） | 从请求到达，到第一个 token 生成出来 | 用户：发出问题后多久开始有反应 |
| **TPOT**（每个 token 的间隔） | 开始出字之后，相邻两个 token 之间隔多久 | 用户：出字流不流畅 |
| **总延时** | 从请求到达，到最后一个 token 生成出来 | 后面还要处理结果的程序 |

TTFT 和 TPOT 在[第 9 课](../lesson09/README.md)里对单个请求测过。到了服务里，TTFT 多了一项：**排队等待的时间**。重负载下它往往比 Prefill 本身长得多。

延时类的指标不能只看平均值，要看**百分位**：P50 是中位数，P99 是“100 个请求里最慢的那一个”的水平。服务的承诺通常写成“P99 首字延时小于多少”。C++ 教程第 14 课说过实时系统要看最坏情况，这里是同一个道理。

## 3. 第一种做法：静态攒批

最直接的做法，是把 C++ 教程[第 16 课的推理服务](../../cpp/lesson16/README.md)搬过来：等凑够一批请求（或者等够一段时间），组成一批，一起算完，再组下一批。

对视觉模型这样做没有问题：每张图只做**一次**前向，一批里所有图同时进去、同时出来。

大模型不一样：**一个请求要做很多步，而且每个请求的步数不同**。有的回答 20 个 token，有的 500 个，事先还不知道。一批里的请求同时开始，却不同时结束。

示例程序的第一部分画出了这个过程。6 个请求，批大小 3，每行是批里的一个位置，每列是一步：

```
请求（到达时刻/输出长度）：A(0/2) B(0/9) C(0/3) D(1/4) E(2/2) F(3/3)

  静态攒批：
    位置 0 |AA.......DDDD|
    位置 1 |BBBBBBBBBEE..|
    位置 2 |CCC......FFF.|
    全部完成于第 13 步；完成时刻：A=2 B=9 C=3 D=13 E=11 F=12 ；白算 16 格
```

字母表示这一步在给这个请求算 token，`.` 表示白算。三个问题都在图上：

1. **位置被占着白算。** A 两步就结束了，但这一批要等 B 跑完 9 步。这期间位置 0 仍然在批里，每一步照样参与计算，算出来的东西直接丢掉。13 步 × 3 个位置共 39 格，白算了 16 格。
2. **新请求要等一整批结束。** D 在第 1 步就到了，位置 0 从第 2 步起就在白算，D 却要等到第 9 步才能开始。它的首字延时取决于**别人**的回答有多长。
3. **提示词要填充对齐。** 一批里的提示词长度不同，要组成一个矩形的张量，短的得填充到和最长的一样长，填充的部分也要算。（图上没画，模拟器里记了账。）

## 4. 第二种做法：连续攒批

问题的根源是“批一旦开始就不能变”。大模型是一步一步生成的，步与步之间是天然的停顿点，完全可以在这里调整批的成员：

> **每一步结束后**：生成完的序列立刻离开，位置空出来。
> **每一步开始前**：有空位，并且有请求在等，就让它们进来。

这就是连续攒批，也叫迭代级调度（iteration-level scheduling）：调度的单位从“一个请求”变成了“一步”。

同样的 6 个请求：

```
  连续攒批：
    位置 0 |AADDDD   |
    位置 1 |BBBBBBBBB|
    位置 2 |CCCEEFFF |
    全部完成于第 9 步；完成时刻：A=2 B=9 C=3 D=6 E=5 F=8 ；白算 0 格
```

A 在第 2 步结束，D 第 3 步就顶上来了。全部完成从 13 步缩短到 9 步，D 的完成时刻从 13 提前到 6，没有一格白算。

### 新来的请求怎么和正在解码的排在同一批

你可能会问：新来的 D 要做 Prefill（一次处理整个提示词），B 正在做解码（一次处理一个 token），它们怎么能放在同一次前向里？

可以，因为有 KV Cache（第 9 课）。对模型来说，两者做的是同一件事：“给定这条序列已经缓存的历史，处理这一批新 token”。区别只是 D 的历史是空的、新 token 有几百个；B 的历史有几百个、新 token 只有 1 个。一次前向里，各条序列的新 token 数可以不同。

模拟器里，一步的耗时就按这个算：

```cpp
now += cost.stepFixedUs + cost.stepPerSeqUs * decoding + cost.prefillPerTokenUs * prefillTokens;
```

`decoding` 是这一步之前就在批里的序列数，`prefillTokens` 是这一步新接纳的请求的提示词 token 总数。

整个调度循环（[`batching_sim.cpp`](batching_sim.cpp) 里的 `runContinuous`）只有三段：

```cpp
while (next < reqs.size() || running > 0) {
    // 1. 接纳：有空位，并且有已经到达的请求
    for (auto& slot : slots) {
        if (next >= reqs.size() || reqs[next].arriveUs > now) break;
        if (slot != -1) continue;
        slot = static_cast<int>(next);
        prefillTokens += reqs[next].promptLen;
        ++running; ++next;
    }
    ...
    // 2. 跑一步
    now += cost.stepFixedUs + cost.stepPerSeqUs * decoding + cost.prefillPerTokenUs * prefillTokens;

    // 3. 每条序列得到一个 token；生成完的离开
    for (std::size_t i = 0; i < slots.size(); ++i) {
        ...
        if (r.generated == 0) r.firstTokenUs = now;
        if (++r.generated == r.outputLen) { r.finishUs = now; slots[i] = -1; --running; }
    }
}
```

把批大小上限设成 1，它就是“逐条处理”。所以示例里的逐条处理直接调用 `runContinuous(reqs, cost, 1)`。

## 5. 模拟：三种调度方式的对比

负载是 200 个请求。提示词和输出的长度都是“多数短、少数很长”：80% 的提示词在 32～255 个 token，20% 在 512～2047；70% 的输出在 16～127 个 token，30% 在 128～511。平均每个请求输出约 150 个 token。

下面是程序的输出。**这些数字是在上面那个假设的成本模型下模拟出来的，不是真实系统的测量**；要看的是三种方式之间的差别从哪里来。

```
轻负载：200 个请求，平均每 4.00 秒到达一个；批大小上限 16，静态攒批最多等 0.5 秒
            token/s  TTFT P50  TTFT P99  总延时 P50  总延时 P99   平均批     白算
  逐条处理       32      0.30     15.72       3.92      19.24      1.0     0.0%
  静态攒批       32      0.53      8.04       2.96      14.56      1.4    20.2%
  连续攒批       32      0.02      0.06       1.93       9.98      1.3     0.0%

重负载：200 个请求，平均每 0.15 秒到达一个；批大小上限 16，静态攒批最多等 0.5 秒
            token/s  TTFT P50  TTFT P99  总延时 P50  总延时 P99   平均批     白算
  逐条处理       49    243.06    513.82     251.04     515.95      1.0     0.0%
  静态攒批      167     46.85    114.57      57.10     124.43     14.9    67.8%
  连续攒批      503      3.37     14.73       9.65      23.89     13.9     0.0%
```

时间单位是秒。

### 轻负载：差别在延时

三种方式的吞吐都是 32 token/s。这不是它们的能力，而是**请求只来了这么多**：服务有空闲时，吞吐等于到达的速度，谁也快不了。

差别在延时上：

- **逐条处理**的首字延时中位数 0.30 秒，P99 却有 15.72 秒。大部分请求到达时服务是空的；偶尔前面正好有一个长回答，就得等它全部生成完。
- **静态攒批**的首字延时中位数是 0.53 秒，比逐条处理还差：它要先等 0.5 秒看能不能凑够一批。轻负载下凑不够，白等。
- **连续攒批**的首字延时中位数 0.02 秒，P99 是 0.06 秒：来了就进，不等人。

### 重负载：差别在吞吐

每 0.15 秒来一个请求，每个请求平均要 150 个 token，相当于每秒要生成约 1000 个 token。逐条处理每秒只能生成 49 个，请求越积越多，最后一批请求排了 500 多秒。

- **静态攒批**的平均批大小有 14.9，看起来批是满的，吞吐却只有 167 token/s。原因在最后一列：**67.8% 的计算是白算的**。输出长度差别越大，白算越多：一批 16 个里只要有一个 500 token 的长回答，其余 15 个位置就陪它空转几百步。
- **连续攒批**的平均批大小 13.9，没有白算，吞吐 503 token/s，是静态攒批的 3 倍。

### 连续攒批没有解决的事

重负载下，连续攒批的首字延时中位数仍有 3.37 秒。原因很简单：到达的速度（约 1000 token/s）超过了批大小 16 时的处理能力（第 1 节的表：571 token/s），请求还是在排队。连续攒批让 GPU 不做无用功，但**不能让 GPU 变快**。这时的选择只有三个：调大批大小上限（每个用户的出字变慢，显存占用变多）、加机器、拒绝一部分请求。练习 1 会让你试第一个。

## 6. 真实的调度器还要处理什么

模拟器里的调度器只有“批大小上限”一个约束。真实的推理服务还要考虑下面这些，它们是读调度器源码（[第 14 课](../lesson14/README.md)）时会遇到的主要内容：

| 问题 | 说明 |
|---|---|
| **显存是真正的上限** | 批里每条序列的 KV Cache 都要占显存，而且随着生成越来越长。能不能接纳一个新请求，取决于还有没有地方放它的缓存。这是[下一课](../lesson12/README.md)的内容 |
| **长提示词会卡住别人** | 新请求的 Prefill 和别人的解码在同一步里。来一个几千 token 的提示词，这一步就特别慢，批里所有人的出字都顿一下。做法是**分块 Prefill**（chunked prefill）：把长提示词切成几段，每一步只处理一段。也可以给每一步设一个“token 预算”（练习 3） |
| **显存不够时的抢占** | 序列越生成越长，可能出现“批里的序列都还没结束，显存已经满了”。这时要挑一条暂停（抢占），把它的缓存让出来，以后再重新算 |
| **调度顺序** | 模拟器是先来先服务。也可以按优先级，或者让短请求先走 |
| **调度器自己的开销** | 调度逻辑在 CPU 上跑，每一步都要执行。模型很小或者批很大时，它本身会成为瓶颈 |

## 7. 和项目、岗位的关系

**和项目。** 本项目的推理服务（C++ 教程第 16 课的 `inference_worker.cpp`）是视觉模型的动态攒批：推理线程每次从队列里“有多少取多少，最多 `maxBatchSize_` 个”，组成一批，推理一次，分发结果。两者对比：

| | 视觉模型的动态攒批（第 16 课） | 大模型的连续攒批（这一课） |
|---|---|---|
| 一个请求要几次前向 | 1 次 | 几十到几千次，事先不知道 |
| 批的成员什么时候变 | 每次前向都是全新的一批 | 每一步都可能有人离开、有人加入 |
| 请求之间有状态吗 | 没有 | 有：每条序列有自己的 KV Cache，要一直留到它结束 |
| 调度要考虑的资源 | 批大小 | 批大小，加上 KV Cache 占的显存 |
| 结果怎么返回 | 一次性：兑现一个 `future` | 流式：每一步给每个请求推送一个 token |

换个角度看：把大模型的“一步”当成视觉模型的“一次推理”，连续攒批就是第 16 课那个循环，只是队列里的任务跑完一步后**自己回到批里**，直到生成完为止。如果项目以后加入“用视觉语言模型描述缺陷”一类的算子，多个工位共用一个模型时，就需要这一课的调度方式。

**和岗位。** 三份岗位描述里对应的是：

- “熟悉 LLM 推理优化核心技术：……Continuous Batching……”
- “提升单卡及集群推理吞吐与延时表现”“持续提升线上推理系统的资源利用率与服务质量”
- “负责推理引擎（如 vLLM、SGLang）的二次开发与定制化优化”——这两个框架的核心就是一个连续攒批的调度器

面试里常见的问法是：“静态攒批有什么问题”“连续攒批为什么能提高吞吐”“吞吐和延时怎么权衡”“TTFT 很高，可能是什么原因”。这一课的模拟结果可以直接用来回答。

## 8. 动手运行

用 CMake（在 `docs/tutorial/inference` 目录下）：

```bash
cmake --build --preset default --target l11_batching_sim
```

```bash
./build/bin/l11_batching_sim
```

或者直接编译这一个文件。**macOS / Linux**：

```bash
clang++ -std=c++17 -I../common batching_sim.cpp -o batching_sim && ./batching_sim
```

**Windows**：

```bat
cl /std:c++17 /EHsc /utf-8 /I..\common batching_sim.cpp && batching_sim.exe
```

程序结尾有一组自检：三种方式在重负载下的吞吐顺序、首字延时的顺序等。做练习时你会改参数，自检可能不再成立，这是正常的；想一想为什么不成立，本身就是练习的一部分。

## 9. 练习

1. **调批大小上限**：把重负载的批大小上限从 16 依次改成 4、32、64（`main` 里 `compare` 的第 4 个参数）。连续攒批的吞吐和首字延时怎么变？到多大时首字延时的中位数降到 1 秒以内？这时每一步要多少毫秒（按第 1 节的公式算），用户看到的出字速度是多少？
2. **改成本模型**：把 `stepFixedUs` 改成 2000（固定开销只有 2 ms）、`stepPerSeqUs` 改成 5000。先猜三种方式的吞吐还差多少，再运行。由此说明：攒批带来的好处取决于成本模型的哪个性质？
3. **长提示词卡住别人**：在 `runContinuous` 里记录每一步的耗时，输出其中最长的一步。它是由什么造成的？然后加一个限制：每一步新接纳的提示词 token 总数不超过 512（超过就留到下一步再接纳；单个提示词超过 512 的也要能进来）。最长的一步变成多少？首字延时变了多少？
4. **让输出长度更整齐**：把 `makeWorkload` 里的输出长度改成固定的 150。静态攒批的“白算”比例变成多少？吞吐和连续攒批还差多少？这说明连续攒批的收益主要来自哪里？
5. **短请求优先**（选做）：模拟器知道每个请求的输出长度。把连续攒批的接纳顺序从“先来先服务”改成“已到达的请求里输出最短的先进”。总延时的 P50 和 P99 各怎么变？这种策略在真实系统里的困难是什么？

## 10. 自测题
