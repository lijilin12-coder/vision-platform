# 第 12 课：PagedAttention——分页管理 KV Cache

> 预计用时：2 小时
> 示例代码：就在这个文件夹里，和这份正文放在一起

## 这一课要回答的问题

上一课的调度器只有一个约束：批大小上限。真实的约束是显存：批里每条序列都带着一份 KV Cache，而且越生成越长。

1. KV Cache 占多少显存？为什么它决定了一块 GPU 能同时服务多少条序列？
2. 给每条序列“按最大长度预留一段连续空间”，浪费在哪里？
3. 分页是怎么做的？块表、引用计数、写时复制各是什么？
4. 块取多大？

## 1. KV Cache 有多大

[第 9 课](../lesson09/README.md)讲过：每生成一个 token，每一层都要把这个 token 的 K 和 V 向量存下来，供后面所有的 token 使用。所以一个 token 占用的缓存是：

```
每个 token 的缓存 = 2（K 和 V）× 层数 × 每层的向量长度 × 每个数的字节数
```

拿一个 32 层、向量长度 4096、用 16 位浮点数存储的模型（7B 参数规模的常见配置）算一下：

```
2 × 32 × 4096 × 2 字节 = 524 288 字节 ≈ 0.5 MB / token
```

一条 2048 个 token 的序列，缓存是 1 GB。同一个模型的权重大约 14 GB（70 亿个参数 × 2 字节）。放在一块 24 GB 显存的 GPU 上，留给 KV Cache 的大约 10 GB，也就是**一共 2 万个 token 左右**。上一课说批越大吞吐越高；批能开多大，就看这 2 万个 token 的空间怎么分。

## 2. 最直接的做法：按最大长度预留

C++ 教程第 14 课延伸讲过缓冲区池：事先申请好一批固定大小的缓冲区，用的时候拿一个。搬到这里就是：每条序列进来时，给它一段连续的空间，大小按“最长可能有多长”算。

为什么要按最长算？因为**一条序列最终会生成多长，事先不知道**。它可能 20 个 token 就结束，也可能一直写到上限。空间要连续（注意力的计算最方便处理连续的数组），又不能中途不够，那就只能按上限留。

问题是大部分序列远没有那么长。上一课的负载里，序列最长可以到 2558 个 token（提示词最长 2047，输出最长 511），平均只有 500 多。按 2560 预留，每条序列留出的空间有八成是空的：

```
按最大长度预留（每条序列一段 2560 个 token 的连续空间）：

序列 1 |████░░░░░░░░░░░░░░░░░░░░|   用了 420
序列 2 |██░░░░░░░░░░░░░░░░░░░░░░|   用了 198
序列 3 |███████████████░░░░░░░░░|   用了 1630
        █ 已使用   ░ 预留了但空着
```

操作系统管这叫**内部碎片**：分出去了，但没用上。

### 那就按需增长？

另一个想法是先给一小段，不够了再扩大，像 `std::vector` 那样。C++ 教程第 14 课说过 `vector` 增长时要“申请一块更大的，把旧的搬过去”。对 KV Cache 来说：

- 搬一次就是在显存里复制几百 MB 到几 GB；
- 扩大的时候旧的和新的同时存在，瞬间要占两份空间；
- 序列们长短不一、来来去去，显存里很快变成“一段占用、一段空闲”交错的样子。空闲的总量够，却找不出一段**连续**的空间给新序列。这叫**外部碎片**。

两条路都不好走。根本的困难是“连续”这个要求。

## 3. 分页：不要求连续

操作系统在几十年前遇到过一模一样的问题：很多个进程，每个进程要多少内存事先不知道，物理内存只有一块。它的解法是**分页**：

- 把物理内存切成固定大小的**页**；
- 进程看到的是一段连续的地址，实际上由散落在各处的页拼成；
- 每个进程有一张**页表**，记录“我的第几页，放在物理内存的第几页”。

C++ 教程[第 15 课预备](../../cpp/lesson15a/README.md)里那张“进程看到的地址是虚拟的，由操作系统映射到物理内存”的图，背后就是页表。

PagedAttention 把这个办法原样搬到了 KV Cache 上：

| 操作系统 | KV Cache |
|---|---|
| 进程 | 序列 |
| 物理内存 | 事先申请好的一大块显存 |
| 页 | **块**（block）：固定能放若干个 token 的 K、V |
| 页表 | **块表**：这条序列的第 i 个逻辑块在哪个物理块 |
| 虚拟地址 → 物理地址 | 第 `pos` 个 token → 物理块 `table[pos / blockSize]` 里的第 `pos % blockSize` 格 |

```
物理块：    0     1     2     3     4     5     6     7
          ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
          │ A0  │ A1  │ B0  │ B1  │ A2  │     │     │     │
          └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘

序列 A 的块表：[0, 1, 4]      序列 B 的块表：[2, 3]
```

A 的三个块不相邻，没有关系：读 A 的第 9 个 token 时，查块表第 `9 / 4 = 2` 项得到物理块 4，取其中第 `9 % 4 = 1` 格。

好处：

- **按需分配。** 序列每写满一块才多要一块。最多浪费最后一块里没写满的部分。
- **没有外部碎片。** 所有块一样大，任何一个空闲块都能给任何一条序列用。
- **不用搬移。** 序列变长只是在块表末尾加一项。

### 实现

[`block_manager.h`](block_manager.h) 里的 `BlockManager` 一共一百多行。数据只有四样：

```cpp
std::vector<int> data_;       // 全部物理块，一次申请好：第 b 块是 data_[b * blockSize_ ...]
std::vector<int> refCount_;   // 每个物理块被多少条序列引用
std::vector<int> freeList_;   // 空闲的物理块（当作栈用）
std::map<SeqId, Sequence> seqs_;   // 每条序列的块表和长度
```

为了能检查“读出来的就是写进去的”，示例里每个 token 只存一个 `int`。真实系统里每一格是上面算过的那 0.5 MB。

追加一个 token（先不看中间那个分支）：

```cpp
bool append(SeqId id, int value) {
    Sequence& seq = seqs_.at(id);
    const int offset = seq.length % blockSize_;  // 新 token 落在最后一个块里的第几格
    if (offset == 0) {
        // 最后一个块正好写满（或者序列还是空的）：要一个新块
        const int block = allocate();
        if (block < 0) return false;             // 没有空闲块了
        seq.table.push_back(block);
    } else if (...) { ... }
    cell(seq.table.back(), offset) = value;
    ++seq.length;
    return true;
}
```

`append` 返回 `false` 表示显存用完了。这正是上一课第 6 节说的“显存是真正的上限”：调度器接纳新请求之前要问块管理器还有没有空闲块；批里的序列写不下去时，要决定暂停哪一条。

读一个 token，就是上面表格的最后一行：

```cpp
int read(SeqId id, int pos) const {
    const Sequence& seq = seqs_.at(id);
    const int block = seq.table[pos / blockSize_];
    return data_[block * blockSize_ + pos % blockSize_];
}
```

### “PagedAttention”这个名字

缓存不连续了，代价落在注意力的计算上。原来算注意力时，一条序列的全部 K 是一个连续的数组，直接做矩阵乘法。现在它们散落在各个块里，计算注意力的算子必须**拿着块表，一块一块地去取**。所以这个技术叫 Paged **Attention**：管内存的那一半很简单，难的是写出一个按块表取数、速度又不掉的注意力算子。那是 GPU 算子开发的工作，这一课只做管内存的这一半。

## 4. 共享：引用计数与写时复制

分页还带来一个连续存储做不到的好处：**多条序列可以共用同一个物理块。**

什么时候会有内容相同的 KV Cache？当两条序列的**开头一段 token 完全相同**时。KV Cache 里第 i 个位置的内容只取决于第 0～i 个 token（因果注意力，第 8 课），所以相同的前缀对应的缓存逐位相同。这种情况很常见：

- 一个应用的所有请求带着同一段很长的系统提示词；
- 多轮对话，每一轮的提示词都以上一轮的全部内容开头；
- 同一个提示词要生成多个不同的回答。

做法还是从操作系统学来的：

- **引用计数**：每个物理块记着有多少张块表指向它。释放序列时计数减一，减到 0 才真正归还。这和 `shared_ptr`（C++ 教程第 4 课）是同一个机制。
- **写时复制**（copy-on-write）：共享的块只能读。谁要往里写，先复制一份给自己，再写。

```cpp
// 复制一条序列：新序列和原序列内容相同，共享全部物理块，不复制任何数据。
SeqId fork(SeqId parent) {
    const Sequence copy = seqs_.at(parent);  // 只复制了块表和长度
    for (const int block : copy.table) ++refCount_[block];
    ...
}
```

什么时候会“往共享的块里写”？只有一种情况：最后一个块**没写满**，并且是共享的。写满的块以后再也不会被修改，可以放心地一直共享。这就是 `append` 中间的那个分支：

```cpp
} else if (refCount_[seq.table.back()] > 1) {
    // 最后一个块没写满，但是别的序列也在用它：不能直接写，先复制一份自己用（写时复制）
    const int shared = seq.table.back();
    const int own = allocate();
    if (own < 0) return false;
    for (int i = 0; i < offset; ++i) cell(own, i) = cell(shared, i);
    --refCount_[shared];
    seq.table.back() = own;
    ++copies_;
}
```

示例程序 [`paged_demo.cpp`](paged_demo.cpp) 的第一部分把整个过程打印了出来（8 个物理块，每块 4 个 token）：

```
  2. 序列 B 写入 5 个 token，然后 A 再写 4 个（A 的块不再相邻）：
    A：长度 10，块表 [0 1 4]
    B：长度 5，块表 [2 3]
    物理块的引用计数：1 1 1 1 1 0 0 0 （空闲 3 块）
  3. 从 A 复制出 C（不复制数据，只是引用计数加一）：
    A：长度 10，块表 [0 1 4]
    B：长度 5，块表 [2 3]
    C：长度 10，块表 [0 1 4]
    物理块的引用计数：2 2 1 1 2 0 0 0 （空闲 3 块）
  4. C 追加 1 个 token：最后一块没写满而且和 A 共享，先复制再写（写时复制）：
    A：长度 10，块表 [0 1 4]
    B：长度 5，块表 [2 3]
    C：长度 11，块表 [0 1 5]
    物理块的引用计数：2 2 1 1 1 1 0 0 （空闲 2 块）
  5. A 结束：只有 A 独占的块被释放，和 C 共享的块还在：
    B：长度 5，块表 [2 3]
    C：长度 11，块表 [0 1 5]
    物理块的引用计数：1 1 1 1 0 1 0 0 （空闲 3 块）
```

第 4 步：C 的块表最后一项从 4 变成了 5，物理块 4 的引用计数从 2 降到 1，前两块仍然共享。第 5 步：A 结束后只有物理块 4 被归还，块 0 和 1 还被 C 用着。

## 5. 模拟：能多放多少条序列

下面两组数字来自示例程序的第二、三部分。**这是模拟**：序列长度按上一课的分布随机生成，“显存”是一个能放 65 536 个 token 的数组。看比例，不看绝对数字。

### 预留和分页

不断加入新序列，直到放不下：

```
                             序列数   实际使用     利用率   块表总项数
  按最大长度预留                 25      10983      16.8%            -
  分页，每块    1 个 token      122      65318      99.7%        65318
  分页，每块   16 个 token      120      63908      97.5%         4053
  分页，每块   64 个 token      117      61322      93.6%         1017
  分页，每块  256 个 token       97      53359      81.4%          255
  分页，每块 2560 个 token       25      10983      16.8%           25
```

- 按最大长度预留只能放 25 条（65536 ÷ 2560），显存的利用率只有 16.8%。
- 每块 16 个 token 的分页能放 120 条，是预留的 4.8 倍。同样的显存，批可以开到将近 5 倍大。
- 最后一行：块和最大长度一样大时，分页就**退化成了预留**。两者是同一个方法的两头。

### 块取多大

表里从上到下，块越大，能放的序列越少：每条序列的最后一块平均有一半是空的，块越大空得越多。那为什么不取 1？

- **块表变长。** 每块 1 个 token 时块表有 6 万多项，每块 16 个时只有 4 千项。块表要传给 GPU 上的注意力算子，每一步都要用。
- **数据更零散。** 块越小，一条序列的数据在显存里散得越开，注意力算子取数越没有规律。连续的数据对硬件友好（C++ 教程第 14 课的“按存放顺序访问”），GPU 也一样。
- **共享只能以整块为单位。** 这一点对大块不利：前缀要凑满一整块才能共享，块越大，凑不满的零头越多。

所以块大小是一个要实测的参数，常见的取值是十几到几十个 token。提出 PagedAttention 的论文里默认用 16；写这一课时 vLLM 代码里的默认值是 64。以你读到的版本为准。

### 共享前缀

16 个请求，前 1000 个 token 是相同的系统提示词，之后各自再有 100 个 token：

```
  不共享：用了 1104 块
  共享：  用了 174 块，写时复制 16 次
```

不共享时每个请求 69 块（1100 ÷ 16 向上取整）。共享时，前缀的 62 个整块只存一份，每个请求自己只需要 7 块：62 + 16 × 7 = 174。1000 个 token 的前缀不是 16 的整数倍，多出来的 8 个 token 在一个半满的块里，每个请求第一次往里写时都触发一次写时复制，所以是 16 次。

省下的不只是显存。前缀的缓存已经有了，Prefill 时这 1000 个 token **不用再算**，首字延时也跟着降下来。

> **真实系统里怎么发现“前缀相同”**：示例里是显式调用 `fork`。服务端没有人告诉它哪些请求前缀相同，要自己发现。vLLM 的做法是给每个**写满的块**算一个哈希值（由这一块的 token 和它前面所有 token 决定），新请求来时按哈希值去查有没有现成的块，查到就直接引用。这叫自动前缀缓存（automatic prefix caching），见 vLLM 文档的 Automatic Prefix Caching 一篇。SGLang 用的是另一种数据结构：把所有序列的 token 组织成一棵基数树（radix tree），沿着树走就能找到最长的公共前缀。两者的目的相同。

## 6. 测试：怎么相信一个内存管理器是对的

内存管理的 bug 很难靠看输出发现：块泄漏了，程序照样跑，只是能容纳的序列慢慢变少；写时复制漏了一种情况，只是某条序列的内容偶尔被另一条改掉。

[`block_manager_test.cpp`](block_manager_test.cpp) 用了两个办法：

**不变量检查。** `BlockManager::invariantsHold()` 检查三件无论怎么操作都应该成立的事：每个块的引用计数等于它在所有块表里出现的次数；每张块表的项数正好够放下这条序列；引用计数为 0 的块都在空闲栈里。第三条就是“没有泄漏”。

**和一个朴素实现对拍。** 同时维护一份“显然正确”的答案：每条序列一个 `std::vector<int>`。然后随机地新建、追加、复制、释放 4000 步，每一步检查不变量，每隔一段把所有序列完整地读出来和 `vector` 比较：

```
随机测试：4000 步，写时复制 241 次，内存不足被拒绝 55 次，结束后空闲块 64/64
全部测试通过
```

输出里特意打印了“写时复制 241 次，内存不足被拒绝 55 次”，并且在测试里要求它们大于 0：随机测试最怕的是**根本没有走到**想测的那条路径，却报告通过。

## 7. 和项目、岗位的关系

**和项目。** 本项目里有两处用得上同样的思路：

- **图像缓冲区。** 现在每个算子每次都申请新的输出图像（C++ 教程第 14 课延伸）。图像大小是已知且固定的，所以用“固定大小的缓冲区池”就够了，不需要分页。分页解决的是“大小事先不知道、还会增长”的问题；问题不同，办法不同。能说清楚“为什么这里不需要分页”，和会写分页一样重要。
- **`Image` 的共享。** `Image` 的像素放在 `shared_ptr` 里，复制 `Image` 只复制指针，多个节点共享同一份像素。这就是引用计数。项目里的 `Image` 创建后不再修改，所以不需要写时复制；如果以后要支持“原地修改”的算子，就会遇到这一课的问题：改之前先看引用计数是不是 1。

**和岗位。** 对应的要求：

- “熟悉 LLM 推理优化核心技术：KV Cache 机制、PagedAttention……”
- “深入理解大模型的推理负载特性，熟悉 KV Cache 管理机制及主流高性能推理库的实现原理”
- “熟悉显存管理、计算图优化及算子融合技术”

常见的问法：“KV Cache 占多少显存，怎么算”“PagedAttention 解决什么问题”“块大小怎么取”“前缀缓存是怎么实现的”。还有一类追问来自硬件一侧：在一块自研的 NPU 或 GPU 上，注意力算子怎么按块表取数才不慢——那是[第 5 课](../lesson05/README.md)和[下一课](../lesson13/README.md)的话题接上这一课的地方。

想看原始出处，读提出这个方法的论文：*Efficient Memory Management for Large Language Model Serving with PagedAttention*（Kwon 等，SOSP 2023）。前三节把动机讲得很清楚。

1. **算一算显存**：选一个你感兴趣的开源模型，从它的配置文件里找到层数、向量长度（注意：有的模型 K、V 的头数比 Q 少，叫分组查询注意力，这时 K、V 的向量长度要按 K、V 的头数算）。它每个 token 的 KV Cache 是多少字节？一块 24 GB 的 GPU 放下权重之后，还能放多少个 token？
2. **故意写错**：把 `append` 里写时复制的那个分支整个删掉，运行 `block_manager_test`。哪些检查失败了？不变量检查能发现这个 bug 吗？为什么？再试另一个 bug：把 `release` 里的 `== 0` 改成 `<= 1`。
3. **把块管理器接进调度器**：把上一课的 `runContinuous` 改成由显存决定能不能接纳：接纳新请求之前，要求空闲块足够放下它的提示词；每一步给批里每条序列 `append` 一个 token，失败时暂停最晚进来的那条序列（释放它的块，放回等待队列，以后从头再来）。对比“按最大长度预留”（批大小上限 25）和分页（每块 16）两种情况下的吞吐和首字延时。
4. **预留水位**：练习 3 做完后会发现：接纳得太满，批里的序列一增长就不够用，频繁发生暂停。加一条规则：空闲块少于总数的某个比例时不再接纳新请求。这个比例取多少时吞吐最高？
5. **按哈希查找前缀**（选做）：给 `BlockManager` 加一个功能：每当一个块写满，计算“这一块以及它之前全部 token”的哈希值，记到一张 `哈希值 → 物理块` 的表里；提供一个函数，给定一串 token，返回能直接引用的现成的块。注意两件事：块被归还后要从表里删掉；哈希冲突怎么办。
