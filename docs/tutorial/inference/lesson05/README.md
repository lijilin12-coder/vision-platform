## 1. 为什么是矩阵乘法，以及怎么衡量

神经网络里耗时的算子，几乎都能归结成矩阵乘法：

| 算子 | 和矩阵乘法的关系 |
|---|---|
| 全连接层 | 本身就是 |
| 卷积 | 把每个窗口摊平之后是矩阵乘法（第 7 节） |
| 注意力（第 8 课） | 几次矩阵乘法加一次 softmax |
| 最近邻搜索（PatchCore） | 主要部分是矩阵乘法（第 8 节） |

所以每一种硬件的厂商，第一件事都是把矩阵乘法做到最快。这个运算在线性代数库 BLAS 里叫 **GEMM**（general matrix multiply），以后在各种源码里会反复看到这个名字。

**怎么衡量：GFLOPS。** 两个 n × n 的矩阵相乘，要做 n³ 次乘法和 n³ 次加法，一共 2n³ 次浮点运算。用它除以耗时，得到每秒做了多少次浮点运算；以十亿次为单位，就是 GFLOPS。它的好处是**和矩阵大小无关**，可以直接和硬件的能力比。

**硬件的上限怎么估。** 一个 CPU 核每秒最多能做的浮点运算次数，大致是：

```
主频 × 每个周期能执行几条乘加指令 × 一条指令处理几个数 × 2（一次乘加算两次运算）
```

写这份教程用的机器是 2.1 GHz 的 Xeon，支持 AVX2（一条指令处理 8 个 float）。假设每个周期能执行 2 条乘加指令（近些年的 x86 服务器核心通常如此，具体型号要查资料），单核上限大约是 2.1 × 2 × 8 × 2 ≈ **67 GFLOPS**。这个数只是个标尺，不必很精确：它告诉我们“1 GFLOPS”和“30 GFLOPS”分别意味着什么。

拿第 1 课的卷积来对一下：conv2 有 472 万次乘加，用了 6.0 ms，折合 **1.6 GFLOPS**，只有上限的 2% 左右。空间很大。

## 2. 起点：照着定义写

矩阵都按行存放在一段连续的 `float` 里。A 是 M × K，B 是 K × N，结果 C 是 M × N（[`gemm.h`](gemm.h)）：

```cpp
void naive(const float* a, const float* b, float* c, int M, int K, int N) {
    for (int i = 0; i < M; ++i)
        for (int j = 0; j < N; ++j) {
            float sum = 0;
            for (int k = 0; k < K; ++k) sum += a[i * K + k] * b[k * N + j];
            c[i * N + j] = sum;
        }
}
```

实测（`matmul` 的完整输出见第 6 节）：

| 矩阵大小 | 耗时 | GFLOPS |
|---|---|---|
| 256 × 256 | 17.6 ms | 1.9 |
| 768 × 768 | 572 ms | 1.6 |
| 1024 × 1024 | 8096 ms | 0.27 |

两个问题：

- **本身就慢**：1.9 GFLOPS，上限的 3%。
- **矩阵一大，慢得更厉害**：从 256 到 1024，计算量是 64 倍，时间却是 460 倍。

第二个问题的原因在最内层循环里的 `b[k * N + j]`：k 每加 1，访问的位置就往后跳一整行。这正是 C++ 教程第 14 课讲的“逐列遍历”。矩阵小的时候，整个 B 都在缓存里，跳着访问也无所谓；B 有 4 MB 时，每一步都跳过 4096 个字节，几乎每次访问都要去更慢的一级缓存甚至内存里取。

1024 比 768 差那么多，还有一个原因：缓存是分组的，地址相差 4096 字节整数倍的数据会被分到同一组里，而一组只能放十几条。1024 × 1024 时每一步恰好跳 4096 字节，同一列的 1024 个数互相挤占位置。这叫**冲突缺失**，是“2 的整数次幂大小的矩阵特别慢”这个现象的常见解释。

## 3. 第一步：交换循环顺序

把 j 和 k 两层循环交换，最内层就变成了“C 的一行 += 一个数 × B 的一行”：

```cpp
for (int i = 0; i < M; ++i)
    for (int k = 0; k < K; ++k) {
        const float aik = a[i * K + k];
        const float* brow = b + k * N;
        float* crow = c + i * N;
        for (int j = 0; j < N; ++j) crow[j] += aik * brow[j];   // 两边都是连续访问
    }
```

计算的内容完全一样，只是顺序不同。结果：256 时 **5.5 GFLOPS**（快 2.9 倍），1024 时 4.0 GFLOPS（比朴素写法快 15 倍以上），而且**不再随矩阵变大而崩溃**。

连续访问为什么快：一是相邻的数在同一个缓存行里（一行 64 字节，16 个 float），取一次能用 16 次；二是 CPU 发现你在顺序读，会提前把后面的数据取进缓存（硬件预取）。

现在的瓶颈换了：5 GFLOPS 左右，是一个周期只算两三个数的水平。数据已经送得够快，是**算得不够快**。

## 4. 第二步：SIMD

**SIMD**（single instruction, multiple data）：CPU 里有一组很宽的寄存器，一条指令可以同时对里面的好几个数做同样的运算。

| 指令集 | 哪些 CPU | 一个寄存器装几个 float |
|---|---|---|
| SSE2 | 所有 64 位 x86 | 4 |
| AVX2 + FMA | 2013 年以后的大多数 x86 | 8 |
| AVX-512 | 部分 x86 服务器和桌面 CPU | 16 |
| NEON | 所有 64 位 ARM（麒麟、Apple Silicon） | 4 |

FMA（fused multiply-add）是“乘加”指令：一条指令完成 `acc += a * b`。

在 C++ 里用 SIMD，是调用编译器提供的**内联函数**（intrinsics）。它们看起来像函数，其实每个对应一条指令。把上面最内层的循环改写成一次处理 8 个数：

```cpp
#include <immintrin.h>

const __m256 va = _mm256_set1_ps(aik);               // 8 个位置都是 aik
for (; j + 8 <= n; j += 8) {
    __m256 acc = _mm256_loadu_ps(crow + j);          // 读 crow[j..j+7]
    acc = _mm256_fmadd_ps(va, _mm256_loadu_ps(brow + j), acc);   // acc += va * brow[j..j+7]
    _mm256_storeu_ps(crow + j, acc);                 // 写回
}
for (; j < n; ++j) crow[j] += aik * brow[j];         // 剩下不足 8 个的，用普通写法
```

示例里的版本（`axpy4`）多做了一件事：**把 4 个 k 合并成一趟**。上面的写法每做一次乘加，就要读一次、写一次 `crow`；合并之后是读一次 `crow`、做 4 次乘加、写一次，读写内存的次数少了很多。

```cpp
__m256 acc = _mm256_loadu_ps(crow + j);
acc = _mm256_fmadd_ps(va0, _mm256_loadu_ps(b0 + j), acc);
acc = _mm256_fmadd_ps(va1, _mm256_loadu_ps(b1 + j), acc);
acc = _mm256_fmadd_ps(va2, _mm256_loadu_ps(b2 + j), acc);
acc = _mm256_fmadd_ps(va3, _mm256_loadu_ps(b3 + j), acc);
_mm256_storeu_ps(crow + j, acc);
```

结果：256 时 **32 GFLOPS**，是上一步的 6 倍，达到了上限的将近一半。

### 三件必须知道的事

**一、不同的 CPU 要写不同的代码。** AVX2 的代码在 ARM 上编译不过。`gemm.h` 的做法是用宏判断，并且**永远保留一份普通写法做回退**：

```cpp
#if defined(__AVX2__) && defined(__FMA__)
    ...  // x86
#elif defined(__aarch64__) || defined(_M_ARM64)
    ...  // ARM：vld1q_f32、vfmaq_f32、vst1q_f32，一次 4 个
#endif
    for (; j < n; ++j) ...   // 回退，也负责处理尾巴
```

**二、要告诉编译器“可以用这些指令”。** 编译器默认只用所有 64 位 x86 都有的 SSE2。`-march=native`（MSVC 是 `/arch:AVX2`）表示“按这台机器的 CPU 来”，`__AVX2__` 这个宏才会被定义。CMake 里对应 `inftut_example(... NATIVE)`。代价是：这样编译出来的程序放到更老的 CPU 上会直接崩溃（非法指令）。正式的库会把几种指令集的版本都编译进去，启动时检查 CPU 再选，这叫**运行时分发**。

**三、先看编译器有没有替你做。** 编译器能自动把简单的循环改成 SIMD，叫**自动向量化**。对第 3 节那个循环，实测：

| 编译器和选项 | 第 3 节的写法，256 × 256 |
|---|---|
| GCC 13，`-O2 -march=native` | 5.5 GFLOPS（没有自动向量化） |
| GCC 13，`-O3 -march=native` | 21 GFLOPS |
| Clang 18，`-O2 -march=native` | 20 GFLOPS |

同一份源码，换个编译器或选项就差 4 倍。所以动手写内联函数之前，先确认编译器到底生成了什么。最直接的办法是看汇编里有没有用到宽寄存器（x86 上是 `ymm`、`zmm`）：

```bash
g++ -std=c++17 -O2 -march=native -I../common -S matmul.cpp -o - | grep -c 'vfmadd.*ps'
```

`vfmadd…ps` 是“一次处理多个 float 的乘加”，`vfmadd…ss` 是“只处理一个”。在线工具 Compiler Explorer（godbolt.org）可以边改代码边看汇编。

## 5. 第三步：分块

SIMD 版本在 256 时是 32 GFLOPS，到 1024 时掉到了 **13 GFLOPS**。算得快了以后，瓶颈又回到了送数据上。

看循环的结构：算 C 的**每一行**，都要把整个 B 从头到尾用一遍。B 有 4 MB，而这台机器每个核的二级缓存是 2 MB（`lscpu` 可以看到），装不下。于是每算一行，B 就要重新从更远的地方读一遍。

**分块**（cache blocking）的办法：不要一次用整个 B，而是切出一小块，让所有的行都把这一小块用完，再换下一块。

```cpp
for (int k0 = 0; k0 < K; k0 += 64)           // B 的 64 行
    for (int j0 = 0; j0 < N; j0 += 256)      // B 的 256 列：这一块 64 × 256 × 4 字节 = 64 KB
        for (int i = 0; i < M; ++i)          // 所有的行轮流使用这一小块
            ...  // 和上一节一样的 SIMD 代码，只是范围限制在 [k0, k0+64) × [j0, j0+256)
```

这 64 KB 在处理 1024 行的过程中被用了 1024 遍，一直留在缓存里。

结果：1024 时 **26 GFLOPS**，是不分块的 2 倍，回到了和小矩阵差不多的水平。256 时没有收益（32 → 29，反而略慢）：整个 B 只有 0.25 MB，本来就在缓存里，分块只是多了几层循环。

这里有一条重要的经验：**瓶颈是会移动的。** 第 3 节的标量写法再怎么分块也没有用（练习 2），因为那时慢在计算上；等 SIMD 把计算加快了 6 倍，内存才成为瓶颈，分块才有效果。每做完一步都要重新测量，再决定下一步。

## 6. 第四步：多线程，以及完整的结果

C 的每一行只依赖 A 的同一行和整个 B，行和行之间互不相干。把行平均分给几个线程，每个线程写 C 的不同部分，不需要锁（C++ 教程第 15 课）。

```cpp
for (int t = 0; t < threads; ++t) {
    const int begin = M * t / threads, end = M * (t + 1) / threads;
    workers.emplace_back([=] { blockedRows(a, b, c, K, N, begin, end); });
}
for (auto& w : workers) w.join();
```

`matmul` 的完整输出（2.1 GHz 的 4 核 Xeon，GCC 13；你的结果会不同，看比例）：

```

256 × 256 的 float 矩阵相乘（每个矩阵 0.25 MB），每项取 5 次的中位数：
  1. 朴素（i-j-k）              17.58 ms     1.91 GFLOPS   最大误差 0.0e+00
  2. 交换顺序（i-k-j）           6.06 ms     5.53 GFLOPS   最大误差 6.7e-06
  3. SIMD                        1.05 ms    32.00 GFLOPS   最大误差 6.7e-06
  4. SIMD + 分块                 1.15 ms    29.30 GFLOPS   最大误差 6.7e-06
  5. SIMD + 分块 + 4 线程        0.79 ms    42.38 GFLOPS   最大误差 6.7e-06
  第 5 种比第 1 种快 22 倍

1024 × 1024 的 float 矩阵相乘（每个矩阵 4.00 MB），每项取 3 次的中位数：
  1. 朴素（i-j-k）          （跳过，加 --naive 运行；下面的误差是和第 2 种比）
  2. 交换顺序（i-k-j）         533.15 ms     4.03 GFLOPS   最大误差 0.0e+00
  3. SIMD                      164.34 ms    13.07 GFLOPS   最大误差 0.0e+00
  4. SIMD + 分块                81.90 ms    26.22 GFLOPS   最大误差 0.0e+00
  5. SIMD + 分块 + 4 线程       25.59 ms    83.91 GFLOPS   最大误差 0.0e+00
  第 5 种比第 2 种快 21 倍

各种写法的结果一致
```

1024 × 1024 上，朴素写法是 8096 ms，最后一种是 25.6 ms，相差 **316 倍**。

几点说明：

- **“最大误差”不是 0，但没有错。** `float` 的加法不满足结合律，加的顺序变了，最后几位就会不同。这在第 7 课做“两个后端的一致性验证”时还会遇到：不同实现之间只能要求“足够接近”，不能要求逐位相同。
- **4 个线程没有快到 4 倍。** 1024 时是 3.2 倍（多次运行在 2.3～3.2 倍之间，机器上同时有别的程序在跑时更低）；256 时只有 1.4 倍，因为整个任务才 1 ms，创建线程、等它们开始工作的开销已经占了不小的比例（这台机器上创建并等待 4 个空线程约 0.08 ms）。这就是需要线程池的原因（C++ 教程第 16 课延伸）。
- **离上限还有一半。** 单核 26～32 GFLOPS，上限估计是 67。成熟的库（OpenBLAS、Intel MKL、各推理引擎自带的实现）还会做：把要用的那块 B 重新排列成正好按访问顺序存放（packing）；让 C 的一小块在整个内层循环期间一直待在寄存器里；用 AVX-512；为每种 CPU 单独调块的大小。

**产品里不要用自己写的矩阵乘法。** 这一课是为了让你知道库里在做什么、性能数字该怎么读、遇到慢的算子该从哪里查起。

## 7. 卷积怎样变成矩阵乘法：im2col

卷积的每个输出值 = 输入的一个小窗口 × 卷积核，对应位置相乘再求和。这是一次内积。所有输出位置、所有卷积核的内积放在一起，就是矩阵乘法：

1. **im2col**（image to columns）：把输入的每个窗口摊平成一列。窗口有 `输入通道数 × k × k` 个数，一共有 `输出高 × 输出宽` 个窗口，得到一个矩阵。
2. 卷积核本来就可以看成 `输出通道数` 行、`输入通道数 × k × k` 列的矩阵，不需要转换。
3. 卷积核矩阵 × im2col 矩阵 = 输出，`输出通道数` 行、`输出高 × 输出宽` 列。

[`im2col.cpp`](im2col.cpp) 用两种方法各算一遍并比较：

```
输入 3×20×24，卷积核 8 个 3×3×3，输出 8×18×22
im2col 矩阵：27 行 × 396 列（10692 个数，是输入的 7.4 倍）
矩阵乘法：(8 × 27) × (27 × 396) → 8 × 396
直接卷积和 im2col + 矩阵乘法的最大误差：9.5e-07
结果一致
```

好处是**一份优化好的矩阵乘法，所有形状的卷积都能用**。代价写在输出里了：im2col 矩阵是输入的 7.4 倍大（3 × 3 的卷积核，每个输入值大约被复制 9 次），要多占内存，复制本身也要时间。所以推理引擎里卷积通常有好几种实现，按情况选：1 × 1 的卷积不需要 im2col，本身就是矩阵乘法；常见的 3 × 3 卷积有专门的写法。第 7 课会看到 ONNX Runtime 在优化模型时把普通的 `Conv` 换成它内部的另一种实现。

## 8. 最近邻搜索也是矩阵乘法

项目计划用 PatchCore 一类的方法做异常检测（[技术调研](../../../03-tech-research.md)第 4 节）：把正常样本的特征存成“记忆库”，检测时对图像上每个位置的特征，在记忆库里找最近的一个，距离越大越可疑。骨干网络交给推理引擎，**最近邻搜索要在 C++ 里自己实现**。

Q 个查询、N 个记忆库特征、每个 D 维，要算 Q × N 个距离。把距离的平方展开：

```
‖q − m‖² = ‖q‖² + ‖m‖² − 2·(q·m)
```

- `‖m‖²` 只和记忆库有关，方案上线时算一次。
- `‖q‖²` 对同一个查询是常数，不影响“谁最近”。
- `q·m` 对所有的 (q, m) 一起算，就是矩阵乘法：查询矩阵（Q × D）乘以记忆库的转置（D × N）。

[`knn.cpp`](knn.cpp) 的输出：

```
784 个查询 × 4096 个记忆库特征，每个 256 维（记忆库 4.0 MB），取 3 次的中位数：
  逐对相减求平方和：          465.7 ms
  矩阵乘法（1 个线程）：       72.7 ms，快 6.4 倍
  矩阵乘法（4 个线程）：       34.2 ms，快 13.6 倍
最近邻相同的查询：784 / 784；距离平方的最大误差 4.3e-04（距离平方本身在 363 左右）
结果一致
```

项目的节拍要求是 100 ms 以内。逐对计算的写法光这一步就超了，换成矩阵乘法才有可能放进去。

一个要小心的地方：这个公式是“两个大数相减得到一个小数”。两个特征非常接近时，真实距离接近 0，而 `‖q‖² + ‖m‖²` 和 `2·(q·m)` 都很大，相减之后误差可能比结果本身还大，甚至得到负数。实现时要把负数截成 0；需要精确距离时，对选出来的那一个最近邻再直接算一遍。

## 9. 怎么找到该优化的地方

这一课是直接告诉你“优化矩阵乘法”。实际工作中要自己找，方法是 C++ 教程第 14 课的延续：

1. **粗粒度计时**，找到最耗时的算子。第 1 课的逐层计时、项目里每个节点的耗时记录都是这个。
2. **算出 GFLOPS，和上限比。** 只有 1～2 GFLOPS，说明连 SIMD 都没有用上，或者访问顺序有问题；已经到上限的一半，就不值得再花力气，应该去减少计算量（量化、换模型）。
3. **用性能分析器看算子内部**（Linux 上 `perf record -g ./程序`，然后 `perf report`；其他平台的工具见 C++ 教程第 14 课）。在火焰图里，一个优化得好的推理程序应该是**少数几个计算函数占满宽度**。如果 `malloc`、`memcpy`、im2col 这类“搬数据”的函数占了很宽，问题就不在计算上。
4. **区分“算得慢”和“等数据”。** 这一课的第 4、5 两步就是这两种情况。一个简单的判断办法：把数据规模缩小到能放进缓存，GFLOPS 明显变高，就是在等数据。Linux 上 `perf stat -e cache-misses,instructions,cycles ./程序` 可以直接数出缓存缺失的次数，以及平均每个周期执行了几条指令。
5. **看汇编**，确认最内层循环是不是你以为的样子（第 4 节）。

GPU 和 NPU 上的思路相同，只是工具换成厂商提供的（比如英伟达的 Nsight），而且多了一类问题：数据在 CPU 和设备之间来回搬（第 7 课）。

## 10. 和项目的关系

| 这一课的内容 | 项目里对应什么 |
|---|---|
| 矩阵乘法的优化 | 项目不自己写，由推理后端（ONNX Runtime、MindSpore Lite）提供。但要会读它们的性能数字 |
| 最近邻搜索 | 异常检测的打分部分，要在 C++ 里实现，是这一课最直接的用处 |
| SIMD 的宏保护和回退 | 项目要在鸿蒙电脑（ARM，NEON）和 Windows（x86，AVX2）上运行，手写的 SIMD 必须两边都有，并且有普通写法兜底 |
| `-march=native` 的风险 | 发布给客户的程序不能用它编译：客户的 CPU 可能比开发机老 |
| 现有的算子 | `operators/src/` 下的 `to_gray`、`threshold` 用的是 OpenCV，它内部已经做了 SIMD。慢的时候先查访问顺序和多余的拷贝，不要急着手写 |

## 11. 动手运行

用 CMake（在 `docs/tutorial/inference` 目录下）：

```bash
cmake --build --preset default --target l05_matmul l05_im2col l05_knn
```

```bash
./build/bin/l05_matmul
```

直接调用编译器（在本课的文件夹里）。**macOS / Linux**：

```bash
clang++ -std=c++17 -O2 -march=native -I../common matmul.cpp -o matmul -pthread && ./matmul
```

**Windows**：

```bat
cl /std:c++17 /O2 /arch:AVX2 /EHsc /utf-8 /I..\common matmul.cpp && matmul.exe
```

`knn.cpp` 的命令相同，换文件名即可；`im2col.cpp` 只验证正确性，不需要 `-O2 -march=native`。朴素写法在 1024 × 1024 上要好几秒，默认跳过，想看就运行 `./matmul --naive`。

## 12. 练习

1. **去掉 `-march=native`**：不带这个选项重新编译 `matmul.cpp` 并运行。第一行打印的指令集变成了什么？第 3 种写法还比第 2 种快吗？为什么？
2. **给标量写法分块**：在 `gemm.h` 里加一个函数，循环结构和 `blockedRows` 相同，但最内层全部用 `axpyScalar`。在 `matmul.cpp` 里测量它。它比第 2 种写法快吗？和第 5 节的结论一致吗？
3. **调块的大小**：把 `kBlockK` 和 `kBlockJ` 分别改成 16、64、256、1024，测 1024 × 1024 的第 4 种写法。画出（或列出）GFLOPS 随块大小的变化。最好的那个块有多少字节？和你机器的缓存大小（Linux 上 `lscpu`，macOS 上 `sysctl hw.l1dcachesize hw.l2cachesize`）比一比。
4. **不是 2 的整数次幂**：把 `run(1024, 3, …)` 改成 `run(1000, 3, …)`，加 `--naive` 运行。朴素写法的 GFLOPS 和 1024 时差多少？
5. **算一算自己机器的上限**：查出 CPU 的主频和支持的指令集，用第 1 节的公式估算单核上限，再算出你的第 4 种写法达到了百分之几。
