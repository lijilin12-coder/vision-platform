# 第 10 课：采样与 Speculative Decoding

> 预计用时：2.5 小时
> 示例代码：就在这个文件夹里，和这份正文放在一起。本课的代码建立在 [第 8 课的 `tiny_gpt.h`](../lesson08/tiny_gpt.h) 和 [第 9 课的 `kv_cache.h`](../lesson09/kv_cache.h) 上

## 这一课要回答的问题

前两课里，每一步都取打分最高的 token（贪心）。这一课先讲从 logits 里选 token 的其他方法，再讲一个建立在上一课结论之上的加速方法：投机解码。

1. 温度、top-k、top-p 这三个参数各对概率分布做了什么？
2. Decode 一次只能出一个 token。有没有办法让目标模型的一次前向计算产生不止一个 token，同时输出一点都不变？
3. 这个办法什么时候真的能加速，什么时候反而更慢？

## 1. 从 logits 到 token

模型输出的 logits 是对词表里每种 token 的打分。贪心是取最大的那个。它的问题是：同样的提示词永远得到同样的回答，而且容易陷入重复。实际使用时通常是**按概率随机抽一个**，这叫**采样**。抽之前，可以用三个参数调整概率分布（[`sampling.h`](sampling.h)）。

### 温度

先把每个打分除以**温度** T，再做 softmax：

```cpp
probs[i] = std::exp((logits[i] - maxValue) / temperature);   // 然后除以总和
```

- T < 1：打分之间的差距被拉大，概率更集中在高分的 token 上，输出更确定。
- T > 1：差距被缩小，概率更平均，输出更随机。
- T 趋近于 0：概率全部集中到最高分上，就是贪心。

### top-k

只保留概率最大的 k 个，其余的概率清零，再重新归一化。作用是不让那些概率很小、但数量很多的 token 被抽到。

### top-p

也叫 nucleus 采样。从大到小累加概率，加到总和刚达到 p 为止，保留这些，其余清零：

```cpp
while (keep < order.size() && cumulative < p) {
    cumulative += probs[order[keep]];
    ++keep;
}
```

它和 top-k 的区别是**保留的个数不固定**：模型很确定时（一个 token 就占了 95%），只留一个；模型拿不准时，留很多个。

抽样本身的写法是：取一个 [0, 1) 上的随机数，从头累加概率，看它落在哪一段（`sampleFrom`）。

### 对推理引擎来说要注意的三点

- **采样在模型之外。** 模型只负责算出 logits，怎么选是引擎的事。这部分代码跑在 CPU 上，不在加速芯片上。
- **它的耗时和词表大小成正比，不能忽略。** top-k、top-p 要排序。词表十几万时，每一步对十几万个数排序并不便宜。上一课说 Decode 阶段比的是“每一步之外的固定开销”，采样就是其中一项。常见的做法是只找出最大的 k 个，不做完整排序（练习 1）。
- **随机数的种子要能指定。** 同样的种子要得到同样的输出，否则问题无法复现。示例里用的是教程自带的 `inftut::Rng`，在所有平台上给出相同的数。

三个参数同时使用时的先后顺序，各个引擎不完全一样。用哪个引擎，就看哪个引擎的文档。

## 2. 投机解码的想法

回到性能。上一课的结论是：

- Decode 一次前向计算只产生一个 token。为了这一个 token，全部权重都要读一遍。
- 一次前向计算处理很多个 token（像 Prefill 那样）时，平均每个 token 的代价可以小得多。在 GPU 上，一次处理几个 token 和处理一个 token 的耗时接近。

问题是 Decode 没法一次处理多个 token：第 2 个 token 是什么，要等第 1 个算出来才知道。

**投机解码**（speculative decoding）的办法是：**先猜，再验证。**

1. 用一个又小又快的**草稿模型**，从当前位置出发，连续生成 k 个 token。这是猜测。
2. 把这 k 个猜测一次性交给**目标模型**（真正要用的大模型）做**一次**前向计算。因为输入是已知的，这一次计算可以像 Prefill 那样同时处理 k+1 个位置，得到 k+1 行 logits。
3. 第 i 行 logits 说的是“在前面都按猜测来的前提下，目标模型自己认为第 i+1 个应该是什么”。从前往后比：猜对了就接受，直到第一个猜错的位置为止。
4. 猜错的位置上，目标模型的答案是现成的，直接用它。后面的猜测作废。

```
已有：            … C [D]                      [D] 是最后一个 token，还没喂给模型
草稿模型猜 4 个：      D → e1 → e2 → e3 → e4
目标模型一次算完：    [D   e1   e2   e3   e4]   输入 5 个 token
                      ↓    ↓    ↓    ↓    ↓
目标模型的答案：       t1   t2   t3   t4   t5
比较：              e1=t1 ✓  e2=t2 ✓  e3≠t3 ✗
这一轮的产出：        e1   e2   t3              3 个 token，目标模型只做了 1 次前向计算
```

关键在于第 3 步为什么是对的。目标模型的第 1 行输出 t1 只取决于 `… C D`，它就是目标模型本来会生成的第 1 个 token。如果 e1 = t1，那么第 2 行的输入 `… C D e1` 和目标模型自己生成时的输入完全一样，所以 t2 也就是它本来会生成的第 2 个 token。依此类推，直到第一个不相等的位置：那一行的输入仍然是对的，所以它的答案 t3 仍然有效；但再往后的行，输入里包含了猜错的 token，结果作废。

所以：**无论草稿模型猜得多差，最后的输出和只用目标模型逐个生成的结果完全相同。** 猜得差只影响速度，不影响结果。每一轮至少产出 1 个 token（全猜错时，就是 t1），最多产出 k+1 个（全猜对时，t(k+1) 是白送的）。

## 3. 实现（贪心版本）

[`speculative.h`](speculative.h) 里是完整的实现。它用到上一课的两样东西：带缓存的前向计算，以及缓存的 `truncate`。

两个模型各有一份 KV Cache。代码维持一个约定：**两份缓存里都放着“除了最后一个 token 以外”的全部 token；最后一个 token 记在 `pending` 里。** 一轮的核心部分：

```cpp
// 1. 草稿模型从 pending 出发，一个接一个地猜 k 个 token
std::vector<int> draft;
int last = pending;
for (int i = 0; i < k; ++i) {
    const Mat logits = forwardCached(m, draftCache, {last}, draftLayers);
    last = argmax(logits.row(0), vocab);
    draft.push_back(last);
}

// 2. 目标模型把 [pending, 猜的第 1 个, ..., 猜的第 k 个] 一次算完，得到 k+1 行 logits
std::vector<int> batch = {pending};
batch.insert(batch.end(), draft.begin(), draft.end());
const Mat logits = forwardCached(m, targetCache, batch);

// 3. 从前往后比，接受到第一个不一致为止
int acceptedNow = 0;
while (acceptedNow < k && draft[acceptedNow] == argmax(logits.row(acceptedNow), vocab)) ++acceptedNow;

// 4. 接受的 token，加上目标模型自己给出的下一个 token（猜错时是纠正，全对时是白送的一个）
std::vector<int> emitted(draft.begin(), draft.begin() + acceptedNow);
emitted.push_back(argmax(logits.row(acceptedNow), vocab));
```

**猜错之后要撤销。** 第 2 步里目标模型把 k+1 个 token 的 K、V 都写进了缓存，其中猜错位置之后的那些是基于错误输入算出来的，必须丢掉；草稿模型的缓存也一样：

```cpp
// 5. 恢复约定：缓存里只留下 pending 和被接受的 token，猜错的那些位置丢掉
const int keep = base + 1 + acceptedNow;
targetCache.truncate(keep);
draftCache.truncate(keep);     // 实际代码里还处理了“k 个全对时草稿缓存少一个位置”的情况
```

这就是上一课说 `truncate` 是“最简单的缓存管理”的用处。在真实的引擎里，这一步对应的是释放一部分缓存块。

## 4. 草稿模型从哪里来

真实系统里，草稿模型一般是同一系列里小得多的模型：它们用相似的数据训练，对“简单”的 token（常用词的后半截、标点、固定搭配）的预测和大模型大体一致。

我们的模型是随机权重，一个随机的小模型和一个随机的大模型毫无关系，接受率会接近 0。所以示例里**人为构造**了一对有关系的模型，这一点要说清楚：

- 目标模型有 8 层。**草稿模型就是目标模型的前 2 层**，后面直接接输出层。它的计算量约是目标模型的四分之一。
- 把目标模型第 3～8 层的输出乘上一个系数 `lateScale`。第 8 课讲过，每一层只是在主线上“添一点修正”；`lateScale` 越小，后 6 层添的修正越小，只算前 2 层的结果就越接近完整的结果。`lateScale = 0` 时两者完全相同，`lateScale = 1` 时就是一个普通的随机模型。

这样我们得到了一个可以调节“草稿模型有多准”的旋钮，用来观察接受率对速度的影响。它是模拟，不代表真实模型的接受率。（“用大模型自己的前几层当草稿”在真实系统里也有人做，但那需要专门训练模型，使它在前几层就能给出像样的预测。）

## 5. 验证：输出必须不变

[`speculative_test.cpp`](speculative_test.cpp) 对不同的 `lateScale` 和 k，比较投机解码和只用目标模型的输出：

```
贪心投机解码：目标模型 4 层，草稿模型 1 层，生成 40 个 token
 lateScale    k     接受率   验证轮数     输出
       0.0    1       100%         20     相同
       0.0    3       100%         10     相同
       0.0    8       100%          5     相同
       0.1    1        82%         22     相同
       0.1    3        62%         14     相同
       0.1    8        43%          9     相同
       0.3    1        58%         26     相同
       0.3    3        37%         20     相同
       0.3    8        18%         17     相同
       1.0    1        11%         36     相同
       1.0    3         5%         35     相同
       1.0    8         2%         35     相同
```

- **输出一栏全部是“相同”**，包括接受率只有 2% 的那一行。这就是第 2 节的结论。
- **“验证轮数”就是目标模型做了多少次前向计算。** 只用目标模型时是 40 次。草稿模型完全准确、k = 8 时只要 5 次；草稿模型很差时接近 40 次，一点没省。
- **k 越大，接受率越低。** 接受率是“被接受的 ÷ 猜的总数”。一轮里只要有一个猜错，它后面的全部作废，所以猜得越多，浪费的比例越高。

### 实测：在我们的实现上，投机解码全部更慢

“实测倍数”一列全部小于 1，连草稿模型百分之百准确的那几行也是。这不是程序写错了，而是加速的前提在这里不成立。

投机解码省的是“目标模型前向计算的**次数**”，前提是**一次处理 k+1 个 token 的前向计算，耗时和处理 1 个 token 差不多**。上一课第 6 节已经如实说明：我们的 `linear` 是朴素的单线程循环，处理 k+1 行的耗时就是处理 1 行的 k+1 倍。于是目标模型验证 k+1 个 token 的代价，和它自己老老实实生成 k+1 个 token 一样多，再加上草稿模型的开销，只会更慢。

### 估算：如果一次验证和一步 Decode 一样快

最后一列是一个**计算出来的数，不是测出来的**。它假设目标模型“一次验证 k+1 个 token”的耗时等于“Decode 一个 token”的耗时（Decode 受内存带宽限制、并行能力有富余的硬件上，k 不大时接近这样）。在这个假设下：

```
只用目标模型：  生成的 token 数 × 1 步
投机解码：      验证轮数 × 1 步  +  草稿模型的步数 × 草稿模型一步的相对代价（这里是 0.26）
估算倍数 = 前者 ÷ 后者
```

从这一列能读出加速的条件：

- **接受率要高。** `lateScale` 0.05 时最高 1.69 倍；0.2 时基本没有加速；草稿模型很差（最后三行）时，即使在理想硬件上也只有原来的三到七成速度，因为草稿模型的时间全部白花了。
- **草稿模型要便宜。** 即使百分之百猜对，也只有 1.6～2.4 倍，因为草稿模型的代价是目标模型的 0.26 倍，不是 0。练习 3 让你改这个比例。
- **k 不是越大越好。** `lateScale` 0.1 时，k = 4 比 k = 2 和 k = 8 都好。k 太小，每轮产出少；k 太大，后面的猜测大多作废。最优的 k 取决于接受率。

所以投机解码是一个**有条件的**优化：硬件上一次验证要足够便宜，草稿模型要又快又准。条件不满足时它是负优化。是否打开、k 取多少，要在自己的硬件和自己的负载上测，这正是第 5 节那张“输出相同”的表加上这一节这张耗时表要做的事。

还有一个代价这里没有体现：草稿模型也要占内存，也有自己的 KV Cache。在线上同时服务很多请求时（下一课），这部分资源本来可以用来多服务几个请求。

## 7. 采样时怎么办

上面是贪心版本：比较的是“两个模型打分最高的 token 是否相同”。如果用的是采样，目标模型的输出本身是随机的，就不能简单地比较是否相同了。这时用的是一条接受/拒绝规则。设目标模型给出的分布是 p，草稿模型给出的分布是 q：

1. 草稿模型按 q 抽一个 token x。
2. 以 min(1, p(x) / q(x)) 的概率接受 x。
3. 不接受时，按 max(0, p − q) 归一化之后的分布重新抽一个。

这条规则保证：**最后得到的 token，其分布恰好是 p**，和直接从目标模型采样没有区别。为什么成立，一句话的解释是：q 给得偏多的 token 按比例打折接受，折掉的那部分概率正好补给 q 给得偏少的 token。接受的概率是 Σ min(p, q)，两个分布重叠得越多，接受率越高。

`speculative_test.cpp` 的后半部分用数值验证了这一点：

```
采样版本的接受/拒绝规则，抽 200000 次：
  目标分布 p    ： 0.500 0.200 0.150 0.100 0.050
  草稿分布 q    ： 0.200 0.400 0.100 0.100 0.200
  实际抽到的比例： 0.499 0.202 0.149 0.101 0.049
  接受率：实测 0.651，理论值 Σ min(p, q) = 0.650
```

草稿分布和目标分布差得不少，但抽出来的比例和 p 一致。完整的推导和多个 token 连续接受时的处理，见提出这个方法的论文（Leviathan 等，*Fast Inference from Transformers via Speculative Decoding*，2023；Chen 等，*Accelerating Large Language Model Decoding with Speculative Sampling*，2023）。

## 8. 和项目、岗位的关系

- **岗位**：三份招聘要求里有两份点名了它（“Speculative Decoding”“投机采样”）。面试时要能回答三件事：为什么输出不变（第 2 节）；加速的条件是什么（第 6 节）；实现时对 KV Cache 有什么要求（第 3 节的撤销）。
- **方法**：这一课的做法可以照搬到任何优化上。先有一个“结果必须相同”的检查，再测耗时；测出来没有变快就如实记录，并且找出前提里哪一条不成立。C++ 教程第 14 课说的“没变快就把改动撤回”，在这里就是“条件不满足就不要打开”。
- **项目**：端侧设备上内存紧张，再放一个草稿模型往往不划算；而且端侧的 Decode 是否有富余的并行能力，要看具体的芯片。这是一个需要在真机上测了才能决定的选项，不要默认打开。

## 10. 练习

1. **top-k 不用完整排序**：`topK` 现在对整个词表排序。用 `std::nth_element` 或 `std::partial_sort` 改写它，只找出最大的 k 个。写一个小的计时程序：词表 10 万、k = 50 时，两种写法各要多久？和上一课测到的 TPOT 相比，这个耗时算大还是小？
2. **忘记撤销**：把 `generateSpeculative` 第 5 步里的 `targetCache.truncate(keep);` 注释掉，运行 `speculative_test`。哪些行变成了“不同”？为什么 `lateScale = 0` 的那几行可能仍然相同？做完改回去。
3. **草稿模型的代价**：把 `speculative_bench.cpp` 里的 `draftLayers` 从 2 改成 1 和 4，各运行一次。接受率、“草稿是目标的多少倍”、估算倍数分别怎么变？更准的草稿模型一定更好吗？
4. **让验证真的便宜**（接上一课练习 3）：如果你在上一课把 `linear` 改成了能有效利用“一次处理多行”的版本，重新运行 `speculative_bench`。“实测倍数”有没有超过 1 的行？没有的话，差在哪里？
5. **采样版本**（选做）：把第 7 节的规则接到 `generateSpeculative` 里，实现一个采样版本。怎么验证它是对的？（提示：不能再比较输出是否相同了。可以固定提示词，统计第一个生成的 token 的分布，和直接从目标模型采样的分布比较。）
