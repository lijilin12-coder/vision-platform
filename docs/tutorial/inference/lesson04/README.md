# 第 4 课：内存规划——张量生命周期与缓冲区复用

> 预计用时：2 小时
> 示例代码：就在这个文件夹里，和这份正文放在一起

## 这一课要回答的问题

到现在为止，我们只关心了“算得对”和“算得快”。这一课关心第三件事：**占多少内存。**

1. 一次推理的中间结果一共占多少内存？其中有多少是必须的？
2. 怎么在推理开始之前，就决定好每个中间结果放在哪里？
3. 这和 C++ 教程第 14 课延伸里的缓冲区池是什么关系？

岗位要求里的“显存管理”说的就是这件事。在 CPU 上它决定一台工控机能同时放几个模型；在 GPU 和 NPU 上，内存不够就是直接跑不起来。

## 1. 第 2 课的执行器是怎么用内存的

```cpp
std::vector<Tensor> values(plan.steps.size());  // values[i] 是第 i 步的输出
for (std::size_t i = 0; i < plan.steps.size(); ++i) {
    ...
    runNode(step.node, in, values[i]);
}
return std::move(values[plan.outputStep]);
```

两个问题：

- **每一步的输出都是一块新申请的内存。** 每次推理申请 18 次、释放 18 次。
- **所有的输出都留到推理结束。** 第 1 步 `conv1` 的输出在第 2 步用完之后就再也没人需要了，但它一直占着内存，直到函数返回。

这一课的示例网络（输入 64×64，第一层 16 个通道）里，18 个中间张量加起来是 1400 KB。数字不大，是因为图小。张量的大小和图像的面积成正比：一个 1×64×1024×1024 的 `float` 张量就是 256 MB，而一个真实的网络里这样大小的张量有很多个。

## 2. 生命周期：每个张量只需要存在一小段时间

执行顺序在编译时就定了，所以每个张量**从哪一步开始存在、到哪一步之后不再需要**，不用运行就能算出来。这段区间叫它的**生命周期**。

- 开始：产生它的那一步。
- 结束：最后一个用到它的那一步。

```cpp
inline std::vector<std::size_t> computeLastUse(const Plan& plan) {
    std::vector<std::size_t> lastUse(plan.steps.size());
    for (std::size_t i = 0; i < plan.steps.size(); ++i) {
        lastUse[i] = i;
        for (std::size_t src : plan.steps[i].inputs) lastUse[src] = i;  // 步骤是按顺序走的，后面的会覆盖前面的
    }
    lastUse[plan.outputStep] = plan.steps.size();   // 模型的输出要一直留到最后
    return lastUse;
}
```

把它画出来（[`memory_demo.cpp`](memory_demo.cpp) 的输出，`#` 表示这一步时它必须存在；先只看前四列）：

```

  #1   conv1      256.0  .##................  A       A
  #2   bn1        256.0  ..##...............  B       A (in-place)
  #3   relu1      256.0  ...##..............  A       A (in-place)
  #4   pool1       64.0  ....#######........  B       B
  #5   conv2a      64.0  .....##............  A       A
  #6   bn2a        64.0  ......##...........  C       A (in-place)
  #7   relu2a      64.0  .......##..........  A       A (in-place)

```

绝大多数张量只活两步：产生它的那一步，和下一步用它的时候。唯一的例外是 `pool1`：它是跳跃连接的起点，第 5 步用一次，第 10 步还要用一次，所以活了 7 步。

竖着看任意一列，最多只有 3 个 `#`。也就是说，**任何时刻同时需要存在的张量最多只有 3 个**，而第 2 课的执行器同时留着 18 个。

（`input` 不在表里：输入图像的内存在调用者手里。常量也不在：它们就是权重，一直在模型里。只有“算出来的”张量需要规划。）

## 3. 规划：生命周期不重叠的张量共用一块缓冲区

两个张量的生命周期如果不重叠，它们就可以先后使用**同一块内存**。问题变成：给每个张量指定一块缓冲区，生命周期重叠的不能用同一块，缓冲区的总大小越小越好。

[`memory_plan.h`](memory_plan.h) 里的 `planMemory` 用的是最直接的贪心做法：按执行顺序走一遍，**模拟**申请和归还。

```
轮到第 i 步：
    给它的输出找一块空闲的缓冲区
        够大的里面选最小的；都不够大，就选最大的那块，把它扩大；
        一块空闲的都没有，就新开一块
第 i 步做完：
    它的输入里，生命周期到此为止的，把缓冲区标记为空闲
```

注意“先给输出找缓冲区，再归还输入”这个顺序。卷积在算输出的时候还在读输入，所以输出不能和输入用同一块。

这里有一点要想清楚：**这个函数没有申请任何内存，也没有做任何计算。** 它只是在编译时把推理过程“演”了一遍，记下“第 i 步的输出放在第几块缓冲区”和“每块缓冲区要多大”。真正的内存在这之后一次申请好。

结果是上面那张表的 `buffer` 一列：18 个张量轮流使用 A、B、C 三块缓冲区。

```
2. 中间张量占用的内存：
  不规划（每个张量一块，留到最后）：18 块，共 1400.1 KB
  规划，不允许原地：3 块缓冲区，共 576.0 KB（A 256.0，B 256.0，C 64.0）
  规划，允许原地  ：3 块缓冲区，共 384.0 KB（A 256.0，B 64.0，C 64.0）
  同一时刻必须存在的张量最多 512.0 KB（不做原地时的下界）
  规划后是不规划的 41%（不原地）和 27%（原地）
```

1400 KB 变成 576 KB。

### 贪心不是最优的

输出里还有一个数：**下界 512 KB**。它是“同一时刻必须存在的张量加起来最多有多大”（第 2 步时 `conv1` 和 `bn1` 的输出同时存在，各 256 KB）。任何规划都不可能比它小，而贪心的结果是 576 KB，多了 64 KB。

多出来的部分是这样来的：到第 6 步时，A 被 `conv2a`（64 KB）占着，B 被 `pool1`（64 KB）占着——两块 256 KB 的缓冲区各自只用了四分之一，但新来的 `bn2a` 没有空闲的整块可用，只好新开一块 C。

原因是这里把内存分成了**一块一块**的。更好的做法是只申请一整块大内存，给每个张量规划的是它在这块内存里的**偏移量**，这样两个 64 KB 的张量可以挤在同一个 256 KB 的空位里。TensorFlow Lite 的规划器就是这样做的。那样问题变成一个二维的装箱问题，求最优解很难，实际用的仍然是贪心（通常是“先放大的张量”），但结果很接近下界。练习 4 让你试一试。

## 4. 原地执行

再看一遍 `relu`：

```cpp
for (std::size_t i = 0; i < x.data.size(); ++i) y.data[i] = std::max(0.0f, x.data[i]);
```

第 i 个输出只依赖第 i 个输入。如果 `y` 和 `x` 是同一块内存，读出 `x[i]`、算完、写回 `y[i]`，不会影响后面任何一个元素的计算。所以它可以**原地**（in-place）执行：输出直接覆盖输入，不需要第二块内存。

卷积不行：算位置 (5, 5) 的输出要读周围 3×3 的输入，如果位置 (4, 4) 的输出已经覆盖了输入，读到的就是错的。池化、全连接也不行。

```cpp
// 这种算子的输出能不能直接写在它的输入上。
// 条件是“每个输出元素只依赖同一位置的输入元素”。
inline bool canRunInPlace(OpType op) {
    return op == OpType::Relu || op == OpType::Add || op == OpType::BatchNorm || op == OpType::Softmax;
}
```

算子“能”原地执行还不够，还要**输入在这一步之后不再被别人需要**——否则就把别人要用的数据覆盖了。这又是一个生命周期的问题：

```cpp
if (mem.bufferOf[src] != kNoBuffer && lastUse[src] == i && ...)   // 这是 src 最后一次被用到
```

上面表格的最后一列是允许原地执行时的规划。`conv1 → bn1 → relu1` 三个张量始终在同一块缓冲区 A 里：卷积写进去，BatchNorm 原地改一遍，ReLU 再原地改一遍。总内存从 576 KB 降到 384 KB，是不规划时的 27%，而且**低于了上一节的“下界”**——因为那个下界假设输入和输出必须同时存在，原地执行打破了这个假设。

看第 10 步 `add2`：它的两个输入是 `bn2b`（在 C 里）和 `pool1`（在 B 里），两个都是最后一次被使用。规划器让它接手 C，结果写回 C；B 随后被归还。

## 5. 按规划执行

`PlannedExecutor` 在构造时把缓冲区一次申请好，之后每次推理只是按规划去用：

```cpp
PlannedExecutor(Plan plan, MemoryPlan mem) : plan_(std::move(plan)), mem_(std::move(mem)) {
    buffers_.resize(mem_.bufferSize.size());
    for (std::size_t b = 0; b < buffers_.size(); ++b) buffers_[b].data.reserve(mem_.bufferSize[b]);
}

const Tensor& run(const Tensor& input) {
    for (std::size_t i = 0; i < plan_.steps.size(); ++i) {
        const Step& step = plan_.steps[i];
        if (!needsBuffer(step)) continue;
        in.clear();
        for (std::size_t src : step.inputs) in.push_back(tensorOf(src, input));
        runNode(step.node, in, buffers_[mem_.bufferOf[i]]);   // 输出写进规划好的那块缓冲区
    }
    return *tensorOf(plan_.outputStep, input);
}
```

这里用到了第 1 课埋下的两个伏笔：

- 算子的 `Into` 版本把结果写进调用者给的张量，而不是返回一个新的。
- `Tensor::resize` 内部是 `std::vector::resize`，容量够用时只改大小，不重新申请内存。缓冲区的容量在构造时已经 `reserve` 够了。

另外，输入图像和常量现在直接用指针指过去（`tensorOf`），不再像第 2 课那样复制一份。

示例做了两项检查：

```
3. 按规划（原地）执行 3 次：和第 2 课执行器的最大差距 0；缓冲区的地址没有变（没有重新申请过内存）
```

- **结果逐位相同。** 内存规划只改变“结果放在哪”，不改变任何一步计算，所以差距必须是 0，不是“很小”。这一点和第 3 课不同。
- **缓冲区的地址前后没有变。** 这是在确认 `run` 里真的没有重新申请内存。

## 6. 生命周期算错了会怎样

内存规划的 bug 很特别，值得亲眼看一次。示例故意把 `pool1` 的生命周期算短，假装它只在第 5 步被用到，漏掉第 10 步的 `add2`：

```
4. 故意把 pool1 的生命周期算短（漏掉 add2 对它的使用）：输出和正确结果的最大差距 0.086
   程序没有崩溃，内存检查工具也不报错，只是结果错了。
```

`pool1` 的缓冲区在第 5 步之后被“归还”，随后被别的张量覆盖；到第 10 步 `add2` 去读它时，读到的是别人的数据。

- 程序**不崩溃**：那块内存是合法的、大小也够。
- AddressSanitizer **不报错**：没有越界，没有释放后使用。从它的角度看一切正常。
- 输出看起来仍然像一组概率，只是数值不对。

这就是 C++ 教程第 13 课说的“释放后使用”，只不过发生在我们自己管理的缓冲区里，工具看不见。**越是自己管理内存，工具能帮的忙越少。** 唯一可靠的防线是这一课一直在做的事：保留一个最简单、最不可能错的执行器（第 2 课的 `run`），把优化后的结果和它逐位比较。

## 7. 和图优化叠加

```
5. 先做第 3 课的图优化，再规划：
  不规划：632.1 KB
  规划，允许原地  ：3 块缓冲区，共 384.0 KB（A 256.0，B 64.0，C 64.0）
  输出和优化前的最大差距 7.2e-07
```

图优化之后节点从 19 个变成 14 个，中间张量少了，“不规划”时的内存从 1400 KB 降到 632 KB。但**规划之后**的结果和不做图优化时一样，都是 384 KB。

这不奇怪：Conv+BN、Conv+ReLU 融合去掉的那些中间张量，正好是原地执行已经“免费”处理掉的那些（BatchNorm 和 ReLU 本来就可以原地做）。两种办法在内存上殊途同归。融合额外省下的是计算（少遍历几次）。

## 8. 时间上有什么变化

```
6. 一次推理的耗时（重复 15 次取中位数）：
  第 2 课的执行器          12.949 ms
  按规划执行               12.932 ms
  图优化 + 按规划执行      13.033 ms
  （只申请、清零、释放第 2 课执行器用到的全部张量：0.029 ms）
```

（数字来自一台 2.1 GHz 的机器，你的结果会不同，看比例。）

**没有变化。** 三个数的差别在测量误差之内（多运行几次，它们的先后顺序会变）。最后一行解释了原因：把第 2 课执行器要申请的张量全部申请、清零、释放一遍，只要 0.03 ms，是一次推理的 0.2%。时间仍然全花在朴素的卷积上。

那为什么每个推理引擎都做内存规划？因为它解决的本来就不是“平均速度”的问题：

- **内存峰值。** 这是最直接的收益：27%。在内存只有几个 GB 的边缘设备上，或者显存固定的 GPU、NPU 上，它决定了模型能不能放得下、一次能处理几张图（批大小）、能同时加载几个模型。
- **延时稳定。** 申请内存的平均耗时很小，但偶尔会很慢（要向操作系统要新的内存页、多个线程争抢分配器）。产线看的是最坏情况（C++ 教程第 14 课），推理路径上没有内存申请，就少了一个不确定的来源。
- **长时间运行。** 每秒几十次、连续运行几个月，反复申请和释放大小不一的内存块会造成碎片（C++ 教程第 13 课的“没有泄漏但一直在涨”）。一次申请、永不释放，就没有这个问题。
- **GPU 上申请显存慢得多。** 所以 GPU 上的框架都自带显存池，不会每次都去找驱动要。

这是一个应该记住的例子：**一项优化值不值得做，要看它优化的是哪个指标。** 只看平均耗时，这一课做的事情毫无意义。

## 9. 和缓冲区池的关系

C++ 教程第 14 课延伸里实现过缓冲区池：用完的缓冲区不释放，放回池里，下次要的时候再拿出来。它和这一课的内存规划解决的是同一个问题，区别在于**什么时候做决定**。

| | 缓冲区池 | 内存规划 |
|---|---|---|
| 什么时候决定“谁用哪块” | 运行时，每次申请的时候 | 编译时，一次算好 |
| 需要事先知道什么 | 什么都不用知道 | 完整的执行顺序和每个张量的大小 |
| 推理时的开销 | 每次申请和归还要加锁、查找 | 没有，只是按下标取缓冲区 |
| 能不能保证峰值最小 | 不能，取决于申请的先后 | 可以在编译时算出峰值并优化它 |
| 适合 | 大小和顺序事先不知道 | 结构和形状固定的图 |

**池是运行时的复用，规划是编译时的复用。** 能在编译时知道的事情，就不要留到运行时再做——这一课和上一课其实是同一个想法。

真实的引擎两种都用：

- **形状固定时用规划。** ONNX Runtime 的“memory pattern”就是这个：记下一次推理里所有的申请，之后一次性申请一整块。TensorFlow Lite 的 arena planner 也是。
- **形状会变时退回到池。** 规划的前提是编译时知道每个张量多大。大语言模型里，输入的长度每次都不一样，中间张量的大小只有运行时才知道，静态规划就做不了，只能用池（arena）。
- **还有一类内存根本不是“中间结果”。** 大语言模型生成每个词时都要用到前面所有词的缓存（KV Cache，第 9 课），它跨越很多次推理、不断增长、每个请求的长度都不同。怎么管理它是大模型推理里最核心的内存问题，第 12 课的 PagedAttention 就是为它设计的一种“池”。

## 10. 和项目的关系

平台的执行引擎现在的做法，和第 2 课的执行器一样（[`executor.cpp`](../../../../core/contexts/execution/domain/src/executor.cpp)）：

```cpp
std::vector<PortValues> outputs(steps.size());   // 每个节点的输出
...
NodeOutputs result;
for (size_t i = 0; i < steps.size(); ++i) result[steps[i].node.id] = std::move(outputs[i]);
return result;
```

每个算子每次都申请新的输出图像，所有节点的输出留到检测结束。对一张 5MP 的图像，`to_gray → threshold → blob` 这样的流程里同时留着好几张 5MP 的图。

这一课的方法可以直接用上，但有三点不同要考虑：

- **输出是要给人看的。** `Executor::run` 把所有节点的输出都返回了，调试方案和显示结果时要用。所以“用完就复用”只能在不需要中间结果的运行模式下做——和第 3 课的算子融合是同一个取舍。
- **`Image` 是不可变的、共享的。** 复制一个 `Image` 只是多一个指针指向同一块像素（C++ 教程第 4 课），一个节点的输出可能被事件、界面、存图各自拿着。它什么时候“没人用了”，靠的是 `shared_ptr` 的引用计数，在运行时才知道。这种情况适合的是**池**而不是静态规划：引用计数归零时把像素内存还给池（C++ 教程第 14 课延伸里的 `buffer_pool.cpp` 就是这个设计）。
- **并行执行。** 节点如果并行执行（C++ 教程第 16 课延伸），就没有唯一的“第几步”了，生命周期要按图上的依赖关系算，而不是按一个线性的顺序。

所以对平台来说，结论是：**算子之间的图像用池，模型内部的张量用规划**——后者由推理引擎替我们做了。

## 12. 练习

1. **手算一遍**：只看生命周期图的前 5 行（`conv1` 到 `conv2a`），不允许原地。在纸上模拟贪心算法，写出每一步之后各块缓冲区的大小和占用情况，和程序的输出对照。
2. **把顺序写反**：在 `planMemory` 里，把“归还输入”挪到“给输出找缓冲区”的前面（并去掉原地的部分）。总内存变成多少？运行 `PlannedExecutor` 会发生什么？是哪种算子先出问题？
3. **卷积原地执行**：把 `OpType::Conv` 加进 `canRunInPlace`（还要去掉 `conv2dInto` 开头的 `assert(&x != &y)`）。结果差多少？为什么这次 AddressSanitizer 同样不报错？
4. **按偏移量规划**：实现第 3 节末尾说的做法——只用一整块内存，给每个张量分配偏移量。贪心规则：按张量从大到小的顺序处理；对每个张量，在所有和它生命周期重叠、并且已经放好的张量之间，找最低的一个放得下它的空位。不允许原地时，你的结果比 576 KB 小吗？能达到 512 KB 的下界吗？
5. **批大小**：把输入的 N 从 1 改成 4（`buildSmallResNet` 里的 `Shape{1, 3, size, size}` 和 `randomImage`）。规划后的内存变成多少？这解释了为什么“显存不够时先减小批大小”。
6. **想一想项目**：读 [`executor.cpp`](../../../../core/contexts/execution/domain/src/executor.cpp)。如果只在“运行模式”下提前释放不再需要的节点输出，`outputs[i]` 应该在什么时候清空？需要在 `ExecutionPlan` 里多存什么信息？（只写设计。）
