# 第 14 课：性能分析

> 预计用时：2 小时
> 示例代码：[`examples/lesson14/`](examples/lesson14/)

## 这一课要回答的问题

产线上每个零件留给检测的时间是固定的，叫**节拍**。超过节拍，零件就流走了。

1. 程序慢，怎么知道慢在哪里？
2. 怎么正确地测量时间？有哪些常见的测量错误？
3. C++ 里最常见的几类性能问题是什么？

## 1. 第一原则：先测量，再优化

竞赛里的性能问题几乎都是算法复杂度：O(n²) 换成 O(n log n)。工程里不一样，程序慢的原因通常**不在你以为的地方**。

凭感觉优化的典型结果是：花了两天把一个只占总时间 2% 的函数加快了 10 倍，整体快了不到 2%，代码却变得难读了。

正确的顺序：

1. **确定目标。** 节拍要求是多少？现在是多少？已经达标就不要动。
2. **测量，找到最耗时的部分。**
3. **只优化那一部分。**
4. **再测量，确认真的变快了，并且结果没有变。**

本项目的需求是 5MP 图像、约 6 个节点的流程在 100 ms 以内（NFR-03），POC-1 实测约 8 ms。**所以现在不需要做任何性能优化。** 这一课教的是方法，等真的需要时知道怎么做。

## 2. 正确地测量时间

### 用优化模式编译

这是最常见的错误。调试版本（`-O0`、`/Od`）里编译器不做任何优化，测到的数字**没有任何参考价值**。

同一个示例，同一台机器，逐行遍历一张 5MP 图像：

| 编译选项 | 耗时 |
|---|---|
| `-O0`（不优化） | 约 8 ms |
| `-O2`（优化） | 约 0.8 ms |

相差 10 倍。而且不优化时，各种写法之间的差距也会被扭曲。

| 编译器 | 优化选项 |
|---|---|
| Clang / GCC | `-O2` |
| MSVC | `/O2` |
| CMake | `-DCMAKE_BUILD_TYPE=Release` |

**性能只在优化版本上测；调试和内存检查只在调试版本上做。**

### 用单调时钟

```cpp
using Clock = std::chrono::steady_clock;

const auto start = Clock::now();
doWork();
const double ms = std::chrono::duration<double, std::milli>(Clock::now() - start).count();
```

用 `steady_clock`，不要用 `system_clock`。后者是“墙上时间”，系统自动校时时可能跳变，甚至倒退。

### 多测几次，取中位数

只测一次的结果不可信：程序第一次运行某段代码时要加载数据到缓存、向系统申请内存，会明显偏慢；运行过程中也可能被别的程序打断。

这在项目里能直接看到。POC-1 里连续检测 5MP 图像的实测结果：

```
[NG] ng_5mp.png    (16.3 ms)      ← 第一张
[NG] ng_5mp_1.png  (7.7 ms)
[NG] ng_5mp_2.png  (7.2 ms)
[NG] ng_5mp_3.png  (7.8 ms)
```

第一张比后面的慢一倍。这就是设计文档里“热启动时要预热模型”的原因：不能让产线上的第一个零件碰上最慢的那一次。

示例里的做法是重复 15 次，取**中位数**（[`examples/lesson14/benchmark.cpp`](examples/lesson14/benchmark.cpp)）：

```cpp
template <typename Fn>
double medianMs(int repeats, Fn&& fn) {
    std::vector<double> times;
    for (int i = 0; i < repeats; ++i) {
        const auto start = Clock::now();
        fn();
        times.push_back(std::chrono::duration<double, std::milli>(Clock::now() - start).count());
    }
    std::sort(times.begin(), times.end());
    return times[times.size() / 2];
}
```

中位数比平均值可靠：偶尔一次特别慢的结果不会把它带偏。

对实时系统，还要看**最坏情况**。平均 8 ms 但偶尔 150 ms，在节拍 100 ms 的产线上就是漏检。

### 别让编译器把你要测的代码删掉

```cpp
const auto start = Clock::now();
sumRowByRow(img);                 // 结果没有被使用
const auto end = Clock::now();
```

开了优化之后，编译器发现计算结果没人用，可能把整个调用删掉，测出来是 0。示例里把结果写进一个 `volatile` 变量，告诉编译器“这个值必须真的算出来”：

```cpp
volatile std::uint64_t sink = 0;
sink = sumRowByRow(img);
```

测出来的时间小得不合理时，先怀疑是不是被优化掉了。

## 3. 三个常见的性能问题

运行示例（数字来自一台 2.3 GHz 的机器，你的结果会不同，看比例）：

```
5MP 灰度图（2592×1944），每项重复 15 次取中位数：
  逐列遍历 / 逐行遍历：慢 1.98 ms，快 0.80 ms，相差 2.5 倍
  传值 / 传 const 引用：慢 0.36 ms，快 0.00002 ms，相差上万倍
  不预留 / 预留空间（500 万个 int）：慢 26.7 ms，快 4.3 ms，相差 6.1 倍
```

三组对比里，两种写法的**计算结果完全相同**。

### 问题一：访问内存的顺序

```cpp
// 逐行：按内存里的存放顺序访问
for (int y = 0; y < h; ++y)
    for (int x = 0; x < w; ++x) sum += pixels[y * w + x];

// 逐列：每一步都跳过一整行
for (int x = 0; x < w; ++x)
    for (int y = 0; y < h; ++y) sum += pixels[y * w + x];
```

只是交换了两层循环，速度差 2.5 倍。

原因是 CPU 的**缓存**。访问内存比做运算慢得多，所以 CPU 会把最近用到的内存及其**相邻的一小段**保存在缓存里。图像是按行存放的：

- **逐行遍历**：下一个像素就在隔壁，大部分时候已经在缓存里了。
- **逐列遍历**：下一个像素在 2592 个字节之外，几乎每次都要重新去内存里取。

对图像处理来说这是最重要的一条：**按数据在内存里的存放顺序访问。** 图像按行存放，所以外层循环是行，内层循环是列。

### 问题二：不必要的拷贝

```cpp
std::uint64_t firstPixelByValue(Gray img);          // 每次调用复制 500 万个字节
std::uint64_t firstPixelByRef(const Gray& img);     // 不复制
```

这就是第 3 课的内容。函数本身只读一个像素，传值的版本却花了 0.36 ms 去复制整张图。一个检测流程里如果这样传递 20 次，就白白用掉 7 ms，和整个流程的耗时相当。

项目里 `Image` 的像素放在 `shared_ptr` 里，复制一个 `Image` 只复制一个指针，所以按值传递也没有这个问题（第 4 课）。

### 问题三：反复申请内存

```cpp
std::vector<int> out;
out.reserve(n);                  // 一次申请够
for (int i = 0; i < n; ++i) out.push_back(i);
```

不预留空间时，`vector` 不够用了就申请一块更大的内存，把已有的元素搬过去，再释放旧的。500 万个元素要这样折腾二十多次。**事先知道大概有多少个元素时，先 `reserve`。**

更一般地说：**向系统申请内存是慢操作。** 在每秒执行几十次的检测循环里，要尽量避免每次都申请和释放大块内存。常见的做法是把缓冲区留着重复使用。这是本项目后续优化的方向之一，现在的 POC 里每个算子每次都申请新的输出图像。

### 其他常见问题

| 问题 | 表现 | 做法 |
|---|---|---|
| 算法复杂度 | 数据量翻倍，时间翻四倍 | 换算法。这仍然是影响最大的一项 |
| 循环里重复做同样的计算 | | 提到循环外面 |
| 用 `std::map` 做频繁查找 | | 元素少时用排序的 `vector`，多时用 `std::unordered_map` |
| 拿着锁做耗时的事 | 多线程反而更慢 | 缩小加锁的范围（第 15 课） |
| 在检测循环里读写文件、打印日志 | 耗时忽高忽低 | 交给另一个线程异步处理 |

## 4. 找出慢在哪里

### 第一步：粗粒度计时

先用计时把范围缩小到某个阶段。本项目的执行引擎已经为**每个节点**记录了耗时，命令行会直接打印出来：

```
[NG] ng_01_one_spot.png  (2.33 ms)
      n1 vision.image_input succeeded 0.005 ms
      n2 vision.to_gray     succeeded 1.273 ms
      n3 vision.threshold   succeeded 0.198 ms
      n4 vision.blob        succeeded 0.632 ms
      n5 vision.judge_count succeeded 0.007 ms
```

一眼看出灰度转换占了一半以上。这是最便宜也最有效的分析手段：**在设计时就把计时做进去。** 第 4 课的 `ScopedTimer` 可以给任意一段代码临时加上计时。

### 第二步：性能分析器

想知道某个阶段内部哪个函数最耗时，用**性能分析器**（profiler）。它的原理是：每隔一小段时间（比如 1 毫秒）中断程序一次，记下当时正在执行哪个函数。采样足够多之后，出现次数最多的函数就是最耗时的。

| 平台 | 工具 | 用法 |
|---|---|---|
| Windows | Visual Studio 性能探查器 | 菜单“调试 → 性能探查器”，勾选“CPU 使用率”，启动 |
| macOS | Instruments | `xcrun xctrace record --template 'Time Profiler' --launch -- ./程序`，或者在 Instruments 应用里选 Time Profiler |
| Linux | `perf` | `perf record -g ./程序`，然后 `perf report` |

分析时要用**带调试信息的优化版本**，这样既是真实的速度，又能显示函数名：

| 编译器 | 选项 |
|---|---|
| Clang / GCC | `-O2 -g` |
| MSVC | `/O2 /Zi` |
| CMake | `-DCMAKE_BUILD_TYPE=RelWithDebInfo` |

### 怎么读分析结果

分析器给每个函数两个数字：

| 数字 | 含义 |
|---|---|
| **自身时间** | 花在这个函数自己的代码上的时间 |
| **总时间** | 这个函数加上它调用的所有函数的时间 |

- 按**总时间**从大到小看，找到占比最大的那条调用路径。
- 沿着路径往下，找到**自身时间**大的函数，那里是真正在消耗 CPU 的地方。
- 特别留意出现在前面的 `malloc`、`free`、`memcpy`：它们分别意味着频繁申请内存和大量拷贝。

很多分析器能把结果画成**火焰图**：横向越宽的函数耗时越多，纵向是调用关系。找最宽的那几块就行。

### 阿姆达尔定律：先算一算值不值

一个函数占总时间的 10%，把它优化到无限快，整体也只能快 10%。**动手之前先看占比。** 占比小的地方，不值得为了性能牺牲代码的清晰。

## 5. 优化之后

1. **重新测量。** 确认变快了，快了多少。没变快就把改动撤回。
2. **运行测试。** 确认结果没变。优化引入 bug 是常事。
3. **写下原因。** 为了性能写得不那么直观的代码，要加注释说明为什么这样写、测得的效果是多少。

## 6. 动手运行

**macOS / Linux**：

```bash
clang++ -std=c++17 -O2 benchmark.cpp -o benchmark && ./benchmark
```

**Windows**：

```bat
cl /std:c++17 /O2 /EHsc /utf-8 benchmark.cpp && benchmark.exe
```

## 7. 练习

1. **对比优化和不优化**：分别用 `-O0` 和 `-O2`（Windows 上是 `/Od` 和 `/O2`）编译 `benchmark.cpp` 并运行。哪些数字变化最大？“逐列 / 逐行”的倍数在两种模式下一样吗？
2. **看看被优化掉是什么样**：把 `sink = sumRowByRow(img);` 改成 `sumRowByRow(img);`（不保存结果），用 `-O2` 编译运行。测到的时间变成了多少？
3. **测一测自己的猜想**：在 `benchmark.cpp` 里加一组对比：用 `for (auto x : img.pixels)` 和用下标两种方式遍历求和。先猜哪个快、差多少，再测。
4. **给项目计时**：用 Release 模式编译项目（`cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release`），用 `vision-cli sample-images` 生成示例图，再运行 `inspect`。哪个节点最耗时？第一张图和后面的图耗时差多少？
5. **用一次性能分析器**：用你平台上的分析器分析 `benchmark`。报告里排在最前面的函数是哪几个？和程序自己打印的结果一致吗？

## 8. 自测题

1. 为什么要“先测量，再优化”？
2. 为什么不能在调试版本上测性能？
3. 测量时间时，为什么要重复多次？为什么取中位数而不是平均值？
4. 程序第一次执行某段代码为什么常常比较慢？这和设计文档里的“预热”有什么关系？
5. 逐行和逐列遍历图像，计算量完全相同，为什么速度不同？
6. 性能分析器是怎么知道哪个函数耗时最多的？“自身时间”和“总时间”有什么区别？
7. 一个函数占总时间的 5%，值得花一周去优化它吗？为什么？
