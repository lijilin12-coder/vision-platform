# 第 12 课：调试技巧

> 预计用时：2 小时
> 示例代码：[`examples/lesson12/`](examples/lesson12/)

## 这一课要回答的问题

程序的结果不对。接下来怎么办？

1. 有没有一套固定的步骤，而不是东改西改碰运气？
2. 调试器怎么用？
3. 崩溃、结果不对、偶尔出错，各自该怎么查？

调试是工程里花时间最多的事情之一。会不会调试，效率能差出十倍。

## 1. 调试的步骤

竞赛里常见的做法是：盯着代码看，加几个 `cout`，改一改再试。程序小的时候这样可以，程序大了就不行了。

**调试是一个缩小范围的过程。** 每一步都要让“问题可能在的范围”变小。

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| **1. 稳定重现** | 找到一组输入，每次运行都出错 | 不能重现的问题没法验证有没有修好 |
| **2. 缩小输入** | 把输入一点点减小，直到再减就不出错为止 | 2×6 的网格比 2592×1944 的图像好分析得多 |
| **3. 读错误信息** | 完整地读，尤其是第一条 | 很多时候答案直接写在里面 |
| **4. 提出猜想** | “我猜是 X 的值不对” | 没有猜想，就不知道该看哪里 |
| **5. 验证猜想** | 用调试器或打印，看 X 到底是多少 | 用事实代替猜测 |
| **6. 修复** | 改代码 | |
| **7. 确认并留下测试** | 重新运行原来的输入；写一个测试防止它回来 | 第 11 课 |

最容易跳过的是第 5 步。很多人猜到一个可能的原因就直接去改代码，改完发现不对，再猜下一个。**先验证，再动手。**

### 二分法

不知道问题在哪一段时，在中间检查一次：到这里为止，数据还是对的吗？对，问题在后半段；不对，在前半段。重复几次就能定位到具体的几行。

对检测流程来说，这正是“调试运行”的用途：逐个查看每个节点的输出，找到第一个输出不对的节点。

```bash
./build/apps/vision-cli recipe debug <方案ID> 某张图.png
```

Git 也有二分工具：`git bisect` 可以在“昨天还好好的、今天坏了”时，自动找出是哪一次提交引入的问题。

## 2. 调试器

调试器让程序停在你指定的地方，然后查看和修改它的状态。三个平台各有一个：

| 平台 | 调试器 | 界面 |
|---|---|---|
| Windows | Visual Studio 调试器 | 图形界面，对初学者最友好 |
| macOS | LLDB | 命令行；也可以在 VS Code、CLion、Xcode 里用图形界面 |
| Linux | GDB（或 LLDB） | 同上 |

**编译时必须带调试信息，并且关闭优化**，否则看不到变量、行号也对不上：

| 编译器 | 选项 |
|---|---|
| Clang / GCC | `-g -O0` |
| MSVC | `/Zi /Od` |
| CMake | `-DCMAKE_BUILD_TYPE=Debug`（本项目的预设默认就是） |

> **用 VS Code 的话**：断点、单步、看变量都可以在图形界面里点，步骤和快捷键见 [在 VS Code 里编译、运行和调试](vscode-guide.md)，那里有一张“LLDB 命令 ↔ VS Code 操作”的对照表。这一课的正文仍然用命令行来讲，因为两种方式背后的概念完全一样。

### 基本操作

所有调试器都提供这几种操作，名字略有不同：

| 操作 | 作用 | Visual Studio | LLDB | GDB |
|---|---|---|---|---|
| 设置断点 | 程序运行到这一行时停下 | 点击行号左侧，或 F9 | `b debug_me.cpp:33` | `break debug_me.cpp:33` |
| 运行 | 开始或继续运行，直到下一个断点 | F5 | `run` / `continue` | `run` / `continue` |
| 单步跳过 | 执行当前行，不进入函数 | F10 | `next` | `next` |
| 单步进入 | 进入当前行调用的函数 | F11 | `step` | `step` |
| 跳出 | 执行完当前函数，回到调用处 | Shift+F11 | `finish` | `finish` |
| 查看变量 | 看当前的值 | 鼠标悬停，或“局部变量”窗口 | `frame variable`，`p 表达式` | `info locals`，`print 表达式` |
| 调用栈 | 现在在哪个函数里，是谁调用过来的 | “调用堆栈”窗口 | `bt` | `bt` |
| 条件断点 | 只在条件成立时才停下 | 右键断点 → 条件 | `breakpoint set -f 文件 -l 行 -c '条件'` | `break 文件:行 if 条件` |
| 监视点 | 某个变量被修改时停下 | “数据断点” | `watchpoint set variable x` | `watch x` |

**调用栈**是最有用的信息之一。程序崩溃时，它告诉你“在哪一行崩的，以及是经过哪些函数一路调用到这里的”。

**条件断点**在循环里特别有用：循环要执行一万次，问题只在某一次出现，就让它只在那一次停下。

## 3. 跟着做一遍

[`examples/lesson12/debug_me.cpp`](examples/lesson12/debug_me.cpp) 计算网格里最大连通块的面积。它能编译，不崩溃，内存检查也不报错，只是结果不对：

```
3×3 网格：最大连通块面积 = 4（应为 4）
2×6 网格：最大连通块面积 = 2（应为 6）
```

**建议先自己试着找一下，再往下看。**

### 第 1、2 步：重现和缩小

问题已经稳定重现了，输入也已经很小：`{"111111", "000000"}`。

注意一个线索：**3×3 的网格是对的，2×6 的不对。** 两者的区别是什么？一个是正方形，一个不是。

### 第 4 步：提出猜想

结果是 2，而不是 6。第一行有 6 个相连的 `1`，却只数到了 2 个。猜想：**搜索到第 2 列之后，没有继续往右走。** 可能是“往右的邻居”被某个条件挡掉了。

### 第 5 步：用调试器验证

编译：

```bash
clang++ -std=c++17 -g -O0 debug_me.cpp -o debug_me
```

在检查邻居是否越界的那一行（第 33 行）设置条件断点，只在处理 2×6 网格时停下：

**LLDB（macOS）**：

```
lldb ./debug_me
(lldb) breakpoint set --file debug_me.cpp --line 33 --condition 'rows == 2'
(lldb) run
(lldb) frame variable rows cols nextRow nextCol
```

**GDB（Linux）**：

```
gdb ./debug_me
(gdb) break debug_me.cpp:33 if rows == 2
(gdb) run
(gdb) print cols
(gdb) info locals
```

**Visual Studio（Windows）**：在第 33 行设置断点，右键 → “条件”，填入 `rows == 2`，按 F5。在“局部变量”窗口里查看。

程序停下后看到：

```
rows = 2
cols = 6
nextCol = 1
```

用 `continue`（Visual Studio 里是 F5）让它继续，观察每次停下时的 `nextCol`。当 `nextCol` 等于 2 时，单步执行（`next` 或 F10）：程序执行了 `continue`，跳过了这个邻居。

可是第 2 列明明在范围内（`cols` 是 6）。再仔细看这一行的条件：

```cpp
if (nextRow < 0 || nextRow >= rows || nextCol < 0 || nextCol >= rows) continue;
```

## 4. 答案

`nextCol >= rows` 应该是 `nextCol >= cols`。列的范围用成了行数。

- 正方形网格里 `rows == cols`，所以完全看不出问题。
- 2×6 的网格里，列号一到 2 就被当成越界，搜索只能走两格。

修复：把 `rows` 改成 `cols`。然后按第 7 步，把 `{"111111", "000000"}` 期望结果为 6 写成一个测试。

### 从这个例子学到什么

- **测试数据要有“不对称”的情况。** 只用正方形测试，这个 bug 永远发现不了。行数和列数不同、宽大于高、高大于宽，都要测。图像处理的代码里，宽和高写反是最常见的错误之一。
- **线索常常藏在“什么情况下对、什么情况下不对”的对比里。**
- 这个 bug 不会被内存检查发现，因为它没有越界访问，只是少算了。**工具不能代替思考。**

## 5. 用打印调试

调试器不是唯一的手段。下面这些情况，打印更合适：

| 情况 | 原因 |
|---|---|
| 问题和时间有关（多线程、实时采集） | 程序停在断点上时，时序就变了，问题可能不再出现 |
| 要观察很长一段时间里的变化趋势 | 一万次循环不可能逐次停下来看 |
| 问题只在产线上出现，没法接调试器 | 只能靠日志 |

打印调试的几个要点：

- **打印到 `std::cerr`**，它不带缓冲。程序崩溃时，`std::cout` 缓冲区里还没输出的内容会丢失，你会误以为程序没有执行到那里。
- **带上位置和变量名**：`std::cerr << "[markBlob] row=" << row << " col=" << col << "\n";`
- **用完删掉。** 调试用的打印不要提交。

长期保留的日志是另一回事：正式的程序有日志系统，带时间和级别，写入文件。本项目的日志见第 17 课。

## 6. 不同症状的查法

| 症状 | 先做什么 |
|---|---|
| **崩溃**（段错误、访问冲突） | 在调试器里运行，崩溃时看调用栈；没法重现时分析崩溃转储（第 17 课）；或者用内存检查工具重新编译运行（第 13 课），它会直接指出是哪一行、什么类型的错误 |
| **结果不对** | 缩小输入；用二分法找到第一个出错的中间结果；用调试器看那附近的变量 |
| **有时对有时错** | 多半是用了未初始化的变量、越界读，或者多线程的数据竞争。用内存检查和线程检查工具（第 13、15 课） |
| **只在优化模式下出错** | 几乎总是代码里有未定义行为。用内存检查和 UBSan（第 13 课） |
| **只在某个平台出错** | 查平台差异：路径编码、整数位数、求值顺序。本项目遇到过的见 [构建说明](../../dev/build.md) 的“跨平台编码约定” |
| **卡住不动** | 在调试器里中断程序（Ctrl+C，或 Visual Studio 的“全部中断”），看每个线程的调用栈，通常是在等一把锁或一个永远不会来的通知（第 15 课） |
| **越来越慢，或内存越来越大** | 第 13、14 课 |

## 7. 让 bug 更容易被发现

好的习惯能让很多 bug 在出现的那一刻就暴露出来，而不是等到很久以后：

| 习惯 | 作用 |
|---|---|
| 打开所有警告，并且不留任何警告 | 编译器能发现未使用的变量、有符号和无符号比较、漏掉的返回值等 |
| 日常开发用带内存检查的调试版本 | 越界、释放后使用，当场报错 |
| 用断言写下你的假设 | 假设不成立时立刻停在那一行 |
| 让非法状态创建不出来（第 5 课） | 错误在源头被拦住 |
| 每个 bug 留下一个测试（第 11 课） | 不会第二次遇到 |
| 小步提交 | 出问题时，要排查的改动很少 |

## 8. 练习

1. **亲手走一遍第 3 节**：用你平台上的调试器，按步骤设置条件断点、查看变量、单步执行，直到亲眼看到 `nextCol` 等于 2 时被跳过。
2. **修复并留下测试**：修好 `debug_me.cpp`。在 `main` 里再加两个不对称的测试用例：一个 6×2 的（6 行 2 列）、一个 1×1 的。
3. **用调用栈**：在 `largestBlobArea` 里的任意一行设断点，停下后查看调用栈。从上到下每一行分别代表什么？
4. **调试项目里的代码**：用调试器运行 `vision-cli`，在 [`recipe.cpp`](../../../core/contexts/authoring/domain/src/recipe.cpp) 的 `Recipe::connect` 里设断点，然后用命令行连接两个节点。停下后查看 `from` 和 `to` 的值，再单步执行，观察它依次做了哪些检查。
   - LLDB：`lldb -- ./build/apps/vision-cli recipe connect <方案ID> n1.image n2.image`
   - Visual Studio：打开项目文件夹，在“调试和启动设置”里填写命令行参数。

## 9. 自测题

4. 调用栈告诉你什么？
