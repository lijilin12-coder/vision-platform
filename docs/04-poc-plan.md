## 2. POC 清单

| 编号 | 内容 | 环境 | 预估 |
|---|---|---|---|
| **POC-1** | **核心骨架**：共享内核 + BC-1 / BC-2 / BC-3 的领域层和应用层 + 5 个算子 + JSON 仓储 + 命令行；CMake 强制上下文边界 | 开发机（Mac、Windows）、Linux | 5–7 天 |
| POC-3a | OpenCV 和核心交叉编译到鸿蒙 + NAPI 调用 + ArkUI 显示结果 | 开发机 + Ubuntu 22.04（Docker 或 WSL2）+ 鸿蒙模拟器 | 4–6 天 |
| POC-3b | ArkWeb 嵌入 Web 界面 + 桥接调用核心；对比三种桥接方式 | **鸿蒙电脑真机** | 4–5 天 |
| POC-4 | ONNX Runtime 与 MindSpore Lite 的推理一致性 | 开发机 + 模拟器 → 真机 | 3–5 天 |
| POC-8 | 鸿蒙电脑长时间运行（≥ 8 小时连续检测）、后台运行、开机自启 | 鸿蒙电脑真机 | 1–2 天（含长时间运行） |
| POC-9 | **热切换**：BC-5 `Station` 聚合的最小实现；连续检测过程中部署新上线包、切换、回滚 | 开发机（Mac 或 Windows） | 3–4 天 |
| POC-10 | 模型工具链 Docker 镜像：ONNX → MindSpore Lite 转换、INT8 量化 | Docker（Mac）或 WSL2（Windows） | 2–3 天 |
| POC-6 | 在鸿蒙电脑上用 DevEco Studio 新增一个算子并运行 | 鸿蒙电脑真机 | 1–2 天 |
| POC-7 | 鸿蒙电脑采集 USB 摄像头图像 | 鸿蒙电脑真机 | 1–2 天 |
| POC-2 | Web 编辑器原型 ↔ vision-runtime，端到端运行并查看中间结果 | 开发机（Mac 或 Windows） | 4–5 天 |
| POC-11 | **方案助手的最小闭环（不用大模型）**：评估器 + `AssistSession` + 一个工作流 + 脚本顾问 | 开发机 | 5–7 天 |
| POC-12 | **大模型顾问**：在 POC-11 的基础上接入一种大模型，在工作流内调参 | 开发机 → 鸿蒙电脑 | 4–6 天 |

Windows 平台不做 POC：核心代码与 Linux 相同，差异只在适配器，风险低，放到 MVP 之后。

## 3. 执行顺序

```
POC-1 ──► POC-3a ──► POC-4（模拟器部分）──►（鸿蒙电脑到货）──► POC-3b ──► POC-8 ──► POC-6 ──► POC-7
   │
   └──► POC-9、POC-10、POC-2（在等待设备期间进行）

POC-1 ──► POC-11 ──► POC-12（独立的一条线，不依赖鸿蒙设备；POC-12 最后一项在真机上验证）
```

- POC-1 是所有工作的基础，最先做。
- 鸿蒙相关的高风险项尽早做；设备到货前先用模拟器完成能做的部分。
- 总时长约 6–8 周（按业余时间估算）。

## 4. 各 POC 详细说明

### POC-1：核心骨架

**范围**
- `core/kernel`：`Image`、`Region`、`Roi`、`PortType` 等最小集合
- BC-1 算子目录：注册表、`OperatorMeta`
- BC-2 方案编排：`Recipe` 聚合（不变量 R1～R6）、`RecipeVersion` 聚合、发布规则 P1、P5
- BC-3 检测执行：`ExecutionPlanner`、`Executor`、`Judge`、`Inspection` 聚合
- 算子：`image_input`（图像入口，由执行引擎送入图像）、`to_gray`、`threshold`、`blob`、`judge_count`
- 适配器：JSON 文件仓储、OpenCV 图像编解码、进程内事件总线
- 命令行：创建方案、发布、对图像运行检测，输出判定、判定依据和各节点耗时
- 每个上下文拆成 `domain` / `application` 两个 CMake 目标，按 ADR-17 设置链接规则

**通过标准**
- [ ] 领域层单元测试覆盖 R1～R6、P1、P5、I1～I4，全部通过，且**不链接 OpenCV**
- [ ] 故意在 BC-2 的代码中引用 BC-3 的领域类，**编译失败**
- [ ] 示例方案在 MVTec AD 的若干张图上运行，判定符合预期
- [ ] 新增一个算子只改 1 个文件
- [ ] 记录：分层和边界规则带来的额外代码量是否可以接受（主观评价 + 文件数）

### POC-3a：鸿蒙交叉编译与 NAPI

**范围**：在 Ubuntu 22.04 容器中用 lycium 编译 OpenCV（core、imgproc、imgcodecs）；同时尝试在开发机上直接用 NDK 的 CMake 编译；鸿蒙工程引用 `core/`，导出 `runInspection(recipeVersionJson, imagePath)`；ArkUI 页面显示判定和结果图。

**通过标准**
- [ ] 模拟器上运行 POC-1 的同一个方案版本，判定和判定依据与 Linux 一致
- [ ] 记录 OpenCV 产物体积和应用安装包体积
- [ ] 交叉编译过程写成可重复执行的脚本
- [ ] 顺便验证 spdlog（纯头文件方式）能否在鸿蒙上编译通过，据此决定日志库是否替换

### POC-3b：ArkWeb 桥接

**范围**：极简网页调用 `listOperators`、运行检测、显示结果图；分别用 B1（NDK JSBridge）、B2（ArkTS 代理 + NAPI）、B3（进程内 HTTP）实现；对比 Base64 和本地资源拦截两种图像传输方式。

**通过标准**
- [ ] 至少一种方案端到端可用
- [ ] 5MP 原图生成 1600px 预览并显示在网页上，延迟 < 300 ms
- [ ] 输出对比表，确定 ADR-10

### POC-4：推理一致性

**范围**：ResNet18 分类模型（算子常见，降低转换风险）；通过后再尝试异常检测骨干网络。开发机用 ONNX Runtime；鸿蒙用 MindSpore Lite Native API。

**通过标准**
- [ ] 同一张图两端输出的最大误差 < 1e-3
- [ ] 记录 CPU 推理耗时；真机上记录 NPU 推理耗时（如果可用）

### POC-8：鸿蒙电脑长时间运行

**通过标准**
- [ ] 应用在前台连续检测 ≥ 8 小时，无崩溃、无内存持续增长
- [ ] 记录应用切到后台、锁屏后检测是否继续；如果不能，调研鸿蒙的长时任务能力
- [ ] 确认能否开机自启；如果不能，记录替代方案（如开机后手动启动一次、由系统设置开启）

### POC-9：热切换

**范围**：`Station` 聚合的最小实现（S1～S5）；一个工位用文件夹图像源连续检测；后台加载新上线包；切换；连续 ERROR 自动回滚；手动回滚。

**通过标准**
- [ ] 连续检测 10,000 张图，期间进行 20 次部署和切换、5 次回滚：**没有丢失或中断任何检测**
- [ ] 每次检测记录的上线包与“检测开始时生效的上线包”一致（H-04）
- [ ] 测量切换本身的耗时和切换期间的内存峰值
- [ ] 测量检测线程里写日志的最坏情况延迟（同步写磁盘），据此决定日志是否改为异步

### POC-10：模型工具链

**范围**：基于 Ubuntu 22.04 的 Docker 镜像；包含 MindSpore Lite 转换工具和 ONNX Runtime 量化工具；先用命令行脚本完成，不做服务接口。

**通过标准**
- [ ] ResNet18 ONNX 转换为 `.ms` 成功，结果可被 POC-4 使用
- [ ] INT8 量化（用 100 张图作为量化校准集），记录精度变化
- [ ] 镜像在 Mac（Apple Silicon）的 Docker 和 Windows 的 WSL2 中都可以运行

### POC-11：方案助手的最小闭环（不用大模型）

**范围**：`Evaluator`；`AssistSession` 聚合（不变量 A1～A10）；为已有的“亮斑检测”示例写一个工作流（灰度 → 阈值 → Blob → 计数判定，可调项：阈值、最小面积）；脚本顾问；留出集评估；稳健性检查（亮度、噪声）；助手报告；命令行入口。设计见 [ddd/07-recipe-assistant.md](ddd/07-recipe-assistant.md)。

**通过标准**
- [ ] 领域层单元测试覆盖 A1～A10，且不链接 OpenCV、不访问网络
- [ ] 从工作流的初始参数出发（故意设得不好），脚本顾问经过若干轮把候选方案调到在调参集上达标
- [ ] 越界的提议（修改可调项以外的参数、超出范围、试图改变结构）被拒绝并记录
- [ ] 构造一个“只适应了调参集”的例子（调参集和留出集的光照不同）：报告里留出集的结果明显变差，并给出提示
- [ ] 产线运行的程序不链接 BC-11（故意引用则编译失败）
- [ ] 记录：一轮循环的耗时；会话记录的大小

### POC-12：大模型顾问

**范围**：实现一种大模型顾问适配器；在 POC-11 的同一个任务上，由大模型在工作流内调参。分别在三种数据外发策略下试验。再增加一个工作流（建议用带旋转定位或卡尺测量的任务），检验换任务时的表现。

**通过标准**
- [ ] 默认策略（不外发图像，只给统计信息）下，大模型顾问能把候选方案调到达标；记录用了多少轮、多少时间
- [ ] 对比“不外发图像”“外发缩略图”“外发原图”三种策略的轮数和结果，据此确定默认提供给顾问的统计信息包含哪些内容
- [ ] 领域层的检查确实拦住了策略不允许外发的内容（用假的顾问适配器记录收到的全部数据来验证）
- [ ] 大模型给出不合法的提议时，循环能继续，不会卡死或崩溃
- [ ] 大模型服务不可用时：会话以“出错”结束并保留已有的记录；编辑器的其他功能不受影响
- [ ] 鸿蒙电脑上能发起对大模型服务的调用（或记录不能的原因和替代办法）
